# 用户名枚举测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：已发现登录接口，需要比较存在账号与不存在账号的失败响应差异，通常放在依赖登录态的测试完成之后。
- 触发信号：`login_form_detected`、`auth_endpoint_detected`、`known_username_available`、`weak_pass_check_completed`、`late_auth_testing_phase`。
- 测试前置环境：通常需要存在认证接口。
- 参考工件：`login-surfaces.json`、`auth_request_sample`、`known_test_usernames`、`failed_login_responses`。
- 解锁输出：`account_enumeration_detected`、`valid_username_candidate`、`lockout_behavior_observed`、`brute_force_protection_review_needed`。
- 建议阻断（可低影响补齐时先补证再测）：未发现登录接口、无允许测试的存在账号、账号锁定风险会影响后续测试、失败登录对照。

## ⚠️ 执行时机

本 skill 整体应在渗透测试**后期**调用。其中 Step 5（账号锁定行为差异检测）会对真实账号发起连续失败登录，导致账号被锁定，因此必须在所有需要该账号正常登录的测试项目全部完成后再执行。

## 核心测试逻辑

用户名枚举的本质：对**同一登录接口**，使用**存在的用户名**和**不存在的用户名**分别发起登录请求，若两次返回值存在**任何可区分差异**，即构成用户名枚举。

差异形式包括但不限于：
- 文案差异：「密码错误」vs「用户名不存在」
- 标点差异：「密码错误！」vs「密码错误。」（含标点或不含标点）
- 业务码差异：`code: 1002` vs `code: 1003`
- 响应长度差异：两次响应 body 字节数不同
- 字段差异：存在时多返回一个字段，如 `avatar_url`
- 状态码差异：`200` vs `401`
- 跳转行为差异：存在时跳转到二次验证页，不存在时停留在登录页
- 延迟差异：存在账号需要查询密码哈希导致耗时更长
- 账号锁定差异：存在的账号连续失败后触发锁定提示或锁定状态，不存在的账号无论失败多少次始终不锁定（⚠️ 见 Step 5，后期执行）

**只要两次响应有任何稳定可重复的差异，即判定存在用户名枚举。**

## 测试账号准备

**优先使用用户提供的账号**（如测试账号、已知账号、从其他功能获取的账号）：
- 使用提供的账号 + 随机密码（如 `Test@9999x!`）构造"存在组"

**若未提供账号**，使用以下 10 个常用账号逐一尝试，取第一个能区分出差异的作为"存在组"：
```
admin
test
user
administrator
root
guest
demo
operator
manager
superadmin
```

**"不存在组"构造方式**（选其一）：
- 使用随机无意义字符串：`zz_notexist_xsec_9x7k`
- 使用当前时间戳拼接：`user_20260605_xsec`
- 密码同样使用任意随机字符串，与存在组密码不同

## 操作流程

### Step 1 — 确认登录接口

在登录页面手动输入一次错误账号密码，通过 BurpSuite 或浏览器开发者工具抓取登录请求，记录：
- 请求方法（GET / POST）
- 接口路径（如 `/api/login`）
- 参数名（如 `username`、`password`）
- 请求头（Content-Type、Cookie、CSRF token 等）

### Step 2 — 发送"存在组"请求

使用**存在的用户名** + **随机错误密码**发送登录请求。

记录完整响应：
- HTTP 状态码
- 响应 body 全文
- 响应长度（字节数）
- 关键字段：`code`、`msg`、`message`、`error`、`data` 等

### Step 3 — 发送"不存在组"请求

保持请求结构完全一致，**仅替换用户名**为不可能存在的字符串，密码同样使用错误密码。

记录完整响应（同上维度）。

### Step 4 — 对比两次响应

逐项对比以下维度：

| 对比维度 | 存在组 | 不存在组 | 是否有差异 |
|---|---|---|---|
| HTTP 状态码 | | | |
| 业务码 (code) | | | |
| 提示消息 (msg) | | | |
| 响应体长度 | | | |
| 响应字段数量 | | | |
| 跳转/行为 | | | |
| 响应耗时 | | | |

**若任意维度存在稳定差异 → 确认存在用户名枚举漏洞。**
**若所有维度完全一致 → 暂无枚举问题，进入 Step 5。**

### Step 5 — 账号锁定行为差异检测（⚠️ 后期执行）

> 执行时机见文档顶部「步骤执行约束」表格。

若 Step 4 无差异，可通过观察**账号锁定行为**进一步判断枚举：

1. 对**存在的用户名**连续发送 N 次错误密码登录请求（N 取系统锁定阈值，通常为 3～10 次）
2. 对**不存在的用户名**同样连续发送相同次数的错误密码登录请求
3. 对比两组账号第 N 次请求后的响应：
   - 存在组触发锁定（如返回「账号已锁定」「请 30 分钟后再试」），不存在组仍返回普通失败提示 → **判定：枚举（锁定行为差异）**
   - 两组行为完全一致（均锁定或均不锁定）→ 该路径无枚举

**注意事项**：
- 执行前告知客户或记录操作日志，锁定账号后及时通知相关人员解锁
- 只用最少次数验证（触发锁定后立即停止），不做持续探测
- 若无法确认系统锁定阈值，默认不执行此步骤

### Step 6 — 若未提供账号且常用账号无命中

使用全部 10 个常用账号均无法与不存在账号产生响应差异时（含锁定行为差异，如条件允许已执行 Step 5），视为暂未发现用户名枚举问题，结束测试，无需报告该项。

## 典型差异示例

```
# 示例一：文案明确差异
存在组响应：{"code": 1001, "msg": "密码错误"}
不存在组响应：{"code": 1002, "msg": "用户名不存在"}
→ 判定：枚举（文案差异 + 业务码差异）

# 示例二：标点差异
存在组响应：{"code": 0, "msg": "账号或密码不正确！"}
不存在组响应：{"code": 0, "msg": "账号或密码不正确"}
→ 判定：枚举（标点符号差异，响应长度+1）

# 示例三：业务码差异，文案相同
存在组响应：{"code": 40103, "msg": "登录失败"}
不存在组响应：{"code": 40101, "msg": "登录失败"}
→ 判定：枚举（业务码差异）

# 示例四：响应长度差异
存在组响应 body：346 字节
不存在组响应 body：289 字节
→ 判定：枚举（响应长度差异，需人工核查额外字段）

# 示例五：账号锁定行为差异（后期执行）
存在组：连续 5 次失败后响应变为 {"code": 423, "msg": "账号已锁定，请30分钟后重试"}
不存在组：连续 5 次失败后响应仍为 {"code": 1, "msg": "用户名或密码错误"}
→ 判定：枚举（锁定行为差异）⚠️ 操作后需通知客户解锁被锁定账号

# 示例六：无差异
存在组响应：{"code": 1, "msg": "用户名或密码错误"}
不存在组响应：{"code": 1, "msg": "用户名或密码错误"}
→ 判定：暂无枚举问题
```

## 证据链要求

一个完整的用户名枚举证据应包含：

1. **登录接口信息**：接口路径、请求方法、关键参数名
2. **存在组完整请求与响应**（用户名使用 `<existing-user>` 替代明文账号）
3. **不存在组完整请求与响应**（用户名使用 `<nonexistent-user>` 标记）
4. **差异对比说明**：明确指出哪个字段/维度存在差异，引用原始响应内容
5. **复现结论**：说明差异可稳定重现，非偶发

## 风险定级

- **中危**：可通过响应差异稳定区分账号是否存在（无批量限制，可辅助定向攻击）
- **高危**：在上述基础上，接口无速率限制、无验证码，且账号体系与已知弱口令规律结合可直接提高爆破成功率

## 修复建议

- 统一登录失败的错误提示与业务码，无论账号是否存在均返回相同文案与结构
- 在服务端完成账号校验与密码校验后，统一输出通用错误，避免提前短路返回
- 补充登录接口限速、验证码、账号锁定机制，并确保这些机制本身不产生新的差异信号

## 复测通过标准

- 存在组与不存在组在同一入口的 HTTP 状态码、业务码、响应文案、响应长度全部一致
- 跳转行为、验证码触发逻辑对两组账号无差异

## 报告表达模板

- **漏洞名称**：用户名枚举
- **漏洞描述**：目标系统登录接口对存在与不存在的用户名返回不同响应，攻击者可通过逐一尝试账号标识并观察响应差异，低成本确认有效用户名，为后续密码喷洒或定向攻击提供前置信息。
- **触发条件**：向登录接口分别提交存在的用户名和不存在的用户名（密码均为错误值），对比响应中的 `<差异维度>`，发现存在稳定可区分差异。
- **验证步骤**：
  1. 使用 `<existing-user>` + 错误密码请求登录接口，响应为：`<response-a>`
  2. 使用 `<nonexistent-user>` + 错误密码请求同一接口，响应为：`<response-b>`
  3. 两者在 `<差异字段>` 上存在差异，可稳定重现
- **影响分析**：攻击者可借此收集有效用户名列表，结合密码喷洒或社工手段进一步扩大攻击面。
- **修复建议**：统一登录失败响应，使账号存在与否返回相同结构与提示，并补充限速与验证码机制。
- **复测建议**：修复后使用相同存在组与不存在组账号重新对比响应，确认所有维度完全一致。
