# SQL注入测试方法论

## 编排适配

- 适用场景：请求语料中存在查询、筛选、分页、排序、报表、导出、详情、字典等带参数接口，或 SQLi hook/报错提示存在注入候选。
- 触发信号：`parameterized_request_detected`、`search_or_filter_form_detected`、`sort_or_page_param_detected`、`sqli_hook_candidate`、`passive_sql_error_match`、`sql_injection_candidate`。
- 测试前置环境：必须有可重放的低影响请求和参数基线；所有探测通过 proxy/passive hook，避免写操作和高并发。
- 必需工件：`request_corpus`、`api_inventory`、`forms/actions`、`sqli_hook_findings`、`baseline_responses`。
- 解锁输出：`sql_injection_validated`、`sql_error_info_leak_confirmed`、`sensitive_data_exposure_candidate`、`vulnerability_chain_input`。
- 阻断条件：无可控参数、仅有写操作/高风险业务动作、响应不可比较、scope 或 WAF/challenge 不允许探测。

## 适用场景

- 目标功能存在数据库查询、筛选、检索、分页、排序、导出、报表、字典查询、详情读取、批量查询等行为。
- 可疑输入位于 URL 参数、表单字段、JSON 字段、路径片段、请求头透传字段、二次请求参数或富查询条件对象中。
- 参数名称或业务语义表现出“结构位”特征，例如排序字段、排序方向、列名、表名、过滤表达式、条件拼接片段。
- 页面或接口出现异常堆栈、数据库错误关键字、响应长度异常、结果集突变、条件分支差异或处理时间异常。
- 漏洞已在单个接口被发现，需要判断是否属于同一查询构造模式并扩展到同模块、同服务、同框架接口。
- 修复后需要确认是否只是封堵了单一参数，还是已经覆盖动态 SQL 生成链路和同源接口。
## 流量钩挂与重放检测

手工逐参测试效率较低，推荐采用**流量钩挂（Hook）+ 全参重放**模式，对所有经过代理的 HTTP 请求自动进行注入探测，与人工浏览操作形成互补。测试人员只需正常点击、填写、查询，代理后端自动对每个新请求的所有参数进行五类注入探测，已测过的请求指纹自动跳过，不重复发包。

### 接入方式

使用项目内置的 `mitm_sqli_hook.py` mitmproxy addon，与现有流量采集 addon 叠加加载即可：

```bash
# 进入 web-pentest-browser-flow 目录
cd web-pentest-browser-flow

# 启动 mitmproxy，同时加载三个 addon
# Agent 手动把 MANUAL_SQLI_PORT 设置为当前未占用的 20000-60999 端口。
SQLI_MITM_PORT="$MANUAL_SQLI_PORT"
SQLI_TARGET_HOST=192.168.1.100 \
SQLI_OUT_DIR=evidence/sqli \
mitmdump \
  -s scripts/mitm_noise_filter.py \
  -s scripts/mitm_passive_hook.py \
  -s scripts/mitm_sqli_hook.py \
  --listen-port "$SQLI_MITM_PORT"

# SQLI_MITM_PORT 由 Agent 手动在 20000-60999 中选择；被占用时手动换另一个。
# 将浏览器或系统代理设置为 127.0.0.1:$SQLI_MITM_PORT
# 安装 mitmproxy 根证书（第一次使用时访问 mitm.it）
```

常用环境变量：

| 变量 | 默认值 | 说明 |
|------|--------|------|
| `SQLI_TARGET_HOST` | 空（全测） | 仅测试该主机，建议填目标 IP 或域名 |
| `SQLI_OUT_DIR` | `evidence/sqli` | findings.jsonl 输出目录 |
| `SQLI_THREADS` | `3` | 并发测试线程数（建议 2–5） |
| `SQLI_TIMEOUT` | `10` | 每个探测请求超时秒数 |
| `SQLI_TEST_COOKIES` | `false` | 是否一并测试 Cookie 参数 |
| `SQLI_MAX_BODY` | `50000` | 响应体超过此字节数跳过 |

### 如何最大化覆盖面（手动操作策略）

代理钩挂只能观察到浏览器实际发出的请求。要尽可能多地发现问题，测试人员应系统地触发所有带参数的功能：

**优先操作列表（按覆盖价值排序）**

1. **所有搜索 / 筛选 / 查询框**：输入不同关键词后点击查询，特别注意模糊搜索、分类筛选、日期范围、下拉选择器。每个查询框至少触发一次，参数变化才会被捕获。
2. **所有列表页的分页 / 排序控件**：点击每一列的排序按钮，翻页，修改每页条数——这些往往携带 `orderBy`、`sortField`、`pageSize` 等结构位参数。
3. **所有表单提交**：注册、登录、信息修改、提交申请——POST 表单体中每个字段都会被测试。填写合理值后提交，不要只停在页面上。
4. **所有详情 / 编辑接口**：点进每一条记录的详情页，编辑后保存，触发带 ID、编号等参数的 GET/POST 请求。
5. **报表 / 导出 / 打印功能**：这类接口往往带有复杂查询条件且容易被忽略。
6. **字典 / 下拉数据接口**：选择下拉框时通常触发 `/dict`、`/option` 之类的辅助查询请求，参数简单但容易有注入。
7. **左侧菜单 / 树形结构**：逐节点展开，每次展开都会触发带节点 ID 的查询。
8. **Cookie 中的业务参数**（如开启 `SQLI_TEST_COOKIES=true`）：部分系统把用户 ID、机构代码、权限标识存在 Cookie 中并透传给后端查询。

**操作节奏建议**：打开每个功能模块后，先在正常数据下完整走一遍操作流程（这会建立基线请求并触发测试队列）；发现页面有多个筛选条件时，分别单独改变每个条件后提交，确保每个参数组合都被捕获。不需要等待探测结果，继续正常操作即可，探测在后台线程异步执行。

### 响应相似度计算辅助规则

所有相似度判断依赖 **Levenshtein** 或 **Jaccard** 算法，并叠加以下长度阈值辅助：

- 两响应长度相同 → 直接视为相似度 100%
- 两响应长度差 > 100 → 辅助相似度定为 90%（取算法值与辅助值中的较大/较小者参与比较）
- 两响应长度差极小时 → 先剥离首尾公共前后缀，再删除明显为 PoC 的片段，若两串均变空则相似度 100%，若一空一非空则相似度 0%，其余情况再算法计算

### 五类注入探测算法

以下以 `value` 表示参数原始值，`respbody` 表示原始响应体，`sim(A,B)` 表示 A 与 B 的相似度（百分比）。

#### 1. 报错型（errsql）

将参数值替换为 `value + poc`，其中 poc 集合：

| poc | 说明 |
|-----|------|
| `'` | 普通单引号 |
| `%DF'` | 宽字节 + 单引号 |
| `"` | 双引号 |
| `%DF"` | 宽字节 + 双引号 |
| `` ` `` | 反引号 |
| `%27` / `%22` | URL 编码单/双引号 |
| `\u0027` / `\u0022` | JSON Unicode 编码单/双引号（仅 JSON 数据体） |

发送后，使用约 100 条数据库报错正则规则匹配响应体（覆盖 MySQL、SQL Server、Oracle、PostgreSQL 常见错误关键字）。任一规则命中即标记为 **errsql**，备注中注明匹配到的具体正则规则。

#### 2. 数字型（numsql）

仅当 `value` 为纯数字且不是 JSON 键值时执行：

```
poc1: value-0-0-0  →  respbody1
  sim(respbody, respbody1) > 90%  →  继续
poc2: value-abc    →  respbody2
  sim(respbody2, respbody) < 90%
  AND sim(respbody2, respbody1) < 90%  →  标记 numsql
```

逻辑：等值运算不影响结果（-0-0-0 仍等于原值），但字母替换使结果发散，说明参数进入了数值型 SQL 条件。

#### 3. ORDER 排序型（ordersql）

仅当 `value` 非空时执行（Jaccard 相似度）：

```
poc1: value,0        →  respbody1
poc2: value,xxxxxx   →  respbody2
  sim(respbody, respbody1) < 90%  →  继续
  sim(respbody, respbody2) < 90%  →  继续
poc3: value,1        →  respbody3
  sim(respbody, respbody3) > 90%  →  标记 ordersql（1 为合法排序方向）
  未满足 →  继续
poc4: value,2        →  respbody4
  sim(respbody, respbody4) > 90%  →  标记 ordersql
```

逻辑：追加随机串使排序破坏（响应变化），而追加 1 或 2 仍为合法排序值（响应恢复），两阶段差异定位结构位注入。

#### 4. 字符型（stringsql）

JSON 数据中该值需被双引号包裹才执行：

```
poc1: value'     →  respbody1   （单引号）
poc2: value''    →  respbody2   （两个单引号）
  sim(respbody, respbody1) < 90%  →  继续
  sim(respbody1, respbody2) < 90%  →  继续（注意是 respbody1 vs respbody2，
                                      因为原始有数据时 respbody ≈ respbody2）
poc3: value'+'   →  respbody3
  sim(respbody, respbody3) > 90%  →  标记 stringsql（MySQL 字符串连接）
  未满足 →  继续
poc4: value'||'  →  respbody4
  sim(respbody, respbody4) > 90%  →  标记 stringsql（Oracle/PG 字符串连接）
```

逻辑：单引号破坏语法使响应偏离；两个单引号先破坏再尝试闭合；`'+'` 或 `'||'` 将原始值完整拼回，响应恢复则确认注入。

#### 5. 布尔型（boolsql）

JSON 数据中该值需被双引号包裹才执行：

```
poc1: value'||EXP(710)||'   →  respbody1
  sim(respbody, respbody1) < 90%  →  继续
  poc2: value'||EXP(290)||'  →  respbody2
    sim(respbody1, respbody2) < 90%  →  走路径 A
    sim(respbody1, respbody2) ≥ 90%  →  走路径 B

路径 A（EXP(710) vs EXP(290) 结果不同）：
  poc4: value'||1/1||'  →  respbody4
    sim(respbody2, respbody4) > 90%  →  标记 boolsql

路径 B（两者相近，改用除法）：
  poc3: value'||1/0||'  →  respbody3
    sim(respbody, respbody3) > 90%  →  继续
  poc4: value'||1/1||'  →  respbody4
    sim(respbody2, respbody4) > 90%  →  标记 boolsql
```

逻辑：`EXP(710)` 会在 MySQL 中溢出报错，`EXP(290)` 不溢出；`1/0` 产生除零错误；`1/1` 返回正常值。通过两组布尔差异交叉验证，确认条件注入。

### 结果标记含义

| 标签 | 类型 | 备注 |
|------|------|------|
| `errsql` | 报错注入 | 括号内注明命中的报错正则规则 |
| `numsql` | 数字型注入 | - |
| `ordersql` | ORDER BY 结构位注入 | - |
| `stringsql` | 字符型注入 | - |
| `boolsql` | 布尔盲注 | - |

多类型命中时以 `-` 拼接显示，如 `errsql-stringsql`。

### 流量钩挂检测的局限与配合

- 响应体超过 50000 字节的请求会跳过扫描（性能限制），需人工补充。
- 动态结果、缓存、CDN 回包可能导致相似度计算偏差，需人工二次确认存疑标记。
- 时间盲注无法通过响应差异发现，需另行对可疑接口单独测试。
- 扫描到的疑似注入点必须人工进行最小化复现，确认差异可解释、可稳定复现，方可出结论。

## 测试思想

- 先判断“输入是否影响 SQL 结构或条件”，再判断“影响是否可稳定复现”，不要先追求拿到大量数据。
- 优先做低影响、最小化验证：证明查询逻辑被操控即可，不以导出数据、扩大结果集或高负载操作作为首要目标。
- 始终建立对照组。SQL 注入的核心不是“报错了”，而是“在仅改变可疑输入的前提下，响应行为出现可解释差异”。
- 将参数分成两类处理：
  - 数据位参数：通常落在等值、模糊、区间、分页条件中。
  - 结构位参数：通常落在排序、列名、表名、拼接条件、动态片段中，修复难度更高，也更容易批量扩散。
- 发现单点后，立刻思考其背后的拼接模式、ORM 用法、查询构造器或公共组件，避免把系统性问题误写成单接口问题。
- 对自动化工具结果保持克制。工具可以帮助筛选，但结论必须回到人工可解释的请求、响应和差异证据。

## 操作流程

1. 明确授权边界、测试账号、业务时段和允许的影响范围，优先选择低峰期与低敏数据路径。
2. 盘点入口，优先关注检索、列表、报表、导出、树形查询、动态筛选、分页排序、详情联查等与数据库交互密集的功能。
3. 固定基线请求，记录原始参数、身份态、返回码、响应长度、关键字段、页面结果和响应时间。
4. 从语义上挑选可疑参数，优先测试搜索词、编号、名称、时间范围、排序字段、排序方向、页码、表标识、字典编码等。
5. 先做轻量扰动，观察错误回显、空结果、全结果、字段缺失、排序失真、响应长度变化、时间差异等现象。
6. 为每个可疑参数构造至少两组对照：
   - 保持业务语义成立的等价输入。
   - 触发不同查询分支但不扩大破坏面的非等价输入。
7. 若怀疑为报错型，确认异常内容是否随输入变化而变化，且能定位到数据库层或 SQL 解析层，而非前端校验或业务异常。
8. 若怀疑为布尔型，确认真值与假值请求在结果数量、页面元素、分页总数、状态码或响应体关键片段上存在稳定差异。
9. 若怀疑为时间型，只做最轻量的时间差验证，并排除网络抖动、缓存命中、异步任务和后端慢查询带来的偶然延迟。
10. 若怀疑为结构位注入，重点验证排序字段、排序方向、列名、表名、筛选表达式是否被直接拼接，而不是只盯常规搜索框。
11. 一旦确认存在注入，仅保留能证明“可控查询逻辑”的最小证据，不继续做数据枚举、批量探测或高负载尝试。
12. 以代码路径或接口族为单位扩展排查：同列表组件、同报表引擎、同 DAO 模板、同动态 SQL 片段应视为同源风险面。
13. 修复复测时先回归原始问题点，再复测同模块同类型参数，最后检查是否仍有旁路接口复现同类差异。

## 关键判断点

- 只有异常信息而没有稳定可控差异，不足以直接定性为 SQL 注入；可能只是错误处理不当或输入校验缺失。
- 只有工具命中而没有人工复核，不足以出结论；至少要能说明哪个参数、什么差异、为什么指向 SQL 层。
- 同一参数在不同身份、不同功能入口、不同编码方式下表现不同，往往说明拼接链路不止一处，需按入口拆分判断。
- 排序分页类参数出现报错、500、空白页、排序错乱时，要优先怀疑结构位注入，而不是简单归因于“参数格式错误”。
- 反射值、模板渲染差异、权限过滤、缓存回包都可能制造假象，必须结合响应字段和服务端行为做排除。
- 鉴权后接口同样可能是高风险：若低权限角色可影响核心查询逻辑并触达敏感数据面，风险不因“需要登录”而自动下降。
- “全站存在”不能只凭扫描器列表下结论。报告中应把“已验证接口”和“推测同源接口”分开表述。
- 复测时若只修补单个参数名、单个接口或单个前端入口，而同类构造仍存在，应视为未完成整改。

## 证据链要求

- 保留一份可复现的基线请求和一份最小化验证请求，确保两者只在目标参数或目标条件上存在必要差异。
- 记录请求方法、接口路径、参数位置、身份上下文、时间戳、状态码、响应长度、关键字段差异和页面表现差异。
- 对布尔型或条件差异型问题，保留真值组与假值组对照，证明结果变化具有方向性和稳定性。
- 对报错型问题，保留错误关键字、异常层级和与输入联动的证据，但不要在 Skill 中沉淀真实报错内容。
- 对时间型问题，至少保留多次测量结果与基线耗时，证明差异超过正常抖动区间，且测试动作本身足够轻量。
- 对结构位问题，说明受影响的是排序、列名、表名或动态片段，而不是泛泛写“参数可注入”。
- 若使用自动化工具，证据中必须能回落到人工可解释的请求和响应，不以工具截图替代技术结论。
- 证据应证明“已验证范围”和“待开发侧举一反三排查范围”是两层概念，避免报告边界失真。

## 风险定级思路

- 高危：可稳定控制查询条件或结构，影响核心业务数据、敏感数据面、多接口同源链路，或在低权限身份下影响高价值数据访问。
- 中危：注入点成立，但受限于强业务前置条件、严格权限边界、较窄数据域或单点接口，影响面可控且不易横向扩散。
- 低危：仅出现弱错误信号、模糊异常或不稳定差异，尚不足以证明 SQL 逻辑被控制；这类情况更适合先记为待确认问题。
- 定级时同时考虑四个维度：可利用稳定性、所需权限、影响数据面、同源扩散可能性。
- 对“排序字段/表名/动态筛选”这类结构位注入，应适当提高关注度，因为它通常暴露的是公共查询构造缺陷而非单点编码疏漏。
- 对复测场景，不要因为“原问题已有修补动作”而自动降级；若同类接口仍可复现，应按当前实际影响重新定级。

## 修复与复测

- 修复应以参数化查询为主线，确保查询语句与外部输入分离，不接受“仅靠转义”作为根治方案。
- 对无法参数化的结构位输入，使用明确白名单：允许的列集合、排序方向集合、表标识映射集合，而不是直接透传。
- 统一梳理动态 SQL、ORM 模板、通用查询组件、报表引擎、自定义筛选器和排序封装，避免只修业务层单点。
- 服务端应补足输入类型约束、异常处理收敛和最小化错误回显，但不要把“隐藏报错”误当成修复完成。
- 复测顺序应固定：
  1. 原始接口原始参数是否失效。
  2. 同页面其他同类参数是否仍可复现。
  3. 同模块其他列表、导出、筛选、报表接口是否共享同样问题。
  4. 不同身份下是否仍可通过同源参数触发异常差异。
- 复测通过的标准不是“单条 PoC 失效”，而是“同源构造链路已被统一收敛，且异常与差异现象消失”。

## 报告表达模板

- 漏洞标题：SQL注入
- 漏洞概述：在 `<功能/接口类型>` 的 `<参数位置>` 中，外部输入参与了后端 SQL 条件或结构拼接，导致查询逻辑可被非预期影响。
- 触发条件：攻击者在已授权、低影响测试条件下，对 `<suspect-param>` 进行最小化构造后，接口返回出现可稳定复现的 `<报错差异/结果差异/时间差异>`。
- 验证结论：通过基线请求与对照请求比较，可确认差异并非由缓存、权限切换、前端校验或随机抖动引起，而是与数据库查询处理逻辑相关。
- 影响范围：已验证 `<已验证接口数量或模块>` 存在问题；结合相同查询组件、动态 SQL 模式或同类参数设计，开发侧需继续排查 `<同源范围>`。
- 风险评价：该问题可影响 `<数据类型或业务能力>` 的查询安全性。若同源接口广泛复用，实际影响面可能大于当前已验证范围。
- 修复建议：采用参数化查询处理数据位输入；对排序、列名、表名等结构位输入实施白名单映射；统一整改动态 SQL 组件并开展同源复测。
- 复测结论：复测应覆盖原接口、同模块同类接口及同源查询组件；仅当原问题点和同源问题点均不再出现可解释差异时，方可判定修复完成。
