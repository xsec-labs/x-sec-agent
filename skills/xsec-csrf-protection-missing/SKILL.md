# CSRF防护缺失测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：登录后存在状态变更表单/API，并主要依赖 Cookie 会话，需要验证 CSRF token、Origin/Referer、SameSite 和二次确认。
- 触发信号：`state_changing_form_detected`、`state_changing_api_detected`、`cookie_auth_state_changing_endpoint`、`csrf_token_missing`、`samesite_none_or_lax_observed`。
- 测试前置环境：通常需要有已登录测试账号和可逆、低影响的状态变更动作；跨站触发需使用受控测试页面。
- 参考工件：`forms/actions`、`request_corpus`、`browser_state`、`controlled_cross_site_page`、`before_after_state_evidence`。
- 解锁输出：`csrf_validated`、`cookie_security_review_needed`、`session_management_review_needed`。
- 建议阻断（可低影响补齐时先补证再测）：无状态变更入口、动作不可逆/会影响真实业务、接口已要求强 CSRF/再认证。

## 适用场景

- 目标是已登录用户可访问的状态变更接口，涉及新增、修改、删除、发布、审批、配置变更、成员关系调整等操作。
- 现象表现为接口依赖浏览器自动携带登录态，但看不到稳定的站点侧请求绑定控制，例如独立的 CSRF token、一次性挑战、关键操作二次认证。
- 前端线索包括表单隐藏字段较多、旧框架页面、编辑保存类按钮、multipart 上传、JSON 编辑接口、批量配置接口。
- 需要在低影响、最小化验证前提下证明“跨站可发起且服务端接受”，而不是追求破坏性利用。
- 需要做复测或批量排查，确认问题是单点缺陷还是同模块、同路由族、同鉴权中间件的系统性缺失。

## 测试思想

- 把 CSRF 判断为“状态变更请求是否只相信登录态，而没有额外确认请求确实来自本站业务流”。
- 先证明正常业务流能完成操作，再构造跨站对照组；没有对照组，结论容易停留在猜测。
- 低影响验证优先选取可逆、无业务副作用、可单独标记的字段或测试对象，例如备注、临时标题、测试分组名等占位值。
- 不把“存在隐藏字段”直接视为防护成立。隐藏字段、框架状态字段、业务主键不等于 CSRF 防护，关键在于服务端是否校验不可伪造的请求绑定信息。
- 不把“前端报错”直接视为验证失败。若后端状态已变化，仍应判定为有效风险并保留“响应异常但变更生效”的证据。
- 不把“接口需要 POST”或“接口是 JSON”视为天然安全。请求格式不是防护，关键仍是服务端验证。

## 操作流程

1. 信息收集
- 找出所有状态变更入口：保存、提交、发布、新增、编辑、启停、分配、导入、绑定、审批。
- 记录请求方法、路径形态、参数来源、是否自动带 Cookie、是否出现 CSRF token、Origin/Referer、二次确认字段。
- 识别同类接口族：同模块多个编辑接口、同控制器多个保存接口、同一旧页面体系下的提交接口。

2. 建立基线请求
- 在测试账号下完成一次正常操作，抓取真实请求，确认哪些字段是业务必需字段，哪些只是展示或框架噪声。
- 确认状态变化的观察点：列表页、详情页、审计日志、成功回执、版本号、更新时间、条目数量。
- 优先筛出最小请求集合，只保留能触发该业务动作的必要字段，减少误判。

3. 构造对照组
- 对照组 A：站内正常提交，应成功并产生预期状态变化。
- 对照组 B：受控第三方页面或受控跨站环境触发最小化请求，保留登录态，其余条件尽量不变。
- 对照组 C：去掉登录态或使用失效会话，预期失败，用于证明结果不是匿名访问造成。
- 对照组 D：如果系统声称已有防护，则补做缺失 token、错误 token、缺失 Origin/Referer 等负向验证。

4. 最小化验证
- 只验证一个可逆动作，不做批量写入、不做敏感删除、不改生产关键配置。
- 若接口影响对象较大，优先选测试对象、空白记录或隔离记录；必要时先与委托方确认可验证范围。
- 若跨站请求触发后前端报错、跳转异常或返回通用错误，立即回到观察点确认状态是否已改变。

5. 影响面扩展
- 一旦单点成立，抽样同模块 2 到 5 个同类接口，判断是否共享同一缺失原因。
- 若多个接口都缺少 token/来源校验，应总结为“控制点缺失于接口族或中间件层”，不要只报单一页面。
- 若只有少数接口受影响，继续找差异：是否新旧页面混用、是否某些接口绕过统一网关、是否仅 multipart 或旧表单链路缺失。

6. 留证与收口
- 固化正常请求、跨站对照请求、最终状态变化三类证据。
- 记录验证时间、账号角色、目标对象、请求前后差异，确保报告能解释“谁在什么条件下触发了什么变化”。
- 验证完成后恢复测试数据，避免残留无意义记录影响复测。

## 关键判断点

- 仅有登录 Cookie 即可完成跨站状态变更，且服务端未要求独立的不可伪造校验信息，可判断为真实风险。
- 如果请求里有框架状态字段、隐藏主键或业务参数，但这些值可从正常页面获得并被跨站重放，不能视为有效 CSRF 防护。
- 成功回执不是唯一依据。更可靠的是服务端状态变化、列表新增、配置被改写、字段值改变、审计时间更新。
- 报错页面也不能直接否定风险；应核对是否存在“响应失败但副作用成功”的情况。
- Origin/Referer 校验只能作为辅助判断。即使存在，也要看是否服务端强制校验、是否允许空值放行、是否仅前端校验。
- SameSite 可以降低部分利用路径，但不应替代服务端 token 或关键操作再认证；报告中应把它写成辅助控制而非唯一修复点。
- CORS 不是 CSRF 防护本身。跨站表单提交、部分导航行为、浏览器自动带 Cookie 的场景与是否允许脚本读响应是两回事。
- 若接口已要求重新输入密码、短信确认、一次性口令或硬件签名，再结合实际请求流判断是否足以阻断跨站伪造，不要机械判洞。

## 证据链要求

- 证据一：正常业务流请求与成功结果，证明该接口确实能完成目标状态变更。
- 证据二：跨站对照请求的触发方式与关键请求要素，证明请求来自受控第三方上下文而非站内页面。
- 证据三：服务端接受后的可观察结果，包括页面列表变化、详情字段变化、回执码、时间戳、审计痕迹。
- 证据四：账号与权限关系，至少说明验证账号角色、被修改对象类型，以及该动作本来属于已登录用户权限范围内的合法操作。
- 证据五：若响应异常但状态已变，更要同时保存异常响应和最终状态变化，避免结论被“报错即失败”反驳。
- 证据六：若判断为批量问题，至少给出一个完整样本和若干同类接口抽样结论，说明共性控制缺失点。
- 全部证据填入原始 target URL、角色、对象 ID 和测试标记，不使用占位符替换真实标识。

## 风险定级思路

- 高危：可由高权限或关键业务账号触发敏感变更，且操作涉及权限配置、账户控制、关键业务数据、批量接口或同模块大面积缺失。
- 中危：影响普通业务数据或局部配置，能够稳定跨站触发并完成状态变更，但影响对象、权限范围或业务后果相对受限。
- 低危：仅影响低敏感个人资料或非关键元数据，且存在额外限制降低可利用性，例如强交互确认、隔离范围小、实际浏览器行为限制明显。
- 若同一问题在多个接口重复出现，应根据“控制缺失范围”上调，而不是按单接口影响孤立定级。
- 若仅证明了请求可发出、但未证明状态变化，应保守写为待确认，不直接上升为有效漏洞。

## 修复与复测

- 修复优先级以服务端控制为主：为所有状态变更接口统一增加 CSRF token 校验或等价的不可伪造请求绑定机制。
- 对关键操作叠加再认证、一次性确认或事务签名，避免单纯依赖会话 Cookie。
- 将 Origin/Referer 校验、SameSite Cookie、敏感操作最小化暴露面作为纵深防御，而不是唯一修复方案。
- 复测时至少覆盖四类情况：正常合法请求成功、缺失 token 失败、错误 token 失败、跨站触发失败。
- 复测不要只盯住原始样本接口，应抽样同模块和同中间件链路的其他状态变更接口，确认不是“补一个、漏一片”。
- 对曾出现“前端报错但后端生效”的接口，复测必须同时检查响应和最终状态，确认副作用确实被阻断。

## 报告表达模板

- 漏洞名称：CSRF防护缺失
- 受影响对象：`<模块/功能>` 下的 `<状态变更操作>`
- 验证结论：在测试账号已登录的前提下，受控第三方上下文可触发浏览器向 `<state-changing-endpoint>` 发起跨站请求；服务端未对 `<csrf-token / 请求来源 / 关键再认证>` 进行有效校验，导致 `<可逆业务状态>` 发生变化。
- 判断依据：正常业务流与跨站对照组请求在业务参数上等价，但跨站请求仍被接受；请求后观察到 `<列表新增 / 字段修改 / 配置变更 / 状态切换>`。
- 影响说明：攻击者无需直接获取账号密码，只需诱导已登录用户访问受控页面，即可能在其权限范围内完成未预期的状态变更；若受害者具备更高权限，业务影响随之扩大。
- 修复建议：在服务端统一引入并强制校验 CSRF 防护机制，对关键操作增加再认证，并辅以 Origin/Referer 校验及 SameSite 等纵深防御。
- 复测结论：修复后，正常站内请求保持可用，缺失或错误校验信息的请求被拒绝，跨站触发不再造成状态变化。
