# 配置文件与备份文件泄露测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：DirSearch、接口暴露或静态目录中发现 `.env`、配置、备份包、压缩包、数据库备份、部署残留、Git/SVN/CVS 目录。
- 触发信号：`config_path_detected`、`backup_path_detected`、`env_file_detected`、`vcs_directory_detected`、`archive_file_detected`、`db_backup_detected`。
- 测试前置环境：通常需要有可访问的候选路径；下载/解压只能针对最小必要工件并在本地隔离目录进行。
- 参考工件：`dirsearch_results`、`candidate_file_response`、`passive_findings`、`artifact_metadata`。
- 解锁输出：`cloud_secret_candidate_detected`、`db_credential_candidate`、`internal_network_leakage_candidate`、`source_code_leakage_candidate`、`unauth_access_candidate`。
- 建议阻断（可低影响补齐时先补证再测）：未发现候选文件、工件过大、路径仅返回公开模板/样例且无敏感内容。

## 适用场景

- **路径扫描后跟进**：路径扫描（dirsearch、ffuf、gobuster 等工具）返回命中后，对疑似配置、备份、版本控制工件的路径进行深入验证。
- **配置与备份文件**：目标存在公开访问的静态目录、下载中心、更新目录、附件目录、部署残留目录或历史发布路径。已发现可疑工件为配置文件、环境文件、备份包、压缩包、安装更新包、导出包、临时副本或编辑器残留文件。
- **Git 仓库泄露**：目标 Web 根目录下存在 `.git/` 目录可访问，常见入口包括 `.git/config`、`.git/COMMIT_EDITMSG`、`.git/FETCH_HEAD`、`.git/index`、`.git/HEAD`、`.git/logs/HEAD`、`.git/refs/heads/master`（或 main）等。可借助 git-dumper、GitHack 等工具还原源码，进一步从中提取配置与凭据。
- **SVN/CVS 仓库泄露**：目标存在 `.svn/entries`、`.svn/wc.db`、`CVS/Root`、`CVS/Entries` 等路径可访问，可利用 dvcs-ripper 等工具还原历史版本，再从中分析配置内容。
- **危害证明场景**：在已确认工件可访问后，需要从中提取并原样保留账号、口令、连接串、API Key、内部主机信息等，证明现实可利用性。
- **组合场景**：备份包中包含配置文件、git 仓库中有 `.env` 提交记录、安装包内嵌明文配置、环境文件暴露生产连接信息等多层组合问题。

## 测试思想

- **核心目标是提取与证明，而不只是确认存在。** 发现文件可访问只是起点，真正的价值在于：从中提取出有现实意义的敏感字段，并说明这些字段能够支撑什么样的后续攻击能力，从而让报告的读者理解真实风险。
- 先回答两个问题：文件能否被当前身份获取，文件内容是否包含正在生效的敏感能力。
- 不把“看起来像配置文件”直接等同于漏洞。真正的风险在于它是否暴露认证材料、连接关系、内部服务信息、部署细节或可复用的控制要素。
- 不把“历史截图、OCR 文本、旧报告路径”直接等同于当前有效泄露。必须确认当前响应、访问条件和内容稳定可复现。
- 不把“可逆编码”误判为“安全保护”。编码、轻度混淆、可本地解码字符串通常仍应视为泄露线索，而不是有效防护。
- 不把“删掉单个文件”视为完整修复。此类问题常来自发布流程、备份策略、对象存储权限、目录映射或运维习惯，往往会在同类路径重复出现。
- 验证时以最小化为原则。只需证明“匿名或低权限可获取敏感工件”以及“该工件中的关键字段具有现实意义”，不需要进一步消费真实数据或执行高影响操作。

## 参考方法（目标与常见路径，不是必须顺序）

下面是达成测试目标的常见路径，不是必须照做的脚本：可以合并步骤、调整顺序、跳过已经确认过的部分，或者换成你判断更合适的方法，只要仍能支撑下面的判断点和证据要求。

1. 明确测试边界。
   确认允许身份、允许访问方式和不可触碰的数据边界，固定本次测试针对的系统、模块和环境。

2. 梳理入口线索。
   从公开下载页、静态资源引用、前端脚本路径、更新提示、目录命名习惯、附件链接、错误回显和已知发布结构中收集可疑工件入口。此外，路径扫描命中结果是重要来源，尤其关注状态码 200/403/301 的敏感路径。

3. 建立工件清单。
   将候选目标按"配置文件""环境文件""备份压缩包""历史版本副本""安装更新包""导出包""目录索引""Git/SVN 仓库"分类，避免把所有路径混在一起处理。

4. 构造对照组。
   至少准备一组正常公开资源和一组不存在或无权限的同级路径，用于判断当前现象是正常下载行为、误报，还是异常暴露。

5. 验证可访问性。
   记录响应状态、鉴权要求、返回头、文件名、大小、内容类型和是否支持直接下载，确认工件是否确实能被当前身份稳定获取。

6. 初步判定内容敏感性。
   重点关注账号、口令、连接串、租户标识、内部主机描述、对象存储配置、消息通道配置、证书材料、环境差异标记和调试开关。

7. 拆分"字段存在"与"字段生效"。
   判断该内容是当前生效配置、历史残留、测试环境样本、占位值还是无效模板，避免仅凭字段名就上报高危。

8. 做最小化验证，提取关键敏感信息。
   优先采用只读、无副作用方式证明风险。根据工件类型选择对应提取策略：

   **配置/环境文件（`.env`、`config.*`、`*.yml`、`*.properties`、`*.ini`、`*.xml` 等）：**
   - 下载文件，搜索以下模式：数据库连接字符串（`jdbc:`、`mysql://`、`host=`）、口令字段（`password`、`passwd`、`secret`、`key`）、API Token（`token`、`apikey`、`api_key`、`access_key`）、内网地址（RFC1918 段）。
   - 对 Base64 或简单编码的值进行本地解码，记录结果但不传播原始值。
   - 判断字段是否具备完整连接四元组（host/ip + port + user + password），完整四元组的风险显著高于仅有单一字段。

   **备份压缩包（`.zip`、`.tar.gz`、`.rar`、`.bak` 等）：**
   - 不在生产环境解压；本地解压后按配置文件策略逐层扫描。
   - 特别检查包内是否含有 `.env`、`config/`、`settings.*`、`database.*` 等子路径。
   - 记录包内结构和命中的敏感字段所在层次，作为组合链路的一部分。

   **Git 仓库泄露（`.git/` 可访问）：**
   - 第一步验证：访问 `.git/config` 确认仓库信息（远程地址、分支名），访问 `.git/HEAD` 确认当前引用，访问 `.git/COMMIT_EDITMSG` 确认最近提交信息。
   - 第二步还原：使用 git-dumper（`git-dumper http://target/.git/ ./repo`）或 GitHack 在本地还原源码，无需直接访问完整 pack 文件列表。
   - 第三步提取：在还原的代码库中，重点检查 `*.env`、`config/`、`settings.py`、`application.yml`、`database.php`、`web.config` 等常见配置文件；同时查看 git log 和历史提交，因为即使当前版本已删除敏感配置，历史提交中可能仍存在（`git log --all --full-history -- '*.env'`）。
   - 第四步识别：提取数据库连接串、私钥、API 密钥、内部服务地址、硬编码口令，记录原始字段名、完整值和所在文件路径。
   - 若仅做最小化验证而不还原完整仓库：访问并记录 `.git/config`、`.git/COMMIT_EDITMSG` 的响应内容足以证明仓库可访问。

   **SVN/CVS 仓库泄露（`.svn/`、`CVS/` 可访问）：**
   - 访问 `.svn/entries`（SVN 1.6 及以下）或 `.svn/wc.db`（SVN 1.7+）确认可访问性。
   - 访问 `CVS/Root`、`CVS/Entries` 确认 CVS 仓库信息。
   - 使用 dvcs-ripper（`rip-svn.pl -v -u http://target/`）或 SvnExploit 提取源码；提取策略与 Git 场景相同，重点关注配置文件和历史修订版本。

9. 识别组合链路。
   若问题体现为多层结构（例如"公开 .git -> 还原源码 -> 源码中含 .env -> .env 中有数据库连接串"），应把入口、载体、内容三层关系串起来，而不是只报告其中一层。清晰的链路有助于说明该问题为何是高风险，而不是"只是一个目录暴露"。

10. 评估影响面。
   横向检查同命名规则、同目录、同发布链路、同对象存储桶、同下载中心和历史版本分发点，确认是否为单点暴露还是流程性问题。对于 git/svn 泄露，检查是否存在多个项目目录下均有 `.git/` 可访问。

11. 固化证据。
   保留完整原始访问请求、响应、文件指纹、敏感字段和值、对照结果、认证状态和时间点，确保后续 Agent 可以直接复核并复用真实敏感值。

12. 形成复测清单。
   在提交建议前先列出所有需回归的位置，包括原始路径、同类后缀、历史包、缓存节点、镜像副本和被暴露凭据的轮换状态。
## 关键判断点

- 当前响应是否真实可用。
  返回错误页、空白包、占位文件或历史截图，不足以证明当前仍存在泄露。

- 工件是否对当前身份不应公开。
  合法下载中心中的公开说明文档不构成此问题；匿名或低权限可获取含敏感内容的配置或备份工件才是重点。

- 内容是否足以构成敏感信息。
  仅有文件路径、通用产品名、非敏感日志级别通常不足以定性；能揭示认证材料、内部连接关系或部署细节时风险显著上升。

- 敏感字段是否为活跃值。
  占位符、示例值、失效测试配置和未启用模块应与当前生产化、生效配置区分开来。

- 编码是否只是伪保护。
  Base64、十六进制、可逆混淆或同文件中同时出现算法线索与密文时，通常不能作为风险消除依据。

- Git/SVN 泄露是否可还原源码。
  仅 `.git/config` 可访问（但 pack 文件不可获取）时，属于信息泄露但还原能力受限；若 `objects/` 目录或 pack 文件可访问，则基本可还原完整或部分源码，危害级别显著上升。历史提交中存在的敏感配置即使当前代码已删除，仍构成可利用泄露。

- 是否存在组合证据。
  单看备份包或单看配置片段都可能被低估；当可访问工件与敏感字段、当前系统结构能相互印证时，结论更稳固。Git 场景中，仓库远程地址 + 提交历史 + 源码内配置文件三者叠加是强组合证据。

- 影响面是单文件还是流程性残留。
  若相同规则在多个模块、多个版本、多个分发链路重复出现，说明问题更接近发布治理缺陷，而非偶发文件摆放失误。

## 证据链要求

- 记录测试身份。
  明确是匿名态、低权限测试账号还是指定业务角色，说明为何该身份不应获得该工件。

- 保留入口证据。
  记录 `<artifact-path>`、访问时间、响应码、响应头摘要、文件大小或目录索引表现，证明工件可被稳定获取。Git/SVN 场景应记录核心探针路径（`.git/config`、`.git/HEAD`、`.svn/entries` 等）的响应状态。

- 保留文件指纹。
  记录文件名、后缀、摘要标识或片段性结构特征，避免完整保存和传播敏感内容。

- 展示完整原始内容。
  截图或摘录保留字段名、结构位置、原始 secret、内部端点、测试凭据和必要上下文，不使用占位符。Git 仓库场景中，commit 摘要、仓库 remote URL（包括 token）和 `.env` 字段名及值均保留原文。

- 体现对照组。
  说明正常资源、无效路径或修复后路径与漏洞路径之间的响应差异，证明不是偶发网络现象或误判。

- 说明生效性依据。
  写清为何认为字段不是摆设，例如命名与当前系统一致、同文件存在完整连接四元组、配置结构与运行组件匹配。对于历史提交中的敏感值，说明为何判断仍生效（如字段名在当前系统中对应的组件仍在运行）。

- 约束验证范围。
  说明未进行破坏性访问、未批量提取数据、未扩展到未授权系统，结论建立在最小化验证基础上。Git 场景说明是否实际执行了仓库还原，还原操作是否在隔离的本地环境进行。

- 绑定修复前后状态。
  复测时保留"原路径访问结果""同类路径复核结果""凭据轮换状态"三个维度，避免只证明单个 URL 已失效。

## 风险定级思路

- 高危。
  匿名或低权限即可获取包含生产敏感配置的工件，且内容足以直接暴露数据库、中间件、对象存储、后台服务或其他高价值资源的连接与认证要素。Git 仓库泄露且可还原含敏感配置的源码时，通常直接定为高危。

- 中危。
  工件可被非预期身份获取，内容暴露了内部拓扑、账号标识、环境关系或部分连接信息，但尚未证明可直接形成高信任访问能力。`.git/config` 仅暴露仓库基本信息但无法进一步还原时，或 SVN 只暴露 entries 文件但内容不含关键配置时，可考虑中危。

- 低危。
  工件虽可访问，但仅含非敏感配置、失效样本、占位值、脱敏片段或无现实利用意义的历史残留。

- 降级因素。
  文件当前已不可获取、值已轮换失效、仅影响隔离测试环境、内容明显为模板样本，或业务上本就要求对当前身份公开下载。Git 泄露但 `objects/` 不可访问且仅有少量元数据时可适当降级。

- 升级因素。
  备份包同时包含多类敏感文件、同类问题跨多个模块或版本复现、可匿名持续下载历史包、暴露值存在跨系统复用迹象，或配置内容能支撑更高影响的后续访问能力。Git 历史提交中存在已删除但仍生效的密钥、仓库 remote URL 中内嵌访问 token，均属升级因素。

## 修复与复测

- 修复原则。
  配置、环境和备份工件不应暴露在公开可达路径；敏感配置应迁出公开分发面，采用权限隔离和专用密钥管理机制。

- 发布治理。
  清理备份后缀文件、历史压缩包、编辑器临时副本、运维导出包、旧安装包和对象存储残留，关闭不必要的目录索引与目录映射。

- Git/SVN 专项修复。
  在 Web 服务器层面拦截对 `.git/`、`.svn/`、`CVS/` 目录及其内部文件的访问（Nginx 的 `location ~ /\.git` 拒绝规则或 Apache 的 `<Directory>` 限制）。仅删除物理目录不足以解决问题，应同时检查 CDN 缓存、对象存储映射和 CI/CD 发布流程是否会再次带入版本控制目录。已通过 git 历史提交过的敏感凭据必须轮换，无论当前代码是否已删除该提交内容（`git filter-branch` 或 BFG 清理仅解决历史问题，不能替代凭据轮换）。

- 凭据治理。
  对已暴露的账号、口令、连接串、证书材料和环境密钥执行轮换与失效处理，而不是只删除文件。

- 存储治理。
  将敏感配置移出 Web 根目录、公共下载目录、静态资源目录和弱权限共享路径，限制仅必要服务账号可读。

- 复测步骤。
  沿原始入口重新验证文件是否仍可获取，再按同类命名规则、同目录、同下载链路和历史版本分发点复核是否存在替代暴露点。Git/SVN 场景应验证核心探针路径（`.git/config`、`.git/HEAD`、`.svn/entries` 等）均返回 403 或 404，并确认 pack 文件和 objects 目录也无法访问。

- 复测重点。
  同时确认三件事：原工件不可再公开获取、同类残留未在其他位置复现、已暴露敏感值完成轮换且旧值不可继续使用。

- 复测完成标准。
  只有当"入口关闭""残留清理""凭据失效"三者同时满足，且业务功能通过新的受控方式正常运行，才应判定修复闭环完成。

## 报告表达模板

### 配置/备份文件泄露

- 标题。
  配置文件与备份文件泄露

- 漏洞概述。
  在测试过程中，发现 `<artifact-path>` 对 `<anonymous-or-low-priv>` 可访问，且工件中包含 `<sensitive-field-type>`（如数据库连接串、API 密钥、服务账号口令等）不应公开暴露的敏感配置或备份内容。

- 验证结论。
  通过对原始访问响应、文件结构和敏感字段的分析，可确认该工件并非普通公开资源，而是包含当前系统敏感配置或备份信息的实际可获取对象。敏感字段 `<field-name>` 对应的组件（`<component-name>`）在目标系统中仍在运行，字段内容具备现实可用性。

- 影响说明。
  该问题可能导致内部连接关系、认证材料、环境配置或历史发布内容泄露，为后续未授权访问、数据泄露或系统横向影响提供前提条件。

- 风险判断。
  风险等级取决于工件可访问范围、敏感字段完整度、字段生效性以及是否跨模块复用；如已暴露生产可用凭据或完整连接要素，应优先按高风险处理。

- 修复建议。
  建议下线公开暴露工件，清理同类残留，调整发布与备份策略，迁移敏感配置到受控存储，并对已暴露凭据执行统一轮换。

- 复测表述。
  复测应确认原始路径和同类分发链路均不可再获取相关工件，历史残留已清理，暴露值已失效，业务功能在新的受控配置机制下运行正常。

### Git/SVN 源码仓库泄露

- 标题。
  Git/SVN 版本控制目录泄露（含源码及配置文件）

- 漏洞概述。
  在测试过程中，发现目标 `<base-url>/.git/`（或 `.svn/`）目录对匿名用户可访问。通过访问仓库元数据文件（`.git/config`、`.git/HEAD`、`.git/COMMIT_EDITMSG` 等），确认版本控制目录处于公开暴露状态，且存在源码还原可能。

- 验证结论。
  利用 git-dumper（或 dvcs-ripper）在本地还原了部分/全部源码，于还原代码中发现 `<file-path>` 包含 `<sensitive-field-type>` 字段（如数据库连接字符串、第三方服务 API Key 等）。其中字段 `<field-name>: <raw-secret>` 必须填入捕获到的原始值；其关联服务组件（`<component>`）在目标系统中仍在运行，具备现实可利用性。此外，git 提交历史中发现 `<commit-hash-prefix>` 曾提交过 `<historical-sensitive-file>`，即使当前分支已删除，通过历史版本仍可获取。

- 影响说明。
  攻击者通过公开访问版本控制目录，可能获取完整业务逻辑源码、敏感配置文件、硬编码凭据和内部服务拓扑，显著降低后续攻击门槛，并可能直接导致数据库、内部 API 或第三方服务的未授权访问。

- 风险判断。
  当前判定为高危。理由：匿名可还原源码、源码中含完整数据库/服务连接要素、字段对应组件当前仍在运行。

- 修复建议。
  在 Web 服务器层面拒绝对 `.git/`、`.svn/` 目录的公开访问，检查发布流程是否会再次引入该目录，并对已暴露的凭据（包括历史提交中存在的）执行统一轮换。

- 复测表述。
  复测应确认 `.git/config`、`.git/HEAD`、`.git/objects/` 等核心路径均返回 403 或 404，git-dumper 无法成功还原代码，且所有已暴露凭据完成轮换。
