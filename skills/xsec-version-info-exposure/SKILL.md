# 版本信息泄露测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：响应头、默认页、错误页、接口文档、前端资源或页面页脚暴露 Web 服务器、框架、中间件、组件精确版本。
- 触发信号：`server_header_version_detected`、`x_powered_by_detected`、`framework_version_detected`、`default_page_detected`、`debug_page_detected`、`component_version_detected`。
- 测试前置环境：通常需要有目标系统返回的版本证据；排除浏览器插件、代理、测试工具和第三方资源噪声。
- 参考工件：`response_headers`、`scout_summary`、`passive_findings`、`screenshot`、`asset_inventory`。
- 解锁输出：`middleware_specific_review_needed`、`config_backup_candidate_detected`、`vulnerability_chain_input`。
- 建议阻断（可低影响补齐时先补证再测）：版本信息不精确、来自非目标域/测试代理、仅为公开无敏感性的通用标识。

## 适用场景

- 适用于发现目标在响应头、响应体、错误页、默认页、登录页、页脚、帮助页、静态资源标识中暴露产品或组件版本的场景。
- 适用于中间件、反向代理、应用框架、CMS、脚本运行时、组件库、管理后台、调试页等对外暴露版本指纹的场景。
- 适用于测试中需要判断“这只是普通资产指纹，还是足以支持报告风险”的场景。
- 适用于复测修复是否仅覆盖单一入口，而遗漏错误页、旁路路径、子应用或网关层头部的场景。
- 不适用于仅出现协议名称、测试工具水印、截图界面版本、第三方浏览器插件信息但无法证明属于目标系统的场景。

## 测试思想

- 这类问题的核心不是“看到了某个技术名词”，而是“目标是否向外部暴露了可被攻击者直接用于识别技术栈和版本代际的信息”。
- 优先区分三类暴露：
  - 精确版本暴露：直接出现 `产品名 + 主次版本号`，可明显缩小攻击者检索范围。
  - 栈信息暴露：错误页、调试页、返回头同时暴露中间件、框架、运行时、文件路径或模块名。
  - 弱指纹暴露：仅出现产品名、通用 Server 名称或模糊组件标识，支持资产识别但未必足以单独上调风险。
- 判断时不要只看一张截图。必须回答四个问题：
  - 版本信息来自哪里，是响应头、页面正文、错误页还是静态资源标识。
  - 信息是否稳定复现，还是偶发于调试状态、缓存页面或测试工具界面。
  - 信息是否足够具体，能否区分大版本、次版本、框架代际或运行环境。
  - 该暴露是否叠加了额外上下文，如堆栈、绝对路径、模块名、错误处理链路，从而显著提升利用参考价值。
- 采用对照组思路，而不是“看到版本号就报”。要把真正的目标暴露和截图噪声、代理工具版本、协议描述、前端文案区分开。

## 参考方法（目标与常见路径，不是必须顺序）

下面是达成测试目标的常见路径，不是必须照做的脚本：可以合并步骤、调整顺序、跳过已经确认过的部分，或者换成你判断更合适的方法，只要仍能支撑下面的判断点和证据要求。

1. 信息收集
- 先识别入口面：首页、登录页、帮助页、错误页、公开接口、静态资源目录、默认站点页、认证前后关键页面。
- 记录可能出现版本信息的位置：响应头、页脚版权、默认报错模板、调试页、框架异常页、接口 JSON 字段、资源文件名中的版本串。
- 在低影响前提下，优先使用正常访问、访问不存在路径、访问未登录入口、访问已登录入口四类最小化路径观察差异。

2. 建立基线
- 先看正常首页和登录页，记录是否存在 `Server`、`X-Powered-By`、`X-AspNet-Version`、`X-Generator` 等头部。
- 再看不存在路径或参数缺失时的错误处理页面，判断版本是否只在异常流程中出现。
- 如同一系统有网关、子应用、不同端口或不同路径前缀，分别建立基线，避免把某一层的头部误认为全站一致。

3. 最小化验证
- 对响应头类问题，只需证明外部请求可稳定获得版本或产品信息，不需要扩大为攻击验证。
- 对错误页类问题，只做低影响异常触发，例如访问不存在路径、访问缺少必要参数的公开页面、访问系统自带错误入口。
- 对页面正文类问题，只需证明页脚、调试页、欢迎页或组件界面中可直接看到版本，不需要继续深入业务操作。
- 若版本信息来自静态资源命名或页面注释，要确认它确实代表服务端或组件真实版本，而不是构建时间戳、前端缓存号或无意义占位串。

4. 构造对照组
- 对比正常页面与错误页面：判断版本是否只在异常路径暴露。
- 对比未登录与已登录：判断版本暴露是否出现在后台、管理页或登录后组件中。
- 对比多个路径或子应用：判断是网关统一注入，还是某个具体组件单独暴露。
- 对比目标内容与测试环境噪声：排除浏览器插件、抓包工具、截图软件、测试代理本身显示的版本号。
- 对比“仅技术名”与“精确版本号”：例如只出现中间件名称，与出现精确版本、运行时版本、框架版本，风险意义不同。

5. 影响面扩展
- 沿着同域名、同网关、同站群、同组件模板查找是否存在同类头部或同一错误模板。
- 检查是否同时泄露多层信息，例如反向代理版本、应用框架版本、运行时版本、调试调用栈。
- 若暴露信息与公开补丁公告、停服版本或历史高危组件代际明显重合，可在评估中上调风险，但仍应以“版本暴露本身”为当前验证边界。

6. 留证
- 固定完整原始请求与响应，记录完整敏感 Cookie、完整 Token 和真实业务数据；仅在 body 体积受限时截断并注明。
- 原始敏感内容保存到受控证据目录；共享发现、截图展示、报告和委派使用最少必要的原始摘录（xSec 不做自动脱敏）与证据引用，截断只因体积限制并明确标记。
- 对页脚或正文类证据，保留“页面位置 + 版本文本 + 页面角色”的组合，证明其面向外部用户可见。

7. 修复复测
- 修复后按照原路径逐项验证：首页、登录页、错误页、公开接口、后台入口、子应用入口都要复测。
- 除验证版本号消失外，还要验证是否退化为新的弱暴露形式，例如虽然删掉精确版本，但仍保留调试页、调用栈或框架标识。

## 关键判断点

- 仅出现通用技术名词，不足以当然认定为高风险；真正需要关注的是精确版本、代际信息和可关联的栈细节。
- `Server: nginx` 与 `Server: nginx/1.18.0` 的意义不同；前者偏资产指纹，后者已经形成更明确的攻击检索线索。
- `X-Powered-By`、`X-AspNet-Version`、框架异常页、默认欢迎页、组件页脚版本通常比单纯页眉文案更有证据价值。
- 若错误页同时暴露调用栈、模块名、框架类名、目录结构、调试页面风格，应判断为“版本暴露 + 栈信息暴露”的组合问题。
- 若页面仅出现“HTTPS”“安全版”“系统版本”但没有具体产品和版本语义，不能直接归入本类漏洞。
- 若截图中出现的是测试工具版本、浏览器版本、代理工具标题栏或 OCR 误识别文本，应判为噪声，不应计入目标漏洞。
- 若版本信息只在认证后管理界面可见，仍可能成立，但报告中要说明其访问前提和暴露边界。
- 若多个入口暴露同一组件版本，说明修复应在网关、模板或统一错误处理层完成，而不是只改单页文案。

## 证据链要求

- 证据至少覆盖四个要素：访问入口、暴露位置、版本内容、外部可见性。
- 对响应头类问题，保留原始请求路径、响应状态和完整头字段，证明无需特殊条件即可获取。
- 对错误页类问题，保留触发条件和最小响应片段，证明是低影响路径即可稳定暴露，而非一次性偶发故障。
- 对正文或页脚类问题，保留页面定位信息，证明普通访问者可直接看到版本文本。
- 对组合型暴露，保留“版本信息 + 栈信息/路径信息/模块信息”的并列证据，支撑风险上调。
- 对复测证据，保留修复前后对照，证明精确版本、调试页、栈细节是否均已消失。
- 原始敏感内容保存到受控证据目录；共享发现、截图展示、报告和委派使用最少必要的原始摘录（xSec 不做自动脱敏）与证据引用，截断只因体积限制并明确标记。

## 风险定级思路

- 低危
  - 仅暴露单一中间件、框架或组件的版本信息，未见调试栈、路径、源码片段或额外敏感上下文。
  - 仅能支持资产识别和攻击面收敛，尚不能证明存在直接利用链。
- 中危
  - 暴露精确版本且同时暴露运行时、框架代际、模块名、错误栈、绝对路径中的一项或多项。
  - 暴露信息位于互联网可访问入口，并明显降低攻击者识别技术栈与筛选利用方案的成本。
  - 暴露版本已显示为明显过旧、停服代际或与公开安全公告高度相关，但当前测试仍保持在最小化验证边界。
- 降级条件
  - 只能确认通用产品名，无法确认版本。
  - 信息来自测试工具水印、截图噪声、非目标界面或 OCR 误识别。
  - 仅有协议字样或营销文案，无法证明属于服务端、框架或组件版本。
- 升级条件
  - 多层版本同时泄露，例如网关、中间件、框架、运行时一起出现。
  - 版本暴露与错误栈、绝对路径、模块名、调试页并存。
  - 同类暴露覆盖多个入口、多个子系统或认证前后多个面。

## 修复与复测

- 修复方向
  - 在网关、反向代理、应用服务器和框架层统一移除或改写对外版本头。
  - 关闭调试模式、默认错误页、框架异常页和开发态欢迎页，改为自定义通用错误响应。
  - 移除页脚、帮助页、登录页、默认模板、公开资源中的精确版本文案。
  - 对必须保留的产品标识，仅保留最小必要品牌信息，不暴露精确版本、代际、构建号、运行时信息。
- 复测步骤
  - 按原测试矩阵复测：首页、登录页、错误页、公开接口、认证后页面、子应用入口分别检查。
  - 复测响应头和响应体两个维度，避免只删头部未删正文，或只删正文未删错误页。
  - 复测不同状态码路径，尤其是 `200`、`404`、`500` 对应模板是否仍带版本指纹。
  - 复测多层代理场景，确认前端网关和后端应用都没有重新注入版本字段。

## 报告表达模板

- 漏洞标题
  - 版本信息泄露
- 漏洞描述
  - 在测试过程中，发现目标系统可向外部访问者暴露 `<component-type>` 的版本信息。该信息出现在 `<exposure-location>`，可通过 `<minimal-trigger>` 稳定获取。暴露内容包含 `<product-or-stack-info>`，可被用于识别技术栈、缩小攻击检索范围并辅助后续针对性分析。
- 风险说明
  - 版本信息本身通常不直接构成利用，但会显著降低攻击者识别中间件、框架、组件代际及补丁状态的成本。若同时伴随 `<extra-context>`，则攻击者可更高效地构造针对性攻击路径，整体风险进一步上升。
- 证据概述
  - 1. 访问 `<entry-point>` 时，响应 `<header-or-body>` 中出现 `<product-or-stack-info>`。
  - 2. 在 `<control-group>` 下复现结果一致，证明该信息来自目标系统而非测试环境噪声。
  - 3. 若访问异常路径或错误页面，还可见 `<extra-context>`，说明暴露不止于单一版本字段。
- 修复建议
  - 建议在网关、应用服务器和框架层统一隐藏或剥离对外版本信息，关闭调试和默认错误模板，并复核所有公开入口、异常路径和子应用页面，确保不再向未授权访问者暴露精确版本及相关栈细节。
