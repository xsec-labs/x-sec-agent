# 客户端硬编码敏感信息测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：前端 JS、source map、小程序/移动端包、配置文件或构建产物中出现硬编码凭据、密钥、内部地址、调试开关或源码泄露。
- 触发信号：`source_map_detected`、`js_secret_candidate_detected`、`frontend_route_inventory_detected`、`client_config_detected`、`mobile_package_available`、`passive_secret_match`。
- 测试前置环境：通常需要能访问或获得分析的客户端资源；source map/包体还原应在本地隔离目录中进行。
- 参考工件：`route_map`、`js_asset_list`、`source_map_files`、`passive_findings`、`client_package_path`。
- 解锁输出：`cloud_secret_candidate_detected`、`internal_network_leakage_candidate`、`api_base_path_detected`、`admin_route_detected`、`insecure_crypto_candidate`。
- 建议阻断（可低影响补齐时先补证再测）：无可访问客户端资源、仅有公开公钥或无效占位值且无法证明可用。

## 适用场景

- 目标为浏览器前端、移动端应用、桌面客户端、小程序包、Hybrid 容器或公开可下载的静态资源。
- 已发现可疑信息出现在 `JS bundle`、`source map`、配置文件、反编译代码、资源文件、调试日志、离线包或安装包中。
- 需要判断暴露内容究竟是公开配置、低价值残留，还是足以影响认证、机密性、完整性的真实敏感信息。
- 需要证明“客户端不应持有的秘密”是否已经转化为可利用能力。
- 该方法论不用于纯服务端密钥管理审计；仅当问题起点位于客户端可获取材料时适用。- 适用于通过 `source map`、未压缩构建产物、历史静态资源、公开安装包可恢复源码的场景，即使尚未发现明确硬编码凭据，仍需评估接口路由、业务逻辑、内部架构的暴露程度。
- 需要区分"仅普通前端资源可读"与"已泄露足以支撑风险结论的源码或敏感配置"之间的差异。
## 测试思想

- 把客户端视为不可信分发面。凡是发到终端的内容，原则上都应视为最终可被读取、复制和长期保存。
- 先判断“是不是秘密”，再判断“泄露后能做什么”。不是所有硬编码字符串都构成漏洞，关键在于它是否承担认证、签名、加解密、内部寻址或高信任调用职责。
- 把“前端可见”与“前端可用”分开分析。公开接口地址、公开应用标识、第三方 SDK 公钥类参数，可能只是配置；账号凭据、对称密钥、长期 Token、内部控制端点、隐藏调试开关则明显不同。
- 把“存在值”与“实际生效”分开分析。死代码、历史构建残留、测试环境遗留、已轮换失效值，风险通常低于当前生产链路中的活跃凭据。
- 验证时坚持最小化原则：仅证明该值确实参与了某个受保护动作，且优先使用测试账号、自有数据、只读接口或无副作用流程完成佐证。- 把"前端构建产物可访问"与"构建边界失守"区分开。普通压缩 `js` 公开可下载通常是正常现象；若同路径存在 `.map`、源码模块、可读配置常量或反编译后出现敏感信息，才进入漏洞判定。
- 分两阶段评估：第一阶段判断"源码/配置是否可恢复"（决定信息泄露风险），第二阶段判断"可恢复内容中是否存在硬编码秘密"（决定是否升级为高危）。
## 参考方法（目标与常见路径，不是必须顺序）

下面是达成测试目标的常见路径，不是必须照做的脚本：可以合并步骤、调整顺序、跳过已经确认过的部分，或者换成你判断更合适的方法，只要仍能支撑下面的判断点和证据要求。

1. 明确入口与样本范围。
   记录目标类型、版本号、构建时间、资源入口、包名或页面路径，固定本次审计对应的客户端样本，避免后续证据无法对齐。

1.5. 发现 source map 与构建产物入口。（前端场景适用）
   从页面加载的静态资源、浏览器开发者工具、页面底部注释、`sourceMappingURL` 指向、构建目录命名规律、公开下载页等位置寻找候选入口。记录主页面、哈希命名的 `js/css`、同名 `.map`、静态资源清单、历史版本资源、CDN 或对象存储路径，标注是否匿名可达。尝试恢复 source map 并确认是否可映射回源码目录结构；仅能访问普通压缩产物时，继续判断内容中是否包含可读常量、接口定义或调试注释。

2. 枚举客户端可读材料。
   优先查看公开静态资源、配置文件、打包产物、source map、调试脚本、反编译结果、缓存文件、日志输出和第三方 SDK 初始化代码。

3. 识别候选敏感信息。
   重点关注账号凭据、对称密钥、签名盐值、长期 Token、内部接口地址、WebSocket 服务配置、上传下载端点、环境切换参数、调试开关和权限标识。

4. 建立语义分类。
   将候选值按“公开标识”“敏感但未证实生效”“已证实参与安全控制”三类整理，避免一开始就把所有字符串定性为漏洞。

5. 回溯调用链。
   从变量定义追到使用点，确认其是否进入登录流程、签名函数、加解密函数、消息通道、内部 API 请求或权限判断逻辑。

6. 构造对照组。
   至少准备一组正常流程和一组去除该值或替换为占位值后的对照，观察请求、响应、解密结果、连接状态或功能表现是否出现稳定差异。

7. 进行最小化验证。
   验证以下任一事实即可：客户端可本地还原敏感数据、客户端可独立生成受信任请求材料、客户端持有的配置可触达本不应公开的高信任通道。

8. 评估影响面。
   判断该值是否跨环境、跨系统、跨端复用，是否存在历史构建残留、缓存可回收包、旧版安装包、CDN 历史资源、镜像站点或第三方分发渠道继续暴露。

9. 固化证据。
   同时保留代码位置、原始代码片段、调用链、对照结果、时间点、客户端版本和认证上下文，确保结论能被独立复核并继续利用。

10. 准备复测清单。
   在提交修复建议前，先列出所有应回归的位置：同类资源、同一密钥的复用点、历史包、旧链接、缓存节点、移动端旧版本和关联 WebSocket/上传通道。

## 关键判断点

- 仅存在公开 `js` 包，不等于漏洞。若内容仍是常规压缩产物、无法恢复源码、无敏感配置泄露，应谨慎定性；存在 `source map`、源码目录结构、完整接口封装或可读注释时，才说明"实现细节恢复"已成立。

- 源码恢复 ≠ 自动高危。若仅暴露接口路径但无认证绕过、无密钥材料，通常为中风险信息泄露；若暴露环境变量、内部域名、第三方平台配置或硬编码凭据，才考虑升级风险等级。

- 字符串是否承担安全职责。
  若值仅用于前端展示、公开路由、非敏感埋点，通常不构成此漏洞；若值承担认证、签名、解密、内部寻址、消息通道鉴权，则应重点关注。

- 客户端是否本不应拥有该能力。
  对称密钥、长期凭据、共享签名因子、后台账号、内部管理地址通常不应下发到客户端；公钥、公开租户标识、纯展示配置则要谨慎定性。

- 该值是否在当前版本真实生效。
  需要确认它不是死代码、历史注释、测试分支或已下线模块中的残留。

- 验证结果是否可重复。
  单次偶发现象、仅凭 OCR 文本、无法复现的截图，不足以支撑高置信度结论。

- 是否存在安全边界突破。
  真正高风险通常体现在可解密原本受保护的数据、可生成被服务端接受的受保护请求、可连接高信任消息通道、或可暴露内部网络结构与后续敏感能力。

- 是否只是“前端加密”表象问题。
  若客户端同时持有密钥和算法，所谓“传输前加密”往往不能提供真正的机密性，应重点分析其是否只是把明文换了一种可逆包装。

- 是否存在合理对照组。
  没有对照组时，容易把公开配置误判成漏洞，也容易把已失效值误判成活跃风险。

- 判断误报时需排除。
  占位样例、已失效测试值、构建工具默认注入但无业务意义的常量，以及无法关联到真实系统的无效残留信息，均不应定性为漏洞。

## 证据链要求

- 记录客户端样本标识。
  包括版本号、构建时间、资源路径、文件哈希或页面入口，证明结论对应的是哪一份客户端材料。

- 保留完整原始代码证据。
  截图或摘录保留原始 secret、内部端点、测试账号及必要上下文，不使用占位符替换真实值。

- 说明调用关系。
  明确“定义位置 -> 使用函数 -> 请求或解密逻辑 -> 结果差异”的链条，而不是只给一个字符串截图。

- 保留最小化验证结果。
  例如同一测试数据在“正常值”和“替换值”下的响应差异、连接成败差异、解密成败差异，且不涉及越权扩展。

- 绑定认证上下文。
  写清使用的是匿名态、低权限测试账号还是指定测试租户，避免结论被误解为更高范围的失陷。

- 记录影响面判断依据。
  包括是否多端复用、是否跨环境复用、是否存在旧包残留、是否可从公开资源重复获取。

- 保留复测前后对比。
  修复后要证明旧值失效、旧资源下线或不可访问、客户端不再持有秘密、相关功能仍可通过服务端受控机制正常运行。

## 风险定级思路

- 高危。
  暴露内容可直接支持认证、签名、解密、消息通道访问或高信任接口调用，且能在最小化验证中稳定证明其有效；或同一秘密跨多个系统、端或环境复用；或泄露硬编码密钥、访问令牌、第三方平台配置、内部网络地址、完整鉴权流程，足以明显降低后续攻击门槛。

- 中危。
  暴露内容具有明显敏感属性，但利用仍依赖额外条件；或只能证明局部数据解密、有限范围配置滥用、内部结构泄露，尚未证明更深层安全边界突破。**亦适用于：可恢复部分源码、路由、组件、接口封装或业务结构，能够帮助攻击者理解系统实现，但尚未出现直接可用的敏感凭据或高价值内部配置。**

- 低危。
  暴露的是过期值、测试残留、未生效死代码、公开标识符、单纯接口地址，或虽为密钥样式字符串但无法证明其参与当前安全控制。仅能看到常规压缩前端包、没有源码恢复能力、没有敏感配置时，通常更适合作为观察项或不报。

- 降级因素。
  值已轮换失效、仅存在于历史包且不可再分发、仅影响测试环境、无法形成稳定可重复验证、服务端已有额外强校验且客户端值不决定最终授权。

- 升级因素。
  可直接触达生产敏感通道、可还原真实业务数据、可跨租户或跨角色复用、可在多个客户端复现、修复后历史资源仍持续暴露。

## 修复与复测

- 修复原则。
  不在客户端保存长期秘密；将签名、加解密、凭据校验和高信任路由选择放回服务端；客户端仅持有短时、最小权限、可吊销的临时凭证。

- 密钥治理。
  对已暴露秘密执行轮换、失效和追踪，检查是否被多系统复用；如有复用，应拆分作用域并重新发放；即使文件已下线，若密钥未轮换，风险仍未真正消除。

- 构建侧修复。
  关闭生产环境 source map 对外发布，区分内部调试映射与对外资源，避免把源码映射、未压缩调试包或测试构建产物带入正式环境；将敏感字符串扫描、产物审查和发布前清单校验纳入 CI/CD 或发版门禁。

- 发布侧修复。
  清理公开目录、CDN、对象存储、历史版本目录和缓存节点中的遗留资源，避免"当前版本已修复，旧版本仍可下载"。

- 信息治理修复。
  将密钥、Token、默认凭据、内部地址、第三方平台敏感配置迁移到服务端或受控配置中心，并对已泄露材料执行轮换。

- 设计治理。
  若客户端曾持有对称密钥，应重新评估该加密方案是否本质上无效，必要时改为服务端处理或采用不会向客户端暴露秘密的机制。

- 客户端加固。
  对安装包启用合理的混淆与加固，但要明确这只是延缓逆向成本，不能替代服务端鉴权、签名校验和敏感配置下沉。

- 复测步骤。
  重新获取最新客户端样本，按原入口重新搜索候选值；验证旧值是否彻底失效；验证旧资源和旧包是否下线；验证相关接口、消息通道、上传下载链路是否已改为服务端受控。前端场景还需复测页面引用的资源、同名 `.map`、历史哈希文件、静态资源清单、CDN 副本与缓存响应，确认入口和旁路都已关闭。若问题来自移动端反编译，还要复测新包是否仍可恢复相同常量，并确认旧包是否仍可继续公开获取。

- 复测结论标准。
  只有当“客户端不再持有该秘密”且“旧秘密失效”且“关联资源不再暴露”同时满足时，才应判定修复完成。

## 报告表达模板

- 标题。
  客户端硬编码敏感信息

- 漏洞概述。
  在客户端可获取材料中发现硬编码的 `<敏感信息类型>`。该信息参与 `<认证/签名/加解密/高信任通道>` 相关逻辑，说明客户端持有了本不应下发到终端的安全控制要素。

- 验证结论。
  测试过程中，基于 `<客户端样本类型>` 中的原始配置与调用链分析，结合 `<最小化验证方式>`，可稳定证明该值处于生效状态，并对 `<数据机密性/接口可信性/消息通道安全性>` 产生影响。

- 影响面说明。
  当前影响覆盖 `<端类型/环境范围/功能模块>`；如该值被复用，还需同步排查 `<关联客户端或系统>`。

- 风险判断。
  该问题的核心不在于“字符串可见”，而在于“客户端持有了真实安全能力”。依据其是否可直接形成有效鉴权、签名或解密能力，综合评定为 `<风险等级>`。

- 修复建议。
  将相关秘密迁移至服务端或专用密钥管理体系，轮换已暴露值，移除历史资源残留，并对同类客户端与旧版本分发链路开展统一复测。

- 复测表述。
  复测时应确认最新客户端中已无法获取相同秘密，旧值已失效，相关旧包或历史静态资源不可再公开获取，且业务功能通过新的受控机制正常运行。

### 前端源码与构建产物泄露（子场景报告模板）

- 漏洞名称：前端源码与构建产物泄露
- 漏洞位置：`<page-or-app>`
- 访问条件：`<anonymous-or-low-priv>`
- 问题概述：测试发现目标对外暴露了可恢复前端源码或可读构建产物，攻击者可据此识别系统实现细节、接口结构或敏感配置，从而降低后续攻击成本。
- 验证结论：通过访问公开静态资源或公开分发的客户端安装包，确认可恢复 `<source-map-or-decompiled-source>`，并识别出 `<routes-or-api-definitions-or-config-categories>` 等信息。
- 影响说明：当前泄露内容可用于辅助枚举接口、分析鉴权逻辑、识别内部依赖关系或定位敏感配置类别。若其中材料仍然有效，可能进一步放大业务暴露面。
- 风险等级：`<medium-or-high>`。定级依据应写明"是否存在源码恢复能力""是否包含敏感常量或凭据""访问门槛"和"影响范围"。
- 修复建议：停止对外暴露调试映射和历史构建产物，清理缓存与旧版本资源，将敏感配置迁移出客户端，并对已泄露的密钥或令牌立即轮换。
- 复测建议：修复后重新检查页面引用链、同名映射文件、历史资源、公开下载入口和缓存节点，确认文件不可访问、源码不可恢复且敏感材料已完成轮换。
