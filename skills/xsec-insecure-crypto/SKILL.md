# 不安全加密方式测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：发现 Base64/Hex/URL 编码冒充加密、弱算法、固定密钥/IV、前端可逆加密、客户端签名密钥或敏感数据弱保护。
- 触发信号：`encoded_sensitive_value_detected`、`client_crypto_code_detected`、`hardcoded_crypto_key_detected`、`weak_algorithm_detected`、`fixed_iv_detected`、`jwt_weak_algorithm_detected`。
- 测试前置环境：通常需要有可观察的密文/编码值和生成位置；若验证可逆性，应使用测试样本或测试账号数据。
- 参考工件：`client_assets`、`storage_snapshot`、`request_corpus`、`crypto_sample_pairs`、`passive_findings`。
- 解锁输出：`password_storage_candidate`、`jwt_security_candidate`、`client_hardcoded_secret_candidate`、`token_replay_candidate`。
- 建议阻断（可低影响补齐时先补证再测）：无可分析加密材料、只有公开哈希/公钥、缺少样本对照或解密会触碰真实敏感数据。

## 适用场景

- 适用于登录、注册、找回密码、单点登录、个人资料、移动端接口、前端缓存、Cookie、本地存储、配置文件或客户端包中出现“加密保护”声明的场景。
- 适用于发现可疑字段经过 Base64、Hex、URL 编码、前端 JS 加工、固定算法封装或客户端可见密钥处理后再传输或存储的场景。
- 适用于需要判断“这是安全加密，还是仅做了编码、混淆、可逆封装、弱算法保护”的场景。
- 适用于需要评估密钥管理是否失当的场景，包括硬编码密钥、固定 IV、客户端内置密钥、跨环境复用密钥、缺少轮换或加密签名职责混用。
- 所有步骤仅限低影响、最小化验证。优先使用测试账号和伪造业务数据；证据中的原始样本保留原文，但不对真实用户数据做扩展性解密或批量验证。

## 测试思想

- 核心不是看“数据是否发生变换”，而是判断该变换是否真正提供了保密性、完整性和可控的密钥管理。
- 先区分编码、混淆、加密、签名四类能力，再判断它们是否被错误地当成“加密”使用。
- 先证明“可逆、可预测、密钥暴露或算法过弱”，再证明“承载的数据具有敏感性或业务控制意义”，这样结论更稳。
- 优先构造对照组而不是直接下结论。例如同一字段不同取值、同一账号不同时间、不同账号相同流程，观察输出是否可逆、是否稳定、是否受客户端控制。
- 最小化验证优先于影响扩展。先用单字段、单账号、单流程完成闭环，再判断是否值得扩大到多入口、多终端、多角色。
- 不把“看到密文”当成安全，也不把“看到可读数据”直接当成高危。风险等级取决于数据敏感性、控制边界、密钥暴露程度和业务后果。

## 参考方法（目标与常见路径，不是必须顺序）

下面是达成测试目标的常见路径，不是必须照做的脚本：可以合并步骤、调整顺序、跳过已经确认过的部分，或者换成你判断更合适的方法，只要仍能支撑下面的判断点和证据要求。

### 1. 信息收集

- 标出所有涉及“保护敏感数据”的入口：`<login>`、`<reset-password>`、`<profile>`、`<api>`、`<cookie>`、`<local-storage>`、`<mobile-client>`。
- 记录字段类型：账号标识、手机号类标识、邮箱类标识、角色信息、令牌、会话标识、密码材料、业务敏感字段。
- 观察前端或客户端线索：`atob/btoa`、`CryptoJS`、`encrypt`、`decrypt`、`secretKey`、`iv`、`ECB`、`CBC`、`MD5`、`SHA1`、`DES`、`3DES`、`RSA` 等字样。
- 观察存储与传输位置：请求体、响应体、Cookie、URL 参数、隐藏字段、缓存、JS 配置、应用包资源、日志回显。
- 初步判断该字段承担的是保密、签名、防篡改还是仅做格式封装，避免一开始把所有变换都归为“加密”问题。

### 2. 构造对照组

- 使用同一测试账号，保持其他参数不变，只修改一个低敏字段，比较变换后输出是否随原文同步变化。
- 使用两个测试账号走同一流程，观察编码结果中是否直接暴露账号属性、角色属性或个人信息片段。
- 对同一输入重复触发，观察输出是否恒定不变；若完全稳定，继续判断是否存在固定密钥、固定 IV、无随机因子等问题。
- 若前端声称“已加密”，比较浏览器内原始值、发包值和服务端返回值，判断保护是否仅存在于客户端表面流程。
- 若怀疑密钥管理不当，优先验证“密钥是否出现在客户端或静态资源中”，不要直接做面向真实资产的扩大利用。

### 3. 最小化验证

- 对疑似 Base64、Hex、URL 编码、简单拼接或固定格式封装的数据，在离线环境做可逆性判断，确认其是否能还原出测试账号自己的字段内容。
- 对疑似弱算法或不安全模式，仅验证算法名称、模式、填充方式、密钥位置、IV 生成方式是否满足“客户端可见、固定、可预测、复用”这些低影响证据。
- 对前端伪加密，验证“浏览器拿到的代码和密钥是否足以完成同样变换”，证明其并未形成真正的服务端保密边界。
- 对 Cookie 或本地存储问题，验证是否存放了本不该由客户端长期持有的敏感数据，而不是只看到一段不可立即识别的字符串就停止。
- 若字段可逆但仅为无敏感性的界面偏好或展示参数，应保留为弱信号，不直接上升为漏洞。

### 4. 影响面扩展

- 在完成最小化闭环后，检查相同方案是否复用于 Web、移动端、小程序、桌面端或网关层。
- 检查是否在多个业务流程中复用同一密钥、同一算法包装器、同一 Cookie 结构或同一前端加密组件。
- 检查问题是否只影响展示性字段，还是已经覆盖身份、令牌、角色、隐私数据、交易数据或审批数据。
- 检查修复边界是否会遗漏旁路入口，例如主站已改但 H5、历史页面、旧接口或静态资源仍保留旧逻辑。

### 5. 留证

- 保留完整原始请求、响应、存储截图、关键字段对照和真实敏感值。
- 保留“原始值特征 -> 变换值特征 -> 可逆或弱保护判断依据 -> 影响字段类型”的闭环笔记。
- 保留测试时间、测试账号角色、入口位置、使用的最小化样本和每一步判断依据，确保报告可复核。

### 6. 修复复测

- 复测时沿用同一对照组，确认不是“页面显示变了”，而是底层存储、传输、密钥管理和服务端控制点都已改变。
- 复测范围至少覆盖原发现入口、同组件复用入口和一个旁路入口，避免只修单点。

## 关键判断点

- `Base64`、`Hex`、`URL 编码`、字符串替换、拼接混淆都不提供保密性，不能视为加密。
- “前端先加密再提交”只有在密钥和控制逻辑不暴露于客户端时才有讨论价值；若客户端可见密钥与算法，则通常不能作为安全边界。
- 可逆加密不等于一定有漏洞，关键在于其是否承载敏感信息、是否让客户端不应获得的数据长期暴露、是否依赖不可信客户端自行保护。
- 仅发现弱算法名还不够，要结合实际承载数据、密钥管理、攻击面和可替代性判断风险，避免把纯技术债一律报成高危。
- 固定密钥、固定 IV、跨租户或跨环境共用密钥、把密钥放在前端包或客户端配置中，通常比“算法名不好看”更值得优先报告。
- 签名与加密要分开判断。签名只能证明完整性或来源，不能证明保密性；把可读载荷误当成“已加密”是常见设计错误。
- Cookie 或本地存储中若保存账号资料、角色资料、联系方式、令牌或其他高敏字段，即便做了可逆处理，也应重点关注长期暴露和复制风险。
- 如果系统仅保存最小必要、无敏感性的展示字段，且不参与认证授权决策，则更可能是低危配置问题，而非实质性数据泄露。

## 证据链要求

- 入口证据：记录问题出现在哪个页面、接口、客户端或存储位置，使用什么测试角色触发。
- 数据证据：记录字段名称、字段用途、完整原始样本值和该字段为何属于敏感数据或安全相关数据。
- 判断证据：记录为何认定其属于编码、可逆加密、弱算法、前端伪加密或密钥管理不当，避免只给结论不给依据。
- 对照证据：至少保留一组输入变化与输出变化的对照，证明该方案可逆、可预测、固定或由客户端完全掌控。
- 范围证据：记录相同方案是否出现在多个入口、多个终端或多个角色流程中，支撑影响面判断。
- 复测证据：记录修复后同样入口的变化，包括字段不再落地、客户端不再持有密钥、算法与模式升级、服务端控制点生效等。
- 原始敏感内容保存到受控证据目录；共享发现、截图展示、报告和委派使用最少必要的原始摘录（xSec 不做自动脱敏）与证据引用，截断只因体积限制并明确标记。

## 风险定级思路

- 低危：仅涉及无敏感性的展示字段或普通配置字段，问题主要体现为“把编码当加密”或“保护方式不规范”，但不直接影响认证、授权、隐私或关键业务数据。
- 中危：可逆保护覆盖了个人资料、账号属性、联系方式、内部标识等敏感信息，或客户端可见固定密钥导致同类数据保护边界明显不足。
- 高危：可逆或弱保护覆盖令牌、会话材料、密码相关数据、核心隐私数据，或密钥暴露足以支撑批量数据解读、伪造或跨入口复用风险。
- 严重：密钥管理失当已经影响系统级信任边界，例如统一签名密钥或统一解密密钥暴露，可能导致多系统、多租户或多业务链路同时失守。
- 定级时同时看四个维度：数据敏感性、客户端可控程度、密钥暴露程度、业务后果。不要只按“算法是否过时”单维度定级。

## 修复与复测

- 修复优先级一：删除不必要的客户端敏感数据存储，不把账号资料、令牌、隐私字段放入 Cookie、本地存储或其他易复制位置。
- 修复优先级二：不要用编码、混淆或前端伪加密替代真正的服务端安全控制；需要保密时应由服务端结合合规算法与密钥管理完成。
- 修复优先级三：淘汰弱算法、不安全模式、固定 IV 和硬编码密钥；区分加密与签名职责，避免共用同一密钥材料。
- 修复优先级四：建立密钥生命周期管理，包括生成、分发、权限隔离、轮换、吊销和环境隔离，避免测试、生产、不同业务共用。
- 复测时检查三类结果：数据是否不再可逆暴露、客户端是否不再持有关键密钥、旁路入口是否同步修复。
- 若修复方式只是“改了字段名”或“换了一层新编码”，应判定为未修复完成。

## 报告表达模板

- 漏洞名称：不安全加密方式
- 发现位置：`<页面/接口/客户端模块/存储位置>`
- 验证前提：在测试过程中，使用 `<test-account>` 与捕获到的原始样本完成最小化验证。
- 问题概述：目标系统将 `<sensitive-field-type>` 通过 `<encoding-or-crypto-scheme>` 处理后存储或传输，但该方案存在 `<reversible-or-weak-reason>`，未形成有效保密边界。
- 判断依据：
- 相关字段在 `<location>` 中可见，且承载 `<data-type>`。
- 通过对照组可确认该值与测试样本存在稳定对应关系，属于 `<encoding / reversible encryption / weak crypto / client-side pseudo encryption / poor key management>`。
- 客户端可见 `<algorithm-or-key-management-issue>`，说明保护依赖不可信客户端或密钥管理失当。
- 影响分析：
- 该问题可能导致 `<impact-scope>` 被低成本读取、复制、长期保留或在多个入口复用。
- 若同类方案复用于其他终端或组件，影响面可能扩大到 `<multi-entry-scope>`。
- 修复建议：
- 移除不必要的客户端敏感数据存储。
- 使用服务端受控、合规且具备密钥生命周期管理的保护方案。
- 对复用组件、历史接口和多终端入口做同步整改。
- 复测结论：修复后应确认 `<field>` 不再以可逆或弱保护方式暴露，客户端不再持有关键密钥，同类入口复测结果一致。
