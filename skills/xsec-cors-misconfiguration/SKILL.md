# CORS跨域配置缺陷测试方法论

## 编排适配

- 适用场景：API 响应出现 Origin 反射、宽松 ACAO、ACAC=true 或疑似跨站可读敏感接口。
- 触发信号：`cors_header_observed`、`origin_reflection_detected`、`acao_wildcard_detected`、`acac_true_detected`、`sensitive_api_fields_detected`。
- 测试前置环境：必须有可重放 API 请求；若验证跨站读取，需要受控测试 Origin/页面和必要登录态。
- 必需工件：`request_corpus`、`response_headers`、`api_inventory`、`browser_state`、`controlled_origin_result`。
- 解锁输出：`cross_origin_read_candidate`、`csrf_review_needed`、`sensitive_data_exposure_candidate`。
- 阻断条件：无 CORS 头、仅公共资源跨域、没有可读敏感响应或无法建立受控跨站对照。

## 适用场景

- 目标系统返回 `Access-Control-Allow-Origin`、`Access-Control-Allow-Credentials`、`Vary: Origin` 等头部，怀疑存在跨域策略过宽或动态回显。
- 前端、网关、认证中心、移动端接口、H5 页面、统一入口 API、文件下载或配置接口存在跨域访问需求，需要判断是否被错误放开。
- 需要在授权测试中验证“跨域是否真的能读到敏感响应”，而不是只停留在头部异常层面。
- 需要对 CORS 问题做风险定级、修复建议、复测闭环，避免把所有跨域异常一律报成中高危。

## 测试思想

- 先判断这是“浏览器同源策略放宽”问题，不要把服务端普通鉴权失败、SSRF、CSRF 或开放接口误归为 CORS。
- 先看入口，再看可读性。真正有价值的判断不在于响应里是否出现某个 CORS 头，而在于浏览器在授权态下是否允许跨站页面读取目标响应。
- 采用对照组思路：同一接口分别在无 `Origin`、伪造 `Origin`、不同认证态、不同接口类型下比较响应头和响应体差异。
- 坚持最小化验证。优先选择低影响、只读、可证明含敏感字段的接口，不对真实业务做状态变更，不扩大到破坏性操作。
- 风险判断分层进行：
  1. 仅存在 CORS 放行头。
  2. 携带凭证的跨域被允许。
  3. 携带凭证后可读取敏感数据或关键业务响应。
  4. 可稳定覆盖多个敏感接口或多个业务域。

## 操作流程

1. 识别入口。
   - 从浏览器开发者工具、接口文档、前端代码、网关响应、移动端抓包中找出出现 `Origin` 相关头部的接口。
   - 优先关注个人信息、账号资料、消息通知、配置读取、业务列表、详情查询、文件元数据、令牌相关接口。
   - 记录接口所属域、是否登录后访问、是否经过网关、是否存在多子域共享。

2. 建立基线。
   - 使用正常请求确认接口在当前授权测试账号下可访问，并保存原始响应头、响应体摘要、状态码、时间点。
   - 区分匿名接口与登录接口，区分纯公开内容与带身份上下文的内容。
   - 若接口本身返回公开配置或静态资源，不要直接作为高风险结论依据。

3. 构造跨域对照组。
   - 对同一接口分别发送不带 `Origin`、带 `<test-origin-a>`、带 `<test-origin-b>` 的低影响请求。
   - 观察 `Access-Control-Allow-Origin` 是否固定白名单、是否动态回显、是否对任意来源放行、是否只在部分路径上生效。
   - 补充观察 `Access-Control-Allow-Credentials`、`Access-Control-Allow-Headers`、`Access-Control-Allow-Methods`、`Vary: Origin` 是否联动变化。

4. 验证凭证参与情况。
   - 在授权且低影响的前提下，分别比较无凭证请求和带现有会话凭证请求的响应。
   - 判断系统是否允许跨域携带 Cookie、会话标识或其他浏览器自动附带凭证。
   - 若使用自定义认证头，重点判断浏览器场景下是否真实可被跨站脚本读取，而不是仅在抓包工具中看到头部。

5. 验证实际可读性。
   - 选取一个最小敏感接口作为验证样本，例如“当前用户资料”或“当前账号可见配置”，避免使用修改类接口。
   - 在受控测试页面或等价受控浏览器环境中，验证跨站脚本是否能读取响应体中的业务字段，而不是只拿到状态码。
   - 若只能发起请求但读不到响应，应降低结论，不夸大为敏感数据泄露。

6. 评估影响面。
   - 横向比较同域下其他接口、同网关下其他路径、同认证体系下其他子系统是否复用相同 CORS 策略。
   - 只做低影响抽样，不做全量枚举；目的是证明策略级问题是否具有复用性。
   - 将“单接口问题”与“网关级通配/动态回显问题”明确区分。

7. 固化证据并准备复测点。
   - 对每一类结论保留一组最小证据：原始请求、跨域请求、响应头差异、响应体敏感字段摘要、认证态说明。
   - 同时记录预期修复点：白名单收敛、禁用凭证跨域、按接口分级放开、网关和应用双侧同步修复。

## 关键判断点

- 看到 `Access-Control-Allow-Origin` 不等于漏洞成立。关键是来源控制是否过宽，以及浏览器是否允许读取。
- `Access-Control-Allow-Origin: *` 若用于公开静态资源，通常不直接构成高风险；若用于敏感接口，需要继续看是否存在可读性和身份上下文。
- 动态回显 `Origin` 比固定白名单更值得优先验证，尤其是任意来源均被回显时。
- `Access-Control-Allow-Credentials: true` 是重要升级信号，但仍需结合真实会话是否会被浏览器带上，以及响应体是否含敏感数据。
- 仅有登录接口、心跳接口、公共配置接口出现跨域头，风险未必高；应优先寻找“当前用户可见数据”接口做最小验证。
- 若接口要求自定义 `Authorization` 等头，需区分“抓包工具可重放”与“浏览器跨站页面可利用”这两个事实，不能混为一谈。
- 若响应中只有成功状态、空对象、无身份差异数据，应谨慎定级，可作为配置缺陷或低危现象处理。
- 若多个子域、多个路径、多个接口表现一致，更可能是网关或公共中间件级配置问题，证据应指向策略层而非单页面。

## 证据链要求

- 保留同一接口的三组核心证据：
  - 正常同源或无 `Origin` 基线请求。
  - 带伪造 `Origin` 的跨域请求。
  - 带授权态且可读到业务字段的最小验证请求。
- 每组证据至少包含：请求方法、路径、关键请求头摘要、响应状态码、关键响应头、响应体字段摘要、时间点。
- 对敏感数据只保留脱敏摘要，例如“返回当前用户姓名字段”“返回账户绑定信息字段”，不要记录真实个人数据。
- 需要明确账号关系：使用何种授权测试账号、该账号本来可见什么数据、跨域后读到的仍是该账号数据还是不应暴露的数据。
- 若结论依赖浏览器可读性，应补充受控页面验证截图或等价过程记录，证明脚本实际读取到字段，而不是只发出了请求。
- 若评估为策略级问题，应补充至少一个同类接口抽样对照，证明不是单点误配。

## 风险定级思路

- 低危：
  - 仅发现 CORS 头配置过宽，但接口为公开内容、无认证上下文、无敏感字段可读性证据。
  - 只能证明存在头部异常，不能证明跨站读取有效业务数据。
- 中危：
  - 登录态接口存在来源放宽，且可稳定读取当前用户敏感资料、业务数据或安全相关配置。
  - 同一认证体系下存在多个只读敏感接口可被跨站读取，但尚未证明跨系统扩散或高敏操作链路。
- 高危：
  - 网关级或统一认证级策略错误，导致多个核心系统的登录态敏感数据可跨站读取。
  - 可读取高敏个人信息、财务信息、医疗信息、后台管理数据，或可稳定覆盖多个角色视角的数据面。
- 定级下调因素：
  - 仅个别公开接口受影响。
  - 需要不现实的前提才能触发。
  - 返回内容无业务敏感性，或无法在浏览器中读取。

## 修复与复测

- 修复建议应聚焦策略收敛：
  - 将允许来源改为精确白名单，不使用任意来源或无校验动态回显。
  - 非必要场景禁止 `Access-Control-Allow-Credentials: true`。
  - 将跨域放开范围限制到确有业务需求的路径、方法、请求头，不做网关级一刀切放行。
  - 对敏感接口继续依赖服务端鉴权，不把 CORS 当作访问控制本身。
- 复测时不要只测原报告接口。
  - 先复测原最小验证接口，确认伪造来源不再被放行或响应不可读。
  - 再抽样复测同域、同网关、同认证体系下的 2-3 个相似接口，确认不是只修一个路径。
  - 检查预检请求与实际请求是否都已收敛，避免仅修 GET/POST 之一。
  - 检查历史允许的业务前端域名是否仍可正常访问，避免因过度收敛引入业务回归。

## 报告表达模板

- 漏洞标题：
  - `CORS跨域配置缺陷导致登录态响应可被跨站读取`
- 漏洞概述：
  - `目标系统在部分接口上对跨域来源校验过宽，并允许浏览器在特定授权态下读取响应内容，导致同源策略保护被削弱。`
- 验证结论：
  - `在授权测试中，使用受控跨站来源对 <sensitive-endpoint> 进行最小化验证，发现系统对非预期来源返回放行头；在携带现有会话的浏览器场景下，可读取包含 <sensitive-field-summary> 的响应内容。`
- 影响范围：
  - `问题影响 <scope-summary>。当前已抽样验证 <count> 类接口存在相同策略表现，需排查同网关/同认证体系下的其他接口。`
- 风险说明：
  - `攻击者若诱导已登录用户访问受控页面，可能借助浏览器跨域机制读取该用户在目标系统中的敏感响应数据。实际风险取决于允许来源范围、凭证策略以及接口返回内容的敏感程度。`
- 修复建议：
  - `建议将跨域来源收敛为精确白名单，取消非必要的凭证跨域，按接口粒度限制允许的方法和请求头，并对同类接口开展统一复测。`
