# SQL错误与语句信息泄露测试方法论

## 编排适配

- 适用场景：响应中出现 SQL/ORM/数据库驱动错误、SQL 语句片段、表字段名或数据库异常回显，需要做低影响复核。
- 触发信号：`passive_sql_error_match`、`server_error_with_sql_keyword`、`database_error_page_detected`、`orm_error_detected`、`sql_statement_fragment_detected`。
- 测试前置环境：必须有目标返回给客户端的错误证据；优先复核 passive 已捕获响应，不主动扩大异常触发。
- 必需工件：`passive_findings`、`request_response_snippet`、`error_page_screenshot`。
- 解锁输出：`sql_injection_candidate`、`error_path_leakage_candidate`、`version_info_candidate`。
- 阻断条件：错误只在服务端日志、来自代理噪声、不可复现或需要高风险畸形输入才能触发。

## 适用场景

- 目标系统在页面、接口、下载页、查询页、管理后台或业务提交后出现数据库相关异常提示。
- 响应中出现 `SQL`、`syntax error`、`IntegrityException`、`SQLException`、`DbException`、`PDO`、`MyBatis`、`ThinkPHP`、`yii\db` 等数据库或框架线索。
- 页面返回了查询语句片段、表名、字段名、驱动名、物理路径、堆栈、行号、存储过程名或 ORM 异常对象。
- 研发声称“只是报错提示，不是注入”，需要判断其是否足以扩大后续攻击面。
- 修复后需要确认是否只是隐藏前端提示，而不是仅把详细错误换了位置继续暴露。

## 测试思想

- 这类问题的核心不在于“是否已完成 SQL 注入”，而在于服务端是否把本应只留在日志和监控中的数据库诊断信息返回给了前端。
- 优先证明“异常信息可被低成本、低影响、可重复地触发”，再判断该信息是否足以帮助攻击者缩小注入面、推断数据结构或识别技术栈。
- 始终构造对照组。至少比较一次正常请求与一次轻微异常请求，确认差异来自服务端数据库处理链路，而不是前端静态文案、网关提示或抓包工具误读。
- 采用最小化验证。优先选择只影响单条查询、单次提交、单个只读接口的方式，不做批量尝试，不做破坏性写入，不做越权扩展。
- 把该问题视为“信息泄露对后续数据库攻击面的放大器”。风险评估既看报错是否存在，也看泄露颗粒度、可重复性、认证门槛和业务敏感度。

## 操作流程

1. 信息收集
- 优先梳理容易进入数据库查询链路的位置：列表筛选、详情查看、搜索框、排序分页、导出下载、配置维护、资料更新、后台管理接口。
- 记录参数类型与业务语义，区分数值型、枚举型、文本型、日期型、布尔型和批量提交字段。
- 关注返回格式差异：HTML 报错页、JSON 错误对象、弹窗提示、空白页、下载异常页、反向代理自定义错误页。

2. 构造对照组
- 先发送一组完全合法请求，保存响应状态码、返回体结构、字段顺序和页面行为。
- 再选择单个参数做低影响扰动，例如空值、超长但有限长度值、类型不匹配值、截断值、边界日期、异常编码或缺失必填字段。
- 保证每次只改变一个变量，避免多个输入同时变化导致无法归因。

3. 最小化验证
- 观察异常响应中是否出现数据库关键字、SQL 片段、表字段名、占位符替换结果、存储过程名、驱动类名、框架类名、物理路径或堆栈行号。
- 若是 JSON 接口，重点看错误字段是否包含 message、trace、file、line、sql、code、type 等诊断项。
- 若是页面型应用，确认错误内容来自服务端实时生成，而不是页面模板中的固定占位文本。

4. 影响面确认
- 用相同方法在同模块的相邻接口上做少量抽查，判断是单点编码问题还是统一异常处理缺失。
- 对未登录、低权限、普通权限三类可授权身份分别做有限验证，确认泄露是否需要认证，以及不同角色是否可见相同细节。
- 若报错中包含 SQL 结构信息，评估其是否能直接暴露表名、字段名、查询条件、库类型、ORM 语义或文件路径。

5. 留证
- 固定保存一组“正常请求”和一组“异常请求”，两者应指向同一接口、同一账号、同一时间窗口。
- 对关键证据做脱敏标注，仅保留能支撑结论的路径、参数位置、错误类别和差异片段。

6. 修复复测
- 修复后重复相同对照组请求，确认前端不再看到详细错误。
- 继续验证是否仍会返回框架异常对象、调试字段、隐藏接口报错或下载页报错，避免只修了一个展示层。

## 关键判断点

- 是否是真实数据库异常链路
  - 真正的风险通常伴随数据库错误码、框架异常类、SQL 关键字、表字段名、物理路径或堆栈信息。
  - 如果只是“系统异常”“请求失败”这类泛化提示，且无任何数据库线索，一般不能直接归为本类问题。

- 是否存在可重复触发
  - 同一路径在相同条件下可稳定复现，结论才足够扎实。
  - 仅一次偶发报错、无法稳定复现、无法确认请求差异来源时，应谨慎下结论。

- 是否属于前端静态内容或中间件统一错误页
  - 静态页面中的示例文本、开发遗留注释、浏览器插件回显，不应误判为服务端 SQL 泄露。
  - 只返回网关错误页但未包含数据库细节时，更接近通用异常处理问题。

- 泄露颗粒度有多深
  - 仅出现数据库相关关键词，说明存在异常暴露，但攻击辅助价值有限。
  - 若出现完整或半完整 SQL、表名、字段名、条件拼接结果、堆栈、文件路径、驱动版本，则说明后续攻击面明显扩大。

- 是否与输入相关
  - 异常应与某个参数、提交字段、查询条件或业务动作具有明确关联。
  - 若不依赖任何输入、任何访问都会报错，更像稳定性或配置缺陷，但仍可能构成信息泄露。

- 是否存在误报
  - OCR 截图中的杂讯、历史缓存页面、测试工具面板内容、二次转述文字，都不能代替原始响应。
  - 报告结论应优先依赖原始请求响应和同条件对照，而非单一截图描述。

## 证据链要求

- 至少保留两组核心证据：正常请求响应、异常请求响应。
- 每组证据应包含以下最小元素：
  - 请求方法、请求路径、参数位置、认证态、时间点。
  - 响应状态码、响应头摘要、响应体关键差异。
  - 触发前页面行为与触发后页面行为。
- 若存在 SQL 语句或堆栈暴露，截图或文本证据中应能证明以下至少一项：
  - SQL 关键片段或数据库错误码。
  - 表名、字段名、视图名、存储过程名或 ORM 映射线索。
  - 文件路径、类名、行号、驱动名或框架异常类型。
- 证据需要说明“为什么这不是普通业务报错”，即指出它与数据库执行链路的对应关系。
- 所有导出证据必须脱敏，只保留占位符，例如 `<target-path>`、`<param>`、`<role>`、`<error-code>`。

## 风险定级思路

- 中危
  - 可向前端返回数据库相关错误提示，但未明显暴露完整 SQL、表结构、物理路径或堆栈。
  - 需要特定认证态、特定页面或特定业务流程才能触发，利用门槛相对更高。

- 高危
  - 返回完整或接近完整的 SQL 语句、表名字段名、数据库错误码、框架堆栈、物理路径、存储过程或驱动细节。
  - 信息可显著降低后续注入、越权探测或定向利用的试错成本。
  - 泄露发生在低权限、未登录或高频公共入口，暴露面较广。

- 风险上调因素
  - 多个接口存在同类回显，说明不是单点问题。
  - 同时暴露 SQL 与物理路径、类名、错误码，形成完整技术指纹。
  - 在核心业务模块、管理后台、批量查询或敏感数据入口出现。

- 风险下调因素
  - 只有模糊数据库异常字样，无结构信息，无复现稳定性。
  - 仅内网受限入口可见，且缺少进一步放大攻击面的辅助信息。

## 修复与复测

- 修复建议
  - 建立统一异常处理，前端只返回通用错误语义，不返回数据库、框架、文件路径和堆栈细节。
  - 在服务端日志中保留完整诊断信息，前端响应中移除 `sql`、`trace`、`file`、`line`、`debug` 等字段。
  - 对查询和更新逻辑采用参数化查询或安全 ORM 绑定，减少动态拼接带来的报错和注入联动风险。
  - 对输入做类型校验、长度校验、枚举校验和空值处理，避免异常值直接进入数据库执行层。
  - 关闭生产环境调试模式，清理默认异常页、开发框架调试组件和详细错误开关。

- 复测方法
  - 使用修复前同一组正常请求与异常请求重放，确认前端只返回通用错误或稳定业务提示。
  - 检查响应体中是否仍保留调试字段、异常对象、堆栈数组、SQL 片段或路径信息。
  - 在同模块相邻接口抽查，确认统一异常策略已覆盖而不是只修复单个接口。
  - 对不同认证角色做少量回归，确认不存在“普通用户已修复、后台接口仍泄露”的情况。

## 报告表达模板

- 漏洞概述
  - 经授权测试，目标系统在 `<target-module>` 的 `<target-path>` 处可因异常输入或异常业务条件返回数据库相关错误信息，前端可见内容包含 `<error-type>`，表明服务端未对数据库异常做充分脱敏处理。

- 判定依据
  - 在相同认证态与相同业务流程下，正常请求返回 `<normal-behavior>`，而仅变更 `<param>` 后，响应中出现 `<error-fragment>`。
  - 错误内容可指向数据库执行链路，包含 `<sql-or-stack-indicator>`，因此可判定为 SQL 错误与语句信息泄露，而非普通业务失败提示。

- 安全影响
  - 该问题会向攻击者暴露数据库实现细节，帮助其推断查询逻辑、数据结构或技术栈，降低后续 SQL 注入及相关攻击的试错成本。
  - 若同类回显存在于多个接口或低权限入口，整体暴露面和攻击辅助价值将进一步上升。

- 修复建议
  - 建议统一收敛数据库异常回显，前端仅返回通用提示；同时在服务端日志中保留排障信息，并结合参数化查询、输入校验和生产环境调试关闭进行整体修复。

- 复测结论
  - 复测时应重复原始对照组请求，确认前端不再返回 SQL、堆栈、物理路径或框架异常对象；若同模块其他接口仍存在类似回显，则该问题不能判定为完全修复。
