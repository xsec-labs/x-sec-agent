# 文件上传安全缺陷测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：发现头像、附件、富文本、导入、素材、对象存储直传或任意上传控件/API，需要验证上传限制和上传后可访问性。
- 触发信号：`file_upload_form_detected`、`file_upload_api_detected`、`object_storage_upload_credential_detected`、`rich_text_upload_detected`、`import_endpoint_detected`。
- 测试前置环境：通常需要有允许上传的测试账号和无害测试文件；禁止上传可执行恶意内容或影响真实用户的文件。
- 参考工件：`forms/actions`、`request_corpus`、`api_inventory`、`browser_state`、`test_file_artifacts`。
- 解锁输出：`uploaded_file_url_detected`、`stored_xss_candidate`、`file_download_access_control_candidate`、`cloud_secret_candidate_detected`、`path_leak_candidate`。
- 建议阻断（可低影响补齐时先补证再测）：无上传入口、上传会触发生产分发或只能上传真实业务材料。

## 适用场景

- 目标系统存在头像、附件、图片、富文本、导入模板、压缩包、证照、Logo、素材库等上传入口。
- 目标系统存在 `<upload>`、`<file>`、`<image>`、`<attach>`、`<import>`、`<editor>`、`<preview>`、`<download>` 等接口或前端线索。
- 需要判断问题属于哪一类：任意上传、未授权上传、上传绕过，或上传后文件可被直接访问、预览、下载、回显。
- 需要在测试范围内，以最小化验证方式确认上传控制是否只存在于前端、是否缺失服务端鉴权、是否存在上传后可达性风险。
- 需要为复测或报告提供一套可复用的证据链和风险分层框架，而不是复述某个具体案例。

## 测试思想

- 把问题拆成三条主线分别判断：是否能传、谁能传、传完后能否被不当访问或解释处理。
- 先证明“控制点是否存在”，再证明“控制点是否有效”。前端按钮限制、页面提示、前端后缀校验都不能视为有效防护。
- 优先使用无害、低影响、可识别的测试文件做最小化验证，避免使用会触发执行、写入系统状态或影响业务的样本。
- 必须设计对照组。至少比较以下差异：
- 合法业务文件与非业务允许类型文件的差异。
- 高权限、低权限、未登录三类身份的差异。
- 上传成功但不可访问，与上传成功且可直接访问之间的差异。
- 返回“上传成功”不等于漏洞成立。还要确认文件是否真实落盘、是否生成可用标识、是否能被后续接口取回。
- “未授权上传”与“任意上传”要分开判断。前者关注鉴权缺失，后者关注类型和内容控制缺失；两者可以单独成立，也可能叠加放大风险。
- 风险的关键放大点通常不在上传动作本身，而在上传后路径可预测、文件可直接预览、下载接口无权限校验、回源服务直接暴露、或存储位置被当作可解析资源。

## 参考方法（目标与常见路径，不是必须顺序）

下面是达成测试目标的常见路径，不是必须照做的脚本：可以合并步骤、调整顺序、跳过已经确认过的部分，或者换成你判断更合适的方法，只要仍能支撑下面的判断点和证据要求。

1. 枚举上传入口。
- 从页面表单、富文本编辑器、头像设置、系统配置、导入功能、拖拽上传组件、历史接口文档和抓包记录中定位入口。
- 记录每个入口的页面位置、接口路径、请求方法、参数名、业务归属和是否需要登录。

2. 建立业务基线。
- 先使用明确允许的业务文件完成一次正常上传，确认合法流程、必要字段、返回结构、文件标识和后续访问链路。
- 记录并原样输出服务端返回的文件 ID、相对路径、预览地址、下载地址、对象键名或引用字段，不替换为占位符。

3. 设计最小化对照组。
- 准备体积小、内容无害、便于识别的测试样本，覆盖“业务允许类型”和“业务不应允许类型”两组。
- 若怀疑仅校验扩展名或 MIME，可在不引入危险内容的前提下，构造“文件名、扩展名、声明类型、实际内容”不一致的低影响样本，验证校验落点。

4. 验证服务端类型控制。
- 对同一入口重复发送对照样本，比较服务端对文件名、扩展名、MIME、文件头、大小、数量、目录参数、分片参数的处理差异。
- 重点关注返回码、错误信息、返回体字段、生成路径、文件后缀变化、是否被重命名、是否仅在前端拦截。

4a. 系统化绕过 Fuzz（文件名、后缀、内容三维度联合测试）。

**核心原则**：每次只改变一个变量，保持文件内容无害（如空文件、纯文本 `test`、合法 JPEG 头字节），目的是找到校验落点而非真实执行恶意代码。先用业务允许的正常文件建立基线，再逐步变形。

**测试样本清单（按优先级排列）**：

所有样本均以合法文件头（magic bytes）开头，确保能绕过仅检查文件头的校验层。推荐统一使用 JPEG 头（`\xff\xd8\xff\xe0` + 若干 JFIF 标记字节，合计约 20 字节）作为默认文件头前缀，再追加测试标识字符串 `xsec-test`，总体积保持在 1 KB 以内，对业务无实质影响。PDF 头（`%PDF-1.4\n%%EOF`）可作为备选，用于允许 PDF 但拒绝图片的入口。

**构造 JPEG 头前缀（Python 片段，可本地执行）**：
```python
# 最小合法 JFIF JPEG 头（20 字节）+ 识别标记 + JPEG 结束符
jpeg_header = bytes([
    0xff,0xd8,0xff,0xe0,0x00,0x10,0x4a,0x46,
    0x49,0x46,0x00,0x01,0x01,0x00,0x00,0x01,
    0x00,0x01,0x00,0x00
])
marker = b"xsec-test"
jpeg_footer = bytes([0xff,0xd9])

payload = jpeg_header + marker + jpeg_footer
# 将 payload 写入对应文件名即可
```

**构造 PDF 头前缀（Python 片段）**：
```python
pdf_payload = b"%PDF-1.4\n1 0 obj\n<< >>\nendobj\nxref\n0 1\n0000000000 65535 f\ntrailer\n<< /Size 1 >>\nstartxref\n9\n%%EOF\nxsec-test"
```

**执行节奏**：
1. 先发"高风险后缀直接尝试"组——如果直接被拦截，记录拦截方式（前端还是服务端 4xx/5xx），再发其他变形样本测试是否能绕过同一控制点。
2. 对每个被服务端接受（2xx）的样本，立即跟进"上传后可访问性"验证（步骤6），确认文件能否被浏览器解释执行或直接下载。
3. 如果服务端对文件进行了重命名（如统一改为 UUID.jpg），需确认重命名后的文件仍可被访问，且浏览器是否根据 URL 后缀还是响应头的 Content-Type 决定渲染方式。
4. 对于 SVG 上传被接受的情况，单独在浏览器中访问该 SVG URL，确认是否触发脚本执行（即使内容无害也要记录此链路存在）。

**脚本化上传包 Fuzz 模板**：

当已经从浏览器 network 抓包、Burp 或 `request_corpus` 中拿到原始 multipart 上传请求包时，优先使用 `scripts/upload_fuzz_template.py` 生成可复用测试矩阵。该模板按 Upload_Auto_Fuzz 的原始策略集做全量 Fuzz，但改成普通 Python 代码：不依赖 Burp/Jython，不生成 WebShell，配置文件测试也只写入无害 marker 内容，不写入 `SetHandler`、`auto_prepend_file` 等会改变服务端解析行为的指令。

只生成测试包，不发送请求：

```bash
python skills/xsec-file-upload-security/scripts/upload_fuzz_template.py \
  --raw-request evidence/upload.raw.http \
  --output-dir evidence/upload-fuzz \
  --limit 0
```

发送低影响请求：

```bash
python skills/xsec-file-upload-security/scripts/upload_fuzz_template.py \
  --raw-request evidence/upload.raw.http \
  --base-url https://target.example \
  --output-dir evidence/upload-fuzz \
  --limit 0 \
  --send
```

若上传包使用相对路径且 `Host` 头不足以确定协议，必须补 `--base-url`。`--limit 0` 表示输出脚本生成的全部样本；需要分阶段低影响验证时，可用 `--categories suffix,content_type,magic_bytes` 或较小的 `--limit` 收敛范围。若只是验证模板自身可运行，使用 `--self-test`；这只会对内置样例包生成请求，不代表目标系统存在上传问题。

模板输出：
- `cases.jsonl`：每个测试样本的变形类型、文件名、声明 MIME、内容摘要、raw 请求路径和响应摘要（若启用 `--send`）。
- `*.raw.http`：可直接放入 Burp Repeater/Intruder 或证据目录的变形请求包。
- `summary.json`：本轮测试数量、输出目录和是否真实发送。

默认覆盖原插件除 WebShell 内容注入外的策略类别：后缀绕过、`Content-Disposition` 请求头操控、`Content-Type` 绕过、Windows/Linux 系统特性、魔术字节注入（JPG、PNG、GIF89a、GIF87a、BMP、PDF、ZIP）、Null 字节、编码绕过、WAF 绕过、配置文件名上传、特殊字符、大小写变体和多重后缀。所有文件内容均为 `xsec-upload-check` marker、图片/PDF/ZIP 头加 marker，或无害配置注释。

**如何判断绕过成立**：
- 服务端返回 2xx 且生成了文件标识或路径 → 上传动作绕过成立。
- 上传后文件可通过浏览器直接访问，且响应的 Content-Type 为 `text/html`、`image/svg+xml` 等可被浏览器主动解释的类型 → 构成完整威胁链路（XSS/内容注入可能性），风险升为高危。
- 上传后文件仅以 `application/octet-stream` 或 `Content-Disposition: attachment` 方式返回 → 执行风险受限，但上传控制缺陷仍存在，结合文件类型评估等级。
- 服务端重命名了文件但仍接受上传 → 上传控制失效，重命名只是存储层处理，不能视为有效安全控制。

5. 验证授权控制。
- 分别以高权限、低权限、未登录状态访问同一上传接口。
- 若页面不可见但接口可直接调用，判断是否存在“隐藏入口但未真正鉴权”的情况。
- 若接口路径、参数或上传组件位于 `<open>`、`<public>`、`<anonymous>` 等语义位置，应优先检查是否误暴露。

6. 验证上传后可访问性。
- 沿着返回的文件 ID、路径、预览接口、下载接口、业务详情页引用链路，确认文件是否可被直接访问。
- 分别验证“上传者本人可访问”“其他已登录角色可访问”“未登录可访问”三种情况，确认风险边界。
- 若系统提供预览、回显、富文本展示或对象存储直链，判断其是否把上传内容当作主动内容处理，而不是仅作为下载对象。

7. 收敛影响面。
- 横向检查同类入口是否共用同一上传服务、同一文件网关、同一对象存储桶策略或同一下载接口。
- 区分单点缺陷与平台级缺陷，避免只凭一个页面下结论，也避免过度扩展未验证的影响面。

8. 留证、清理与复测。
- 固化最小必要证据后，删除测试文件或通知对方清理，避免残留。
- 修复后按“原入口、同类入口、上传后访问链路、不同角色”四个维度复测，确认控制点不是只补了单一路径。

## 关键判断点

- 仅前端限制，服务端仍接受非业务允许类型文件，可判定为真实控制缺陷。
- 服务端拒绝上传，但只是在响应层报错，仍实际生成文件或文件标识，不能判定为修复有效。
- 低权限或未登录可直接调用上传接口，即使只能上传图片，也属于授权控制缺陷。
- 允许上传非业务允许类型，但文件无法被访问、无法被引用、且存储区不会被主动解释处理，风险通常低于“上传后可直接访问或被处理”的场景。
- 上传后若仅返回成功布尔值，没有返回路径，也要继续从业务详情页、文件列表、预览接口、下载接口寻找可达性证据。
- 若下载接口本身无权限控制，上传缺陷与访问控制缺陷会形成组合链路，风险应整体评估，不宜拆散淡化。
- 需要警惕“复测假象”：单个入口限制了扩展名，但分片上传、批量上传、富文本上传、历史兼容接口仍可绕过。
- 无法证明落盘、无法证明可访问、无法证明鉴权缺失时，不要直接上升为高危，应回到证据链补证或下调结论。
**绕过 Fuzz 专项判断点**：
- 双后缀绕过（如 `test.jpg.html`）被服务端接受且浏览器以 HTML 解释：高危，完整威胁链路成立。
- Null 字节截断（`test.html%00.jpg`）在现代框架中通常不生效，但老旧 PHP/C 扩展仍存在；若不生效，记录后继续其他变形样本，不要停在这一种。
- SVG 被图片接口接受：即使当前内容无害，该上传路径本身已构成 stored XSS 风险入口，需单独记录为中高危。
- 服务端对文件进行了重命名（UUID 化）但接受上传：重命名不等于有效校验，仍需确认重命名后文件的 Content-Type 响应头；若 CDN/OSS 回源按 URL 后缀推断类型，可能导致绕过。
- 后缀大小写（`.HtMl`）或末尾加点（`.html.`）被接受：说明后缀白名单未规范化处理，属于校验逻辑缺陷。
- 无后缀文件（`testfile`）被接受且落盘路径不含后缀：需确认服务器是否按内容推断处理，Web 服务的默认 MIME 配置可能决定最终行为。
- MIME 与文件头不一致样本均被接受：说明系统未做魔数校验，校验仅依赖 Content-Type 请求头（用户可控），属于弱校验，可升格描述。
- 路径穿越文件名（`../test.html`）被服务端不过滤地传入存储层：需进一步确认落盘路径是否真实穿越，不要仅凭接口返回推断。
## 证据链要求

- 保留入口定位证据：页面位置、功能名称、接口路径、请求方法、关键参数名。
- 保留正常业务上传基线：合法文件请求与响应，用于证明业务预期。
- 保留对照组证据：非业务允许类型样本的请求与响应，以及与合法样本的差异点。
- 保留身份差异证据：高权限、低权限、未登录三组请求结果，明确每组身份来源与时间点。
- 原始敏感内容保存到受控证据目录；共享发现、截图展示、报告和委派使用最少必要的原始摘录（xSec 不做自动脱敏）与证据引用，截断只因体积限制并明确标记。
- 保留访问链路证据：上传后通过预览、下载、详情页回显或引用接口取回文件的结果。
- 保留修复前后对比：修复后相同请求的阻断结果，以及旧文件、旧路径、旧接口是否仍可访问。
- 每条结论至少要能回答四个问题：入口在哪里、什么控制失效、谁可以利用、上传后文件处于什么状态。

**绕过 Fuzz 专项证据记录**：
- 对每个测试样本，记录：文件名（含变形方式说明）、声明的 Content-Type、文件实际内容描述、完整原始请求、服务端响应码与响应体、服务端返回的存储路径或文件 ID。
- 若服务端接受上传，补充记录：通过浏览器直接访问该文件 URL 时的响应头（特别是 `Content-Type` 和 `Content-Disposition`），以及页面渲染行为（是否被解释为 HTML/SVG/脚本，还是作为下载对象）。
- 对于"绕过成立但无法访问"与"绕过成立且可被浏览器解释"两种结果，应分别截图留证，不能混为一谈。
- Fuzz 测试结束后，应输出一张"测试矩阵摘要"表格，至少包含：变形类型、是否上传成功、上传后是否可访问、浏览器响应类型、风险结论，便于报告引用和复测对照。

## 风险定级思路

- 高危：未登录或低权限可上传，且上传后文件可被直接访问、预览、引用或经业务链路暴露；或平台级上传服务普遍缺失控制，影响多个模块。
- 高危：服务端允许非业务允许类型文件进入可访问区域，且文件路径、文件 ID、预览链路明确可证。
- 中危：上传控制可被绕过，但文件仅存于不可直接访问区域，仍需结合业务引用范围、存储位置和后续处理链路评估。
- 中危：仅特定高权限角色所在后台存在类型控制缺陷，但能被稳定复现，且可影响系统完整性或存储资源。
- 低危或提示项：只发现前端校验薄弱，但服务端校验和鉴权有效；或上传成功的判定无法证明真实落盘与后续可达。
- 定级时不要只看“能否上传”，还要结合身份门槛、文件类型、访问链路、可扩散范围、是否平台级复用。

## 修复与复测

- 修复建议应覆盖三层：上传前鉴权、上传时校验、上传后存储与访问控制。
- 鉴权层面：对上传接口、预览接口、下载接口、回源接口统一做服务端权限校验，不依赖页面是否显示按钮。
- 校验层面：采用白名单策略，联合校验扩展名、声明类型、文件头、大小、数量、分片合并结果和业务上下文。
- 存储层面：使用随机文件名，隔离存储目录，避免直接暴露在可解析资源路径下，默认按下载对象处理而非主动渲染。
- 管理层面：补充病毒扫描、内容审计、配额限制、审计日志和异常告警，但这些不能替代基础鉴权与白名单。
- 复测时至少验证四件事：原始入口已阻断、同类入口同步修复、上传后的旧访问链路失效、不同角色差异符合权限设计。
- 若曾存在历史可访问文件，复测需确认历史遗留文件已清理或已受新访问控制保护。

## 报告表达模板

- 漏洞标题：
- 文件上传安全缺陷 / 未授权上传 / 上传后文件访问控制缺失

- 漏洞描述：
- 在 `<业务模块>` 的 `<功能入口>` 处，服务端对上传请求的 `<类型校验或权限校验>` 不充分。测试中使用无害样本进行最小化验证，发现 `<低权限用户/未登录状态/非业务允许类型文件>` 仍可被服务端接受，并生成 `<文件标识或引用记录>`。

- 验证结果：
- 通过对照合法上传与异常上传请求，可见服务端未有效校验 `<扩展名/MIME/文件头/身份权限>`。
- 上传完成后，文件可通过 `<预览链路/下载链路/业务回显链路>` 被访问，说明问题不仅存在于上传动作，还影响到上传后文件的访问控制边界。

- 安全影响：
- 攻击者在获得相应入口访问条件后，可能向系统写入非预期文件，或绕过既有业务边界上传内容。
- 若相关文件随后可被其他用户、匿名访问或业务组件直接引用，风险将从单点上传控制缺陷扩大为内容暴露或系统完整性风险。

- 修复建议：
- 为上传、预览、下载相关接口补充统一的服务端鉴权。
- 对上传文件实行白名单校验和隔离存储，避免使用用户可控文件名与可直接解析路径。
- 对历史已上传文件与同类接口开展排查，确保修复不是单点补丁。

- 复测结论：
- 修复后应确认 `<异常样本>` 被服务端阻断，`<低权限/未登录>` 无法调用上传接口，且历史访问链路不再返回原测试文件。
