# 暴力破解防护缺失测试方法论

## 编排适配

- 适用场景：发现登录、短信登录、邮箱登录或认证失败处理路径后，验证服务端是否具备限频、锁定、验证码升级和密码喷洒防护。
- 触发信号：`login_form_detected`、`auth_endpoint_detected`、`failed_login_baseline_available`、`captcha_absent_on_auth`、`password_spray_surface_detected`。
- 测试前置环境：必须有认证接口和授权测试账号；需要授权方明确允许少量失败登录、约定最大次数、速率、锁定恢复方式和停止条件。
- 必需工件：`auth_request_sample`、`failed_login_responses`、`rate_limit_observations`、`test_account_list`。
- 解锁输出：`brute_force_protection_missing`、`captcha_otp_defect_candidate`、`account_lockout_observed`、`weak_pass_check_constraints_updated`。
- 阻断条件：无登录接口、无测试账号、授权禁止失败请求、账号锁定无法恢复或目标已触发风控。

## 适用场景

- 目标是登录、统一认证、OA、后台管理、客服门户、短信验证码校验等身份认证入口。
- 已获得授权，且可以使用测试账号、测试手机号、测试验证码流程或经确认可用于验证的非生产身份数据。
- 关注点不是"是否能猜中真实口令"，而是"服务端是否缺少频率限制、锁定、冷却、验证码升级或异常检测"。
- 适用于单账号重复尝试、同密码跨账号尝试（密码喷洒）、验证码重复提交、不存在账号的限频验证、同一账号在多个等价接口重复认证等低影响验证场景。
- 如果系统仅表现为"没有图形验证码"，不能直接判定存在漏洞；仍需验证是否已有其他有效控制点。

## 测试思想

- 先确认认证入口，再确认认证控制点。暴力破解防护缺失的核心不是页面长什么样，而是失败请求在时间、次数、账号、设备、会话维度上是否被服务端约束。
- 优先构造对照组，而不是直接扩大尝试规模。对照组要能回答四个问题：失败是否累计、限制是否稳定、限制是否可被轻易绕过、对不存在的账号是否同等约束。
- 将问题拆成五类判断：① 单账号爆破防护、② 密码喷洒防护、③ 不存在账号的处理、④ 验证码有效性校验、⑤ 等价接口绕过。不同类型共因相同，但验证方式和风险表述不同。
- 保持最小化验证。通常只需少量失败请求，就足以证明"没有限制"或"限制只在局部生效"；不需要真实爆破成功，更不应追求批量命中。
- 将"工具返回差异"与"安全控制生效"分开判断。状态码变化、响应长度变化、偶发报错、WAF 拦截、前端提示变化，都必须结合连续请求序列解释。

## 操作流程

### 步骤 1：确认入口

- 识别登录表单、认证接口、短信验证码提交接口、找回密码中的验证码校验点。
- 记录请求方法、关键参数、失败提示、是否依赖 Cookie/Session、是否有前端验证码或滑块。
- 同时记录接口返回的**错误信息差异**：账号不存在 vs. 密码错误是否提示相同，这本身也是账号枚举风险指标，会影响后续喷洒难度评估。

### 步骤 2：识别最小测试对象

- 优先使用约定测试账号、测试手机号、测试租户或专用验证环境。
- 额外准备 1 个**明确不存在的账号标识**（如随机字符串），用于专项验证系统是否对不存在账号同等限频。
- 如果必须验证多账号场景，只使用经过授权的少量样本，不扩展为批量枚举。

### 步骤 3：建立基线请求

- 发送一次正常格式但必然失败的认证请求，确认失败提示、响应码、响应体长度、返回字段和时间戳。
- 同步对**不存在账号**发送相同格式的请求，对比：响应码是否相同、错误提示是否相同、响应时间是否存在显著差异（时序差异可辅助账号枚举）。
- 观察失败后是否立即出现验证码升级、冷却提示、临时锁定或二次验证。

### 步骤 4：单账号爆破防护验证

- 对同一测试账号发送 **5～10 次**连续错误口令或错误验证码请求，节奏均匀，不刻意放慢。
- 关注是否出现失败计数累计、短时间限频、账号锁定、会话冻结、验证码刷新或接口熔断。
- 如果连续失败后仍可无限重试，且响应行为稳定，可判定存在单账号爆破防护缺失。

### 步骤 5：不存在账号的限频验证（重点检测）

- 对明确不存在的账号标识重复发送错误认证请求（5～10 次）。
- 判断：系统是否对不存在账号**同样执行**频率限制或锁定？
- **常见缺陷模式**：系统先查询账号是否存在，只对"查询到用户记录"才累计失败计数，导致攻击者对不存在账号可无限重试，完全绕过账号锁定机制。
- 如果不存在账号可无限重试而真实账号会被锁定，属于**锁定绕过**，应单独记录为独立发现。

### 步骤 6：密码喷洒防护验证（重点检测）

密码喷洒的本质不是单账号多次尝试，而是对多个账号各尝试极少数候选口令，从而规避按账号计数的锁定策略。验证时应设计两个明确的对照组：

- **对照组 A**：对同一测试账号连续发送少量错误口令（5～10 次），验证单账号锁定是否生效。
- **对照组 B**：使用单一常见密码（如 `123456`），依次对多个不同测试账号（含存在与不存在账号各 2～3 个）各发送 1 次尝试，验证跨账号低频限制是否生效。

保持除账号字段外其他条件尽量一致：来源、请求头、设备标识、时间间隔。

- 判断：系统是否仅在单账号维度计数，还是同时在 IP/设备/会话维度进行跨账号检测？
- 如果单账号在多次失败后被锁定，但切换账号后可立即继续以同一密码尝试，则账号维度的控制不能防御密码喷洒。
- 喷洒防护的关键是**源维度控制**（IP 限频、设备指纹、会话行为评分），而不仅仅是账号锁定。
- 喷洒对不存在账号也应同样验证：若不存在账号没有任何限制，喷洒成本更低。
- 若跨账号尝试未出现命中，但所有请求均被正常受理、无联动阻断、未触发验证码升级，且响应差异可支持持续喷洁，仍可判定存在防护缺失，**不需要真实命中成功才能得出结论**。

### 步骤 7：验证码校验有效性验证（重点检测）

**7a. 验证码存在性与触发时机**
- 确认是否在首次请求即要求验证码，还是在多次失败后才触发验证码升级。
- 记录触发验证码的失败次数阈值（如"第 3 次失败后出现图形验证码"）；该阈值即为免验证码的爆破窗口。

**7b. 验证码可重用性**
- 提交一次含正确验证码但错误密码的请求，记录该验证码值。
- 在下一次请求中**复用同一验证码值**，观察服务端是否拒绝（验证码应为一次性，服务端校验后立即作废）。
- 若可重用，攻击者只需解一次验证码即可持续提交，验证码机制形同虚设。

**7c. 验证码可绕过性（直连接口）**
- 如果页面有验证码，尝试直接调用后端认证接口，请求中省略验证码参数或设为空字符串。
- 若接口在验证码缺失时仍返回正常认证失败（而非"验证码错误/必填"），说明验证码校验未在服务端强制执行。

**7d. 验证码无限穷举**
- 对同一验证码保持账号密码不变，仅多次变换验证码答案，观察是否出现验证码失效或次数限制。
- 对于图形验证码：服务端是否在错误答案后刷新验证码？是否对同一会话的验证码错误次数计数？
- 对于短信/邮件验证码：是否有错误次数上限？超出后是否强制重新发送？

### 步骤 8：等价入口对照组

- 检查 Web 表单、异步接口、移动端接口、后台接口、不同 Content-Type 的请求是否共用同一失败控制逻辑。
- 若页面层面出现验证码或锁定，但直连接口仍可重复尝试，应判定为控制点可绕过。

### 步骤 9：评估影响面

- 确认问题是单入口、单业务、单租户，还是统一认证、管理后台、短信验证码网关等公共认证能力。
- 判断是否面向公网、是否覆盖管理员入口、是否可影响大量有效账号。

### 步骤 10：固化证据并停止扩展

- 达到可证明阈值后停止继续尝试，避免对业务造成干扰。
- 将验证过程收束为"少量请求即可证明"的证据链。

## 常见绕过手法（测试时同步检查）

以下手法在实战中常被用于绕过频率限制，测试时应逐一确认是否已被防御：

| 绕过手法 | 测试方式 | 典型缺陷 |
|---|---|---|
| 修改 `X-Forwarded-For` / `X-Real-IP` | 每次请求变换伪造 IP | 系统仅基于 IP 限频且信任客户端 IP 头 |
| 更换 User-Agent | 变换 UA 字符串 | 限频与 UA 绑定而非与账号/会话绑定 |
| 切换请求格式（JSON↔Form） | 同参数不同 Content-Type | 不同路由处理逻辑不一致 |
| 更换认证接口路径（/api/v1/ vs /api/v2/） | 尝试历史版本或并行接口 | 旧版本接口未部署同等控制 |
| 绕过 Session 绑定（不带 Cookie） | 去除 Cookie 后重复尝试 | 失败计数与 Session 强绑定 |
| 使用不存在账号 | 构造随机账号标识 | 计数逻辑依赖账号存在性 |

## 关键判断点

- 没有图形验证码不等于存在漏洞；关键在于服务端是否对失败尝试实施了有效控制。
- 统一错误提示不等于安全；若失败次数不累计、无冷却、无锁定、无升级验证，仍可能成立。
- **是否存在"只防暴力破解、不防密码喷洒"的情况**：单账号失败会锁定，但多个账号各尝试一次不会触发任何联动限制。
- 单账号有限制不代表问题已修复；若更换账号即可继续尝试，则属于密码喷洒防护不足。
- **对不存在的账号无限制，不代表"没有风险"**；攻击者可针对构造账号标识进行喷洒，规避锁定。
- 页面被限制不代表接口被限制；如果接口可绕过页面验证，问题仍然成立。
- 验证码可重用、可绕过、可无限穷举，均构成独立的验证码校验缺陷。
- **验证码是否真正参与服务端校验**：仅前端展示验证码，不代表后端用它阻断跨账号尝试。
- 返回 429、验证码刷新、临时锁定、冷却倒计时、二次校验提升，通常是控制生效信号；但要确认是否真正落到服务端，而非仅前端展示。
- 返回 500、长度变化或偶发超时，不应直接视为安全控制；需要排除异常处理、网关报错或脆弱实现。
- 对短信验证码场景，判断重点是错误次数限制、验证码时效、尝试窗口和重新发送策略，而不是是否真的命中正确验证码。
- **密码喷洒测试不需要真实命中才能得出结论**：若已证明跨账号低频尝试不受任何联动限制，且响应差异足以支持持续喷洒，即可判定防护缺失，不必继续扩大账号数量或尝试轮次。
- **风险是否被高估**：若目标仅内网可达、强制 MFA、统一风控联动良好、账号枚举信号弱，则应下调风险描述，不能只因"请求可通过"就机械上调风险。
- 如果只能证明"某个低价值入口缺少防护"，而无法证明可扩展到其他认证入口，风险定级应保持克制。

## 证据链要求

- 保留认证入口截图或接口定位依据，但必须使用脱敏后的页面名、路径占位符和参数占位符。
- 保留一组基线失败请求与响应，标注时间点、账号类型、参数位置、失败提示和响应差异。
- 保留一组最小化连续失败样本，证明在达到合理尝试次数后仍未触发限频、锁定、冷却或验证码升级。
- 如涉及不存在账号，保留"不存在账号可无限重试"与"真实账号被锁定"的对照证据，体现控制缺失维度。
- 如涉及密码喷洒，保留"单账号受限"与"跨账号仍可继续"的对照证据，体现控制点缺失维度。
- 如涉及验证码，分别保留：验证码可重用的对照请求、省略验证码参数接口仍正常响应的请求、同一验证码多次穷举的请求序列。
- 如涉及多入口，保留"页面受限但接口未受限"或"入口 A 生效、入口 B 不生效"的对应证据。
- 如涉及短信验证码，保留错误验证码重复提交后系统仍接受尝试的序列证据，不记录真实手机号或真实验证码。
- 所有截图、请求和响应中必须脱敏：域名、IP、Cookie、Token、账号、手机号、身份证号、业务编号一律替换为占位符。
- **背景证据**：记录测试时间窗、来源环境、受控账号数量、尝试次数上限和停止条件，用于支撑测试结论具备可重复性与授权前提。
- 证据应支持结论闭环：入口在哪里、测试对象是谁、做了多少次低影响尝试、预期控制是什么、实际为何判定未生效。

## 风险定级思路

- **低危**：仅单一低价值入口存在尝试控制不足，且存在其他补偿措施，难以扩展到高价值身份或公共认证能力。
- **中危**：常规账号密码登录或验证码校验缺少有效限频/锁定，面向公网，可对普通用户账户形成稳定撞库或喷洒风险；或验证码可被重用/绕过但仅限于普通入口。
- **高危**：问题位于统一认证、管理员入口、公共短信验证码能力或跨系统复用认证能力，且缺陷覆盖范围大、绕过成本低、可显著放大账户接管风险；或验证码完全可绕过导致等价于无验证码防护。
- 定级时看"控制缺失的覆盖面"和"被利用的现实成本"，不要仅因工具能连续发送请求就机械上调。
- 若已观察到分层控制，例如网关限频、账号锁定、二次验证升级，但局部仍可绕过，应根据绕过条件是否普遍、是否需要额外前提来校准风险。

## 修复与复测

- 修复建议应落到服务端控制：失败次数累计（对所有账号标识，不论是否存在）、时间窗口限频、账号锁定或冷却、验证码升级、多因素认证、异常登录监测、日志告警。
- 不建议只依赖前端验证码、前端倒计时或页面按钮置灰；这些措施必须由服务端校验支撑。
- 对密码喷洒问题，修复点应覆盖账号维度与源维度，避免只锁定单账号而忽略跨账号低频尝试。
- 对不存在账号的限频：应在认证逻辑层面对所有失败尝试统一计数，不依赖账号是否存在于数据库。
- 对验证码问题：验证码应在服务端强制校验、一次性使用并立即失效；错误次数超限应强制刷新或冻结会话。
- 对短信验证码问题，修复点应覆盖验证码错误次数、有效期、重发频率、绑定对象和校验窗口。
- 复测时先验证原入口，再验证等价接口、不同客户端、不同请求格式，确认控制点不是只修补了单一路径。
- 复测通过的标志应包括：达到阈值后出现明确限制；限制可持续一段合理时间；更换会话或刷新页面不能立即绕过；日志或审计能记录异常尝试；对不存在账号同样触发限制。
- 复测报告中要区分"控制已部署"与"策略合理有效"。例如仅增加验证码但失败次数仍不累计，不能视为完全修复。

## 报告表达模板

**漏洞名称**：暴力破解防护缺失

**漏洞描述**：目标认证入口 `<auth-entry>` 在连续认证失败后，服务端未对 `<account>` / `<source>` / `<verification-object>` 维度实施有效的限频、锁定、冷却或验证升级；且对不存在的账号标识亦未执行等价限制，导致攻击者可能持续尝试口令、喷洒密码或穷举验证码。

**验证方式**：在授权测试前提下，使用测试身份构造少量错误认证请求，分别对单账号连续失败、不存在账号连续失败、跨账号同密码尝试（密码喷洒）、验证码重用/绕过进行对照验证，观察系统是否触发服务端控制。

**判断依据**：
- 测试账号在 5～10 次失败后接口仍返回可继续尝试的响应，未出现稳定的限频、锁定、冷却或验证升级；
- 对不存在账号同等尝试，接口响应稳定且无任何限制；
- 切换账号后可立即继续以同一密码尝试，源维度无任何控制；
- 验证码参数省略/复用后接口仍接受请求，验证码校验未在服务端强制执行。

**影响说明**：若攻击者掌握有效账号标识或手机号，可结合弱口令、撞库结果或验证码穷举，在较低成本下持续发起认证尝试，增加账户接管或批量撞库成功的可能性。实际影响取决于入口价值、账号规模和补偿控制情况。

**修复建议**：在服务端增加失败次数累计（不论账号是否存在）、时间窗口限频、账号锁定或冷却、验证码一次性强制服务端校验、二次验证升级、异常尝试告警，并统一覆盖所有等价认证入口与客户端。

**复测建议**：修复后应对原认证入口、并行接口、不同请求格式、不存在账号标识和不同身份维度同步复测，确认控制策略已统一生效且不可被简单绕过。
