# 密码明文处理与返回测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：登录、记住密码、改密、重置、用户详情或认证链路中出现密码明文传输、响应返回、缓存或可逆保存。
- 触发信号：`password_value_in_request_detected`、`password_value_in_response_detected`、`password_value_in_storage_detected`、`remember_password_detected`、`reset_password_returns_plaintext`。
- 测试前置环境：通常需要使用测试账号和受控临时口令；需要能捕获请求/响应和浏览器存储。
- 参考工件：`request_corpus`、`storage_snapshot`、`browser_state`、`test_password_marker`。
- 解锁输出：`browser_storage_review_needed`、`insecure_crypto_candidate`、`transport_security_review_needed`、`session_management_review_needed`。
- 建议阻断（可低影响补齐时先补证再测）：无密码流、无法使用测试口令、仅为前端输入框当前值且未持久化/未返回或证据会暴露真实密码。

## 适用场景

- 适用于登录、注册、修改密码、重置密码、用户管理、账号详情查询、导入导出、记住密码、自动登录等涉及口令处理的业务流程。
- 适用于 Web、H5、前后端分离系统、移动端接口、桌面客户端接口等存在认证请求与用户资料返回的场景。
- 适用于怀疑密码在请求体、响应体、响应头、前端状态、浏览器存储、客户端缓存或调试回显中暴露的场景。
- 适用于需要判断“前端未 hash”究竟只是弱实现现象，还是已经形成明文返回、明文缓存、明文存储链路的场景。
- 不适用于仅看到掩码值、固定占位符、一次性挑战值或不可逆摘要就直接下结论的场景，必须先排除误判。

## 测试思想

- 这类问题应按链路看待：`入口输入 -> 传输过程 -> 服务端处理 -> 落盘/缓存 -> 返回前端 -> 再次查询或复用`。
- 核心目标不是证明“能否进一步利用”，而是判断原始密码或等效秘密是否在不该出现的位置被处理、保存或返回。
- 优先区分四个问题：密码是否以明文或可逆形式提交、服务端是否回显密码、前端或客户端是否缓存密码、是否有足够证据支持“服务端明文存储”。
- `前端未 hash` 不是天然高危，也不是安全边界本身。若全程受 TLS 保护且未发现返回、缓存、落盘或日志暴露，它通常只能作为低风险现象或实现缺陷记录。
- 真正需要优先定性的，是“服务端把密码再次交给前端”“账号详情或列表接口带出口令字段”“记住密码功能把原始口令持久化在客户端”“修改或重置后仍可取回原始密码”。
- 全程使用测试账号和临时测试口令标记开展验证。测试口令应具备可识别性，并在证据中保留完整原文供后续复核。
- 必须构造对照组，而不是凭单张抓包截图定性。至少回答：什么动作触发了暴露、关闭相关功能后是否仍存在、是否只是占位符、退出或刷新后是否仍可见。

## 参考方法（目标与常见路径，不是必须顺序）

下面是达成测试目标的常见路径，不是必须照做的脚本：可以合并步骤、调整顺序、跳过已经确认过的部分，或者换成你判断更合适的方法，只要仍能支撑下面的判断点和证据要求。

1. 信息收集
- 梳理所有与密码有关的入口：登录、修改密码、重置密码、找回密码、用户查询、用户详情、管理员维护用户、记住密码、自动登录。
- 标记可能的字段名和承载位置，如请求体字段、JSON 字段、表单项、响应对象、表格列表、导出文件、前端本地存储键名。
- 确认认证方式、是否启用 TLS、是否存在网关、代理缓存、前端状态持久化、移动端本地缓存等中间环节。

2. 建立基线
- 在干净环境下清理站点数据或客户端缓存，记录未登录状态下的存储、请求与响应基线。
- 准备专用测试账号，并设置一次性临时测试口令标记，确保后续可与返回值做一一对应。
- 同时准备至少一组对照条件，如“记住密码开启/关闭”“修改前/修改后”“登录成功/登录失败”。

3. 验证入口链路
- 以最小必要动作触发登录、修改密码或重置密码，观察请求体、表单、查询参数、请求头、WebSocket 负载中是否直接出现原始口令。
- 若仅看到客户端提交明文口令，要继续判断是否处于 TLS 保护下，以及是否还有后续返回、缓存、日志或多跳转发暴露证据。
- 不要仅凭“请求里是明文”就直接推断“数据库明文存储”；该结论必须由后续链路证据支持。

4. 验证返回链路
- 重点检查登录响应、当前用户信息、用户详情、列表查询、管理员检索、密码修改结果、重置结果、导出接口等返回内容。
- 优先寻找与临时测试口令标记一致的值，或可经低影响识别还原为同一值的字段。
- 对同一接口做最小化对照，排除固定默认值、掩码文本、占位符字段、旧缓存页面或非原始值回显。

5. 验证缓存与落点
- 检查响应预览、页面渲染数据、前端状态管理、`localStorage`、`sessionStorage`、`IndexedDB`、浏览器记住密码逻辑、客户端本地缓存中是否保留口令。
- 检查刷新页面、退出登录、切换账号、关闭重开后，这些值是否仍存在，判断其持久性与二次暴露面。
- 如发现响应头、下载内容或中间页面也携带口令字段，应按最小化原则留证，不扩展为高影响利用动作。

6. 构造对照组
- 对比“记住密码开启/关闭”，判断是否只有特定功能分支导致原始口令持久化。
- 对比“修改前/修改后”的查询接口，判断服务端是否能再次吐出刚设置的新口令。
- 对比“本人资料接口/管理员用户管理接口”，判断暴露是否仅限本人，还是扩大到运营、客服、管理员等角色视角。
- 对比“单条详情/批量列表/导出结果”，判断是否存在批量暴露。

7. 影响面收敛与扩展
- 若一个接口发现返回口令，应沿同一数据模型继续核查创建、编辑、查询、列表、导出、同步接口，判断是否属于通用返回模板问题。
- 若一个页面出现明文缓存，应检查同域子系统、公共登录组件、统一用户中心、网关聚合接口是否复用同样逻辑。
- 影响面分析应围绕“谁能看到、能看到几类账号、是否可持续获取、是否可能造成账号接管或口令复用风险”展开。

8. 留证与复测
- 证据应同时保留动作前后差异、测试账号角色、时间点、触发步骤和完整原始值，确保结论可复核。
- 修复后按原路径复测，并补测相邻路径，避免只修一个登录接口却遗漏用户查询、导出或缓存逻辑。

## 关键判断点

- 最强证据是：测试时提交的临时口令标记，在返回包、详情接口、列表字段、导出结果或客户端缓存中再次出现。
- `******`、固定默认文案、空字段、一次性挑战值、不可逆摘要，不应直接认定为“密码返回”或“明文存储”。
- 若返回的是摘要值或加密值，要继续判断其是否可逆、是否等价于原始口令暴露，而不是简单把“存在 password 字段”直接定性。
- 仅有 `前端未 hash`、且传输受 TLS 保护、未发现下游返回与缓存时，通常只能定为低风险实现问题，不宜夸大成高危。
- 若为明文 HTTP、弱代理链路、可落日志路径、多级转发场景，即便未证明服务端存储，也应上调对传输暴露面的关注。
- 如要下结论为“服务端明文存储”，优先具备以下任一证据：修改后可再次查询出原始口令、多个接口稳定返回同一原始口令、重置或导出结果包含原始口令、退出后重新查询仍可取回旧值。
- 若只有即时响应中回显一次口令，但无更多证据支持落盘，应报告为“返回链路暴露”，不要越界推断后台实现细节。

## 证据链要求

- 证据至少覆盖六个要素：触发入口、测试账号类型、临时口令标记关系、请求中的位置、响应或缓存中的位置、对照组差异。
- 必备材料包括：完整原始请求截图或记录、完整原始响应或缓存截图、动作前后的对照证据、账号角色和步骤说明、刷新或退出后的持久性对照。
- 展示密码时保留完整原始值，确保能直接证明一致性并供后续 Agent 复用。
- 若需要说明“可还原”或“可解码”，展示完整原始秘密值和还原/解码结果；仍禁止无关的批量数据获取。
- 不采集、不展示其他真实用户口令，不做批量枚举，不为报告增加不必要的高影响验证动作。

## 风险定级思路

- 高危：
- 服务端响应、列表、导出、缓存中直接出现原始口令或等效可复用秘密，且可造成账号接管或横向影响。
- 暴露范围不止本人，可被管理员、客服、运营或其他授权角色批量查看，或同类接口多处稳定复现。
- 中危：
- 本人或受限角色可在特定接口中取回原始口令，影响面有限但口令暴露事实明确。
- 客户端或浏览器持久化缓存了原始口令，刷新、退出或重启后仍保留，具备再次读取风险。
- 明文传输处于弱保护链路，存在代理、日志、中间件等可接触面，但尚未证明明文存储。
- 低危：
- 仅观察到“前端未 hash”或请求侧明文提交，且有 TLS 保护、无返回、无缓存、无存储侧证据。
- 暴露仅为低价值测试链路或单点历史兼容实现，且缺少复用、持久化或扩大影响的证据。
- 升级因素：
- 跨角色可见、批量列表或导出、退出后仍可取回、多个接口复用同一返回模型、口令可用于关联系统复用。
- 降级因素：
- 实际为占位符、掩码值、不可逆摘要、一次性值，或只是客户端原始提交在受保护链路中的正常表现。

## 修复与复测

- 修复方向
- 服务端禁止返回密码及等效秘密字段，所有用户相关响应采用字段白名单输出，而不是直接回传数据库对象。
- 密码仅在服务端以带唯一盐值的强口令哈希方式存储，不得明文存储、可逆加密存储或以简单编码代替保护。
- 禁止记住密码功能在客户端保存原始口令，改为服务端控制的短期票据或安全会话方案。
- 同步清理日志、缓存、消息、审计、导出模板、调试接口、同步接口中可能遗留的密码字段。
- 不要把“前端先 hash 一次”当作主要修复手段；客户端处理只能作为兼容细节，不能替代服务端正确存储与输出控制。
- 复测步骤
- 沿原始漏洞路径重新执行登录、修改密码、查询详情、列表、重置、导出、记住密码等动作。
- 验证响应中不再出现密码字段，或字段被彻底移除/置空/掩码化，且不可还原为原始口令。
- 验证浏览器和客户端缓存中不再保留原始口令，退出、切换账号、重启后也不会残留。
- 验证修改后的新口令无法再被任何查询、详情、列表、导出接口取回，确保修复覆盖整条链路。

## 报告表达模板

- 漏洞标题
- 密码明文处理与返回
- 漏洞描述
- 在测试过程中，发现系统在 `<业务动作>` 链路中对密码字段处理不当。测试账号提交的临时口令标记在 `<请求位置/响应位置/缓存位置>` 中以明文或可还原形式出现，说明系统未遵循密码最小暴露原则。
- 风险说明
- 一旦上述数据被前端缓存、日志、中间件、代理或其他授权用户接触，可能导致账号接管、口令复用风险扩大及关联系统连带影响。若同类字段可在查询、列表、导出或多角色界面中稳定获取，风险应进一步上调。
- 证据概述
- 1. 使用测试账号在 `<动作>` 中设置或提交临时口令标记。
- 2. 在 `<接口/页面类型>` 的 `<字段位置>` 观察到与提交值一致或可还原的一致性片段。
- 3. 通过 `<对照条件>` 排除占位符、固定文案和非原始值回显。
- 4. 在 `<刷新/退出/切换账号>` 后确认 `<是否仍存在>`，据此判断影响范围与持久性。
- 修复建议
- 建议服务端停止返回任何密码或等效秘密字段，统一采用字段白名单输出；服务端使用强口令哈希算法加唯一盐值存储密码；同时排查缓存、日志、导出和账号管理相关接口，确保同类链路一并修复。
