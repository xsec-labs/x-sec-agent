# XSS跨站脚本测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：发现搜索回显、评论/富文本、消息通知、日志查看、文件名展示、预览组件、DOM 拼接、LLM 输出渲染等输入到输出路径。
- 触发信号：`reflected_input_detected`、`stored_input_surface_detected`、`rich_text_editor_detected`、`dom_sink_detected`、`unsafe_html_render_detected`、`ai_output_rendered_in_frontend`、`file_upload_name_reflected`。
- 测试前置环境：通常需要有可控输入和可观察输出位置；存储型验证只使用无害测试标记并可清理，不影响真实用户。
- 参考工件：`forms/actions`、`request_corpus`、`browser_screenshots`、`dom_sink_notes`、`test_marker`。
- 解锁输出：`xss_candidate_detected`、`cookie_security_impact_context`、`csrf_or_session_risk_context`、`llm_output_injection_validated`。
- 建议阻断（可低影响补齐时先补证再测）：无输入回显链路、无法创建/清理测试内容、页面输出已安全转义或 CSP/渲染环境无法执行且无可证明影响。

## 适用场景

- 适用于怀疑存在用户输入被浏览器当作 HTML、属性、脚本片段或前端模板内容解释的场景。
- 适用于搜索框、筛选参数、详情页回显、富文本编辑、消息通知、评论备注、资料配置、导入后展示、日志查看、后台审计、删除确认框、预览弹窗等入口。
- 适用于区分反射型、存储型、DOM 型和“提示框触发型”XSS；其中“提示框XSS”通常不是独立成因，而是前端将可控内容带入 `alert/confirm/prompt` 或自定义弹窗组件后的表现形式。
- 适用于渗透测试、漏洞复测、影响评估和报告撰写，不适用于高影响利用。

## 测试思想

- 先找“输入点”，再找“落点”，最后判断“浏览器如何解释这段数据”。XSS 的核心不是字符串里是否有特殊字符，而是数据是否进入了危险渲染上下文。
- 先证明“可控内容到达了页面或脚本上下文”，再证明“浏览器发生了解析或执行”。不要一上来追求强刺激验证；如果验证需要写入业务数据，先确认这条测试数据可删除、删除入口可用，并在测试结束后清理。
- 始终构造对照组：正常文本、带编码字符的文本、带上下文边界特征的测试文本、最小化执行指示。没有对照组，就很难判断是过滤、转义、富文本白名单还是浏览器插件干扰。
- 最小化验证优先级应为：页面回显差异 > DOM/源码差异 > 渲染痕迹 > 受控提示标识。除非确有必要，不读取敏感对象、不外联、不做持久破坏。
- 影响判断要围绕四件事：谁能写入、谁会看到、是否持久、是否进入高权限人员或多人共享视图。

## 参考方法（目标与常见路径，不是必须顺序）

下面是达成测试目标的常见路径，不是必须照做的脚本：可以合并步骤、调整顺序、跳过已经确认过的部分，或者换成你判断更合适的方法，只要仍能支撑下面的判断点和证据要求。

1. 明确测试账号、可接受影响级别，优先选择隔离测试数据和专用低权限账号。
2. 若测试需要新增、导入、提交或保存数据，先确认该数据具备可识别标记、可删除路径和删除权限；无法确认可清理时，不要向业务环境写入持久测试内容。
3. 枚举入口点：查询参数、表单字段、富文本内容、模板变量、上传后文件名或描述、消息主题、备注、昵称、日志来源字段、导入数据字段。
4. 标记回显链路：提交后立即回显的是反射候选；保存后在列表、详情、预览、通知、审批、日志或弹窗中再次出现的是存储候选；仅在前端交互、路由切换、预览组件或脚本拼接时出现的是 DOM 候选。
5. 为每个入口构造对照组，至少保留一组纯文本基线和一组上下文探针，比较响应正文、页面元素、浏览器开发者工具中的 DOM 变化。
6. 判断回显上下文是文本节点、HTML 片段、属性值、URL 位置、脚本字符串还是前端弹窗参数。不同上下文决定后续验证方式和修复建议。
7. 若内容只被当作普通文本显示，记录为已编码或已转义迹象，不急于升级结论；若出现标签闭合、属性逃逸、节点新增、弹窗文本异常、预览组件解析等现象，再进入下一步。
8. 进行最小化验证时，优先使用不会访问 Cookie、Token、本地存储或外部网络的受控测试标识，仅证明“浏览器已执行可控片段”。
9. 对存储型链路，必须复核二次触发点：创建者自查看、其他普通用户查看、后台管理员查看、消息/通知触发、导出/打印/预览触发。
10. 对反射型链路，必须确认是否需要用户点击、是否只在错误页或搜索页触发、是否受浏览器安全策略或模板转义影响。
11. 对 DOM 型链路，重点看前端是否从 `location`、哈希、查询串、接口响应或富文本配置中取值后，使用危险 API 直接拼进页面或弹窗。
12. 对提示框型链路，重点确认是原生提示框、自定义模态框还是删除确认框；其本质仍是前端将未转义数据带入危险渲染或执行位置。
13. 记录影响面时，不要只停留在“能弹框”，而要说明该数据能否进入共享页面、后台页面、审批流、运营位或高权限会话。
14. 测试完成后，删除新增的测试记录、导入数据、备注、通知、文件描述等可控内容；如确实无法删除，应记录原因、残留位置和通知处置动作。

## 关键判断点

- 反射型判断：输入是否在同一次请求响应中出现；是否仅通过 URL、查询串、错误信息、搜索结果、跳转页或模板变量回显。
- 存储型判断：输入是否先入库，再在后续页面、通知、日志、后台管理、导出预览或其他用户视图中出现。
- DOM 型判断：服务端响应可能本身安全，但前端脚本在运行时把可控数据放入危险 DOM API、组件属性或前端模板。
- 提示框型判断：如果触发点是删除确认、系统消息、审批提示或自定义弹层，要继续追溯其数据源和渲染方式，不要把“弹框”误当作漏洞成因本身。
- 上下文判断：同样是回显，文本节点、属性值、URL 协议位、脚本字符串、富文本容器的风险和验证方式不同。
- 交互条件判断：无需交互、一次点击、二次查看、管理员查看、定时任务推送，风险差异很大。
- 误报排除：仅出现 HTML 文本原样展示、浏览器插件注入、自定义调试脚本干扰、截图无法对应真实请求链路，都不能直接下结论。
- 修复有效性判断：仅加响应头、仅依赖 HttpOnly、仅在单页做过滤，通常不足以证明已根治。

## 证据链要求

- 保留入口证据：测试账号角色、操作步骤、输入字段名或参数名、提交动作、时间点，以及测试数据的唯一标识，便于后续定位和删除。
- 保留传输证据：关键请求与响应的截断内容，重点保留字段名、参数位置、编码形态、是否入库或回显。
- 保留落点证据：页面源码、DOM 结构、预览区域、提示框文本、列表页或详情页中的实际显示位置。
- 保留对照证据：同一位置下，基线文本与测试文本的差异，证明不是普通富文本能力或浏览器渲染误差。
- 保留触发证据：如需最小化执行证明，应说明触发条件、触发动作和受控结果，避免展示任何敏感读取或外联行为。
- 保留影响证据：是否跨账号可见、是否进入后台、是否影响管理员或多人共享页面、是否可重复触发。
- 保留清理证据：对写入型或存储型测试数据，应记录删除路径、删除时间和清理结果，避免将测试内容长期遗留在业务环境。

## 风险定级思路

- 高风险通常满足以下一项或多项：可持久存储、影响后台或高权限角色、默认可见或高频访问、可进入共享页面或业务流程关键节点。
- 中风险通常表现为：需要构造特定链接或特定交互、影响面主要限于普通用户视图、需要额外步骤才能触发，但执行链路明确成立。
- 低风险或待定通常表现为：只能证明异常渲染，尚不能证明可执行；或仅在受限、不可共享、低价值的自查看场景出现，且存在明显缓解条件。
- 定级时不要只看“是否弹框”，更要看写入门槛、触发门槛、受害角色、持久性、传播面、修复成本和现有防护是否真的生效。
- `HttpOnly`、`CSP`、受限角色、低频页面可以影响危害表达，但一般不改变“存在 XSS 成因”这一判断。

## 修复与复测

- 修复优先级应是“按上下文输出编码”而不是笼统过滤；文本节点、属性、URL、脚本字符串、富文本容器要分别处理。
- 富文本场景应采用明确白名单清洗，并同时校验服务端入库前和前端展示前两个环节，避免只修一侧。
- 前端代码应避免将不可信数据直接写入危险 DOM API、模板拼接、弹窗组件参数或预览容器。
- 提示框型场景应对传入文案统一转义，禁止把不可信输入直接拼接到可执行上下文。
- `HttpOnly`、`SameSite`、CSP 等属于减缓影响或纵深防御，不能替代根因修复。
- 复测时至少覆盖：原始入口、同类入口、列表页、详情页、预览页、后台页、消息提示、日志页、导出/打印等二次展示位置。
- 复测时既要验证“危险内容不再执行”，也要验证“正常业务文本仍可正确显示”，避免以过度过滤换取表面通过。
- 对存储型问题，复测前先确认历史脏数据是否被清理；否则旧数据仍可能在新版本页面中触发残留风险。复测产生的新测试数据也要在验证完成后删除，并在复测结论中说明清理情况。

## 报告表达模板

- 漏洞标题：`XSS跨站脚本`
- 漏洞类型：`反射型 / 存储型 / DOM型 / 提示框触发型`
- 风险等级：`<高/中/低/待定>`
- 发现位置：`<模块/页面/功能点>`
- 触发条件：`攻击者可在 <入口字段> 写入受控内容，该内容会在 <查看位置> 被浏览器按 <上下文类型> 解释。`
- 验证方式：`在低影响前提下，使用受控测试标识构造对照组，确认内容从 <输入点> 到 <落点> 的传播链路，并观察到解析或执行迹象。`
- 影响说明：`该问题可影响 <受害角色>，触发方式为 <直接访问/二次查看/预览/提示框/后台查看>，具备 <持久性/共享性/高权限可见性>。`
- 证据摘要：`已保留关键请求响应、页面/DOM差异、触发截图、账号角色关系和时间点，可支撑漏洞结论。`
- 修复建议：`按输出上下文实施编码或白名单清洗，消除危险 DOM 写入点，并对同类展示位进行统一治理。`
- 复测结论：`按原路径与同类路径复测后，确认受控内容不再被解析执行，正常业务展示未受破坏。`
