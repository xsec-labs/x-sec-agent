# 会话与Token失效缺陷测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：目标存在登录、退出、改密、注销、禁用、刷新令牌、rememberMe 或 JWT 生命周期，需要验证旧 Cookie/Session/Token 是否失效。
- 触发信号：`authenticated_session_obtained`、`logout_flow_detected`、`password_change_flow_detected`、`refresh_token_detected`、`remember_me_detected`、`jwt_token_detected`。
- 测试前置环境：通常需要有有效测试账号、旧令牌快照和低影响受保护接口；触发失效事件建议可恢复且不影响真实用户。
- 参考工件：`browser_state`、`old_token_snapshot`、`request_corpus`、`protected_endpoint_baseline`、`invalidation_event_log`。
- 解锁输出：`stale_token_reuse_detected`、`jwt_security_review_needed`、`browser_storage_review_needed`、`access_control_review_needed`。
- 建议阻断（可低影响补齐时先补证再测）：无登录态、无生命周期事件、无法保存旧凭据、改密/注销会影响后续测试。

## 适用场景

- 目标系统存在登录态，认证凭据以 Cookie、Session ID、JWT、Access Token、Refresh Token 或类似字段承载。
- 业务流程包含退出登录、修改密码、注销账号、账号禁用、超时过期、单点退出、切换账号或重新登录。
- 测试中发现“前端显示已退出”但旧凭据疑似仍可访问受保护资源。
- 测试中发现旧 Token 在重新登录、切换终端或等待一段时间后仍可调用接口。
- 需要判断这是实际的服务端失效缺陷，还是仅前端清理、本地缓存变化、文案误导或策略允许的并发会话。

## 测试思想

- 把这类问题视为“认证生命周期控制”缺陷，而不是单纯的前端退出按钮缺陷。核心判断标准是服务端是否真正拒绝旧凭据。
- 先固定一个最小受保护请求作为验证载体，再围绕生命周期事件做前后对照，避免因为接口差异引入误判。
- 优先验证显式失效事件：
  退出登录、修改密码、注销账号、账号禁用、管理端踢下线。
- 再验证隐式失效事件：
  空闲超时、绝对过期、刷新令牌轮换、重新登录后旧凭据淘汰。
- 不要因为 Cookie 值变化、页面跳回登录页或本地存储被清空就下结论。必须以旧凭据是否还能访问受保护资源为准。
- 对 JWT 或无状态 Token 保持警惕：如果设计要求退出即失效，但服务端只做客户端删除、不做吊销或版本校验，也属于真实风险。

## 操作流程

1. 明确认证载体。
   识别请求头、Cookie、Local Storage、Session Storage 或隐藏字段中承载登录态的关键字段，记录其名称、出现位置和更新时机。
2. 选定最小验证请求。
   选择一个低影响、稳定、可重复的受保护接口作为样本，例如“读取当前用户资料”或“查询当前账户可见列表”，避免直接选删除、修改、审批类动作。
3. 建立登录基线。
   使用正常登录态调用该受保护接口，确认返回成功，并保存“登录成功请求”“受保护请求”“对应响应”的基线证据。
4. 抽取旧凭据。
   在生命周期事件发生前，单独保存一份旧 Cookie 或旧 Token，用于后续回放；不要混用后续新登录产生的新凭据。
5. 触发失效事件。
   在低影响前提下分别测试退出登录、修改密码、重新登录、等待超时、注销或禁用等事件；一次只改变一个条件，保证因果清晰。
6. 回放旧凭据。
   对同一个受保护请求进行最小化复测，替换为旧凭据，观察服务端是否拒绝；必要时同时测试旧 Access Token 与旧 Refresh Token。
7. 建立对照组。
   保留三组结果：
   旧凭据请求、当前新凭据请求、无凭据请求。
8. 缩小影响面验证。
   如果旧凭据仍有效，再抽样验证 2 到 3 类接口：
   只读个人信息、业务列表查询、单个低影响操作。
9. 复核是否为策略差异。
   若系统声明支持多端同时在线，需要区分“重新登录后旧 Token 仍有效”是否符合策略；但显式退出、修改密码、账号禁用后仍有效，通常不能视为正常。
10. 固化证据链。
    记录时间点、账号、触发事件、旧新凭据对应关系、关键响应差异和服务端返回码，为报告和复测准备可复现材料。

## 关键判断点

- 退出成功响应不等于会话失效。判断依据应是旧凭据访问受保护资源时是否被拒绝。
- 只删除前端 Cookie 或 Local Storage，不代表服务端已销毁会话、加入黑名单或提升 Token 版本。
- 如果旧凭据在退出后仍返回 200、仍能读取当前账户数据、仍可执行低影响业务动作，可判定为有效缺陷。
- 如果旧凭据仅访问公开资源成功，或服务端明确返回未认证、会话过期、签名失效，则不应判为该漏洞。
- 如果旧凭据在极短时间内因网关缓存、并发竞争出现一次成功，需要重复一次相同请求确认，避免把瞬时一致性问题直接定性。
- 如果仅发现“Cookie 无 Expires/Max-Age”或“Token 看起来很长”而未证明失效控制缺失，不足以形成漏洞结论。
- 如果修改密码、注销账号、账号禁用后旧凭据仍有效，风险通常高于单纯退出按钮无效，因为说明关键账户状态变更没有联动认证失效。
- 如果旧 Refresh Token 仍可换取新 Access Token，说明问题不只在访问控制，还涉及令牌轮换与吊销链路不完整。

## 证据链要求

- 保留登录成功时的认证建立证据，所有敏感字段使用捕获到的完整原始值，包括旧 token 和 session Cookie，不使用占位符或打码。
- 保留同一个受保护接口在三种状态下的请求与响应：
  正常登录、新状态、旧凭据回放。
- 保留生命周期事件证据：
  退出成功提示、修改密码成功提示、注销完成提示、超时等待时间点或管理端禁用动作。
- 保留关键差异字段：
  HTTP 状态码、业务状态码、响应体中的用户标识、是否仍返回敏感数据、是否仍允许业务操作。
- 保留时间线：
  登录时间、触发失效事件时间、旧凭据回放时间、再次验证时间。
- 保留账号关系说明：
  测试账号权限级别、是否同账号重登、是否跨终端、是否存在管理端操作。
- 截图只保留必要字段，避免暴露真实单位名、真实地址、真实手机号、真实证件号、完整 Token 或完整 Cookie。

## 风险定级思路

- 低风险倾向：
  旧凭据仅在极短时间窗口内可访问低敏只读信息，且系统有明确短期缓冲机制，无法稳定复现。
- 中风险倾向：
  退出登录或会话超时后，旧凭据仍可稳定访问受保护接口，但影响主要限于当前普通用户数据读取或一般业务查询。
- 高风险倾向：
  修改密码、注销账号、账号禁用后旧凭据仍长期有效；或旧凭据可访问高敏数据、管理功能、跨角色能力；或旧 Refresh Token 可持续换发新 Token。
- 提升定级的因素：
  无服务端吊销、有效期过长、支持跨终端复用、可稳定复现、覆盖多个接口、涉及敏感个人信息或关键业务操作。
- 降低定级的因素：
  仅前端假退出但后端实际已拒绝；仅公开接口可访问；必须依赖异常竞态且不可稳定重现；影响范围被严格限制。

## 修复与复测

- 修复方向应落在服务端，不要只依赖前端删除本地凭据。
- 对有状态会话：
  退出、密码修改、注销、禁用后立即销毁服务端会话，并确保网关、应用层和单点登录层状态同步失效。
- 对无状态 Token：
  引入 Token 黑名单、版本号、会话版本戳或服务端会话绑定；关键事件发生后拒绝旧版本 Token。
- 对 Refresh Token：
  实施单独吊销、轮换和复用检测，避免旧 Refresh Token 在退出后继续换发新令牌。
- 对过期策略：
  同时设置合理的空闲超时和绝对过期，避免“永不过期”或仅客户端倒计时。
- 复测时不要只测一个接口。
  至少覆盖退出、修改密码、重新登录后旧凭据、超时后旧凭据四类路径，并抽样验证多个受保护接口。
- 复测通过标准：
  旧 Cookie、旧 Session、旧 Access Token、旧 Refresh Token 在对应失效事件后均被服务端拒绝，且无法借由刷新、重放或切换入口恢复访问。

## 报告表达模板

- 标题：
  会话与Token失效缺陷
- 漏洞概述：
  在测试中，系统在 `<失效事件>` 发生后未对旧认证凭据执行有效吊销，导致 `<old-token-or-cookie>` 仍可访问 `<protected-api>` 对应的受保护资源，说明登录态生命周期控制不足。
- 复现摘要：
  使用测试账号建立正常登录态后，选取低影响受保护接口作为验证对象；在触发 `<logout/password-change/account-disable/timeout>` 后，回放事件前保存的旧凭据，请求仍返回有效业务数据或成功状态；对照无凭据请求则被拒绝，证明问题存在于旧凭据未失效，而非接口匿名开放。
- 影响说明：
  攻击者一旦获取历史会话标识或令牌，在用户主动退出或关键账户状态变更后，仍可能继续冒用原身份访问系统，具体影响取决于该凭据可访问的数据范围和业务能力。
- 修复建议：
  建议在服务端建立统一的会话失效机制，对退出登录、修改密码、注销账号、账号禁用、超时过期等事件执行即时吊销，并同步覆盖 Access Token、Refresh Token 与相关会话缓存。
- 复测建议：
  修复后应按相同时间线复测旧凭据回放，并覆盖多个受保护接口与多种失效事件，确认不存在“个别接口已拦截但其余接口仍可用”的残留问题。
