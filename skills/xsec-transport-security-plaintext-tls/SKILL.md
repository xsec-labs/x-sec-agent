# 明文传输与TLS弱配置测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：目标存在 HTTP 明文入口、登录/敏感 API 非 HTTPS、HTTPS 未强制、混合内容、弱 TLS 协议/套件或证书问题。
- 触发信号：`http_scheme_detected`、`login_over_http_detected`、`sensitive_api_over_http_detected`、`tls_weakness_detected`、`mixed_content_detected`、`secure_cookie_missing`。
- 测试前置环境：通常需要有目标 URL、传输层响应和必要的 TLS/证书观测；验证不需要登录真实敏感账号。
- 参考工件：`scout_summary`、`request_corpus`、`tls_scan_summary`、`response_headers`。
- 解锁输出：`password_plaintext_transport_candidate`、`cookie_secure_missing`、`session_risk_context`。
- 建议阻断（可低影响补齐时先补证再测）：所有入口强制 HTTPS 且 TLS 基线正常、明文只来自本地代理/测试环境或证书问题不属于目标域。

## 适用场景

- 目标存在 Web、App、API、C/S 客户端、反向代理或数据库连接等多段通信链路，需要判断传输层是否保护了敏感数据。
- 已发现登录、注册、找回密码、短信验证、单点登录、患者或用户资料查询、报表下载、内部客户端访问等入口，需要确认是否仍经 HTTP 或弱 TLS 传输。
- 已知站点支持 HTTPS，但怀疑仍保留 HTTP 可达入口、弱协议版本、弱加密套件、证书校验不足或回退配置问题。
- 需要做渗透测试中的最小化验证、复测或报告撰写，而不是开展高影响利用。

## 测试思想

- 这类问题的核心不是“页面能否打开”，而是“敏感信息在传输途中是否可能被旁路获取、降级访问或中间篡改”。
- 判断时要把链路拆开看：用户到前端、前端到接口、客户端到服务端、服务端到数据库，任何一段未加密都可能形成真实风险。
- 明文传输的判定重点在于是否能观察到可识别的敏感内容、认证要素、业务数据或可被直接利用的协议细节，而不是仅凭字段名猜测。
- TLS 弱配置的判定重点在于服务端是否允许不安全协议或弱参数协商成功，以及这些配置是否作用于真实业务入口，而不是只看“支持 HTTPS”。
- 全程坚持最小化验证：优先使用测试账号、测试数据、只读动作和单次请求，证明风险存在即可，不追求扩大影响。

## 参考方法（目标与常见路径，不是必须顺序）

下面是达成测试目标的常见路径，不是必须照做的脚本：可以合并步骤、调整顺序、跳过已经确认过的部分，或者换成你判断更合适的方法，只要仍能支撑下面的判断点和证据要求。

1. 信息收集
- 盘点对外与对内入口：`<target-url>`、移动端接口、下载地址、回调地址、客户端配置、数据库或中间件连接信息。
- 识别敏感操作：登录、换绑、查询详情、导出、短信发送、令牌刷新、客户端自动登录、SQL 查询或同步任务。
- 记录协议与端口现状：是否同时开放 HTTP/HTTPS，是否存在非标准 TLS 端口，是否有仅内网可见但经共享网络传输的链路。

2. 构造对照组
- 对同一路径建立 HTTP 与 HTTPS 对照，观察是否自动跳转、是否仍返回业务内容、是否允许继续提交敏感参数。
- 对同一服务建立“强协议”与“弱协议”对照，确认旧版本 TLS 是否仍能协商成功，确认弱配置是否只存在于边缘端口还是主业务入口。
- 对同一业务动作建立“含敏感字段”与“不含敏感字段”对照，区分普通页面访问与真实敏感数据暴露。

3. 最小化验证
- 使用测试账号或无害测试值触发一次完整请求，确认认证字段、会话标识、个人信息字段或关键业务参数是否可在链路中直接识别。
- 如果是 C/S 或数据库链路，只验证是否能看到明文 SQL、账号标识、业务主键或查询结果片段，不做写入、删改或批量抓取。
- 如果是 TLS 问题，只验证弱协议、弱套件或不安全回退是否被接受，不做高并发压力或异常协商试探。

4. 影响面扩展
- 横向检查同域名下其他认证入口、子系统、移动端接口、文件下载接口、内部客户端配置，确认问题是单点还是共性配置缺陷。
- 纵向检查入口之后的后端链路：前端已上 HTTPS 不代表服务端到数据库、客户端到中间件也已加密。
- 复用同一判断框架检查测试、预发、正式、专网入口，但仅保留最低必要的样本证据。

5. 留证
- 保留能够说明“协议、路径、参数类型、返回结果、时间点、账号角色、是否协商成功”的最小证据集合。
- 原始敏感内容保存到受控证据目录；共享发现、截图展示、报告和委派使用最少必要的原始摘录（xSec 不做自动脱敏）与证据引用，截断只因体积限制并明确标记。
- 对复测场景保留前后对照证据，证明控制点是否真正生效，而不是只改了展示层。

6. 修复复测
- 复测时按原入口、原路径、原端口、原客户端版本重新验证，避免只测首页或只测单一接口。
- 同时确认“旧问题消失”和“替代控制生效”：HTTP 是否被拒绝或跳转、TLS 弱版本是否关闭、内部链路是否已不可读。

## 关键判断点

- 只有 HTTP 可访问静态首页，不涉及登录、会话、敏感查询或后续跳转到敏感操作时，通常不应直接等同于高危明文传输。
- 认证字段即使经过简单编码、可逆变换或弱摘要，只要整体链路仍为明文或可被中间篡改，仍应视为传输保护不足。
- 只看到字段名而看不到值，不足以证明高风险；看到凭据、令牌、个人数据、业务详情、SQL 语句或可复用标识时，证据更充分。
- HTTPS 已启用但 HTTP 仍可提交敏感请求、弱 TLS 仍可协商、证书校验可被绕过或客户端允许回退时，问题依旧成立。
- 内网链路不能天然视为安全；若客户端、服务端、数据库之间经过共享网络、终端众多或可被授权抓包，仍应纳入风险判断。
- 复测中若接口被移除、端口关闭或仅首页跳转，但其他旧入口仍保留同类问题，不应判定为完全修复。

## 证据链要求

- 入口证据：目标标识、协议、端口、业务动作、测试时间、测试账号角色或匿名态。
- 请求证据：方法、路径、完整请求头、参数位置、敏感字段类型和原始字段值；记录完整密码、令牌、Cookie 和个人信息。
- 响应证据：状态码、重定向行为、返回内容类型、关键业务提示，用于证明请求确实被服务端接收并处理。
- 抓包证据：能够直接说明明文可见、弱协议协商成功或链路未加密的关键截图或文本，不保留超出结论所需的大量报文。
- TLS 证据：支持的协议版本、弱套件或回退结果、证书链异常点、是否作用于真实业务端口。
- 复测证据：修复前后的同一路径对比，证明 HTTP 已失效或跳转、TLSv1.0/TLSv1.1 等旧版本已不可协商、客户端到数据库链路已无法识别明文内容。

## 风险定级思路

- 高危：明文传输了账号口令、会话标识、患者或用户敏感信息、核心业务数据，且攻击面位于外网、移动网络或大范围办公网络。
- 中危：未加密链路暴露了内部业务数据、SQL 语句、数据库访问细节、可复用标识，或 HTTP 入口仍可承载敏感操作，但影响面相对受限。
- 低危：主要表现为 TLS 旧版本、弱协议或配置遗留，强协议仍可用，且未直接观察到敏感数据明文传输；此时更偏配置缺陷或合规缺口。
- 降级判断：仅有非敏感静态内容走 HTTP、可立即强制跳转到 HTTPS、无敏感参数提交且无其他可见链路暴露时，可结合业务重要性适当降级。
- 升级判断：若同类问题横跨多个入口、覆盖登录与数据查询、同时存在 TLS 弱配置与明文链路，说明是体系化缺陷，应提高风险评价。

## 修复与复测

- 修复方向应覆盖全链路，而不是只改前台页面：强制 HTTPS、关闭 HTTP 敏感入口、启用 HSTS、禁用 TLSv1.0/TLSv1.1 和弱套件、校验证书、加密客户端到服务端及数据库连接。
- 对移动端或 C/S 客户端，要同步检查硬编码地址、回退逻辑、证书校验策略、数据库驱动加密参数和代理转发配置。
- 对内部系统，要确认中间件、负载均衡、应用服务器、数据库网关的加密策略一致，避免边界 HTTPS 已修复而后端链路仍明文。
- 复测步骤应与初测保持可比性：同一入口、同一动作、同一角色、同一抓包位置。
- 复测通过的最低标准：
- HTTP 访问敏感路径时被重定向、拒绝或不再返回业务内容。
- 旧 TLS 版本和弱协商方式不再成功。
- 抓包中不再出现可识别的明文凭据、敏感字段、SQL 语句或业务详情。
- 相关子系统与历史入口已同步检查，避免“修一个接口，漏一批接口”。

## 报告表达模板

```markdown
漏洞概述：
经测试，发现 `<system-or-module>` 在 `<business-action>` 过程中存在传输层保护不足问题。具体表现为 `<http-plaintext-or-weak-tls>`，导致 `<credential-or-data-type>` 在链路中存在被窃听、篡改或降级访问的风险。

验证过程：
测试在测试账号/测试数据条件下，对 `<entry-point>` 进行最小化验证。结果显示，请求经 `<protocol-or-link>` 传输时，能够观察到 `<raw-sensitive-elements>`（填写捕获到的原始值），或服务端仍接受 `<weak-tls-version-or-weak-negotiation>` 协商。

影响分析：
该问题说明系统未对 `<affected-link>` 实施充分的传输加密控制。攻击者一旦位于可观测链路中，可能获取或干扰 `<data-category>`，影响认证安全、数据保密性与通信完整性。若同类配置在多个入口复用，实际影响面将进一步扩大。

修复建议：
建议从协议强制、弱配置关闭、证书校验和后端链路加密四个层面统一整改，并在整改后对历史入口、客户端版本及关联子系统开展同范围复测。
```

- 若结论偏向明文传输，突出“哪些敏感元素可被直接观察到”。
- 若结论偏向 TLS 弱配置，突出“哪些旧版本或弱参数仍能协商成功，以及它们对应的真实业务入口”。
- 若问题出现在内部客户端或数据库链路，明确“影响的是哪一段链路”，避免让读者误以为只有 Web 前端存在风险。
