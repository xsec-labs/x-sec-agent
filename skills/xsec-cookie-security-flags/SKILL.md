# Cookie安全属性缺失测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：目标下发 Cookie，尤其是登录态、SSO、后台、刷新令牌、验证码或 rememberMe Cookie，需要检查 HttpOnly/Secure/SameSite/Path/Domain。
- 触发信号：`set_cookie_observed`、`session_cookie_detected`、`auth_cookie_detected`、`remember_me_detected`、`sso_callback_detected`。
- 测试前置环境：通常需要捕获到 Set-Cookie 响应；登录态 Cookie 检查需要可登录或可访问会话下发入口。
- 参考工件：`response_headers`、`request_corpus`、`cookie_snapshot`、`browser_state`。
- 解锁输出：`csrf_review_needed`、`session_cookie_weakness_detected`、`transport_security_review_needed`、`browser_storage_review_needed`。
- 建议阻断（可低影响补齐时先补证再测）：目标未下发 Cookie、Cookie 来自第三方非目标域或代理/测试工具噪声。

## 适用场景

- 目标系统在登录、单点登录、会话续期、退出登录、找回密码、敏感操作等流程中返回 Cookie。
- 抓包、代理记录或截图显示 `Set-Cookie` 中缺少 `HttpOnly`、`Secure`、`SameSite`，或仅部分 Cookie 配置了安全属性。
- 需要区分“真实风险”“基线缺口”“业务例外”三类情况，避免机械报洞。
- 需要对修复版本做一致性复测，确认不是只修复了单个接口、单个环境或单个登录入口。

## 测试思想

- 核心目标不是证明“已经能接管会话”，而是判断安全关键 Cookie 是否按用途具备最小必要保护。
- 先识别 Cookie 的业务用途，再判断应配置哪些属性；不要把所有 Cookie 一律按高风险处理。
- 优先做最小化验证，以响应头和下发链路为主，证明“谁发了什么 Cookie、缺了什么属性、影响哪类保护”即可。
- 始终建立对照组，至少覆盖未登录与已登录、首次登录与续期刷新、主站与子系统、修复前与修复后。
- 风险判断依赖上下文：认证 Cookie、会话 Cookie、前端可读业务 Cookie、统计 Cookie 的安全要求不同。

## 参考方法（目标与常见路径，不是必须顺序）

下面是达成测试目标的常见路径，不是必须照做的脚本：可以合并步骤、调整顺序、跳过已经确认过的部分，或者换成你判断更合适的方法，只要仍能支撑下面的判断点和证据要求。

1. 识别入口
- 在测试环境中优先检查登录、SSO 回调、验证码校验、会话刷新、退出登录、后台入口、个人中心等易下发 Cookie 的响应。
- 记录每次响应中完整原始 `Set-Cookie`，包括 Cookie 名称、值、路径、域和属性组合。

2. 建立 Cookie 台账
- 对每个 Cookie 标注用途：认证态、会话标识、偏好设置、跟踪统计、前端脚本可读数据。
- 标注下发条件：未登录下发、登录后下发、特定角色下发、特定子域下发。
- 标注已有属性：`HttpOnly`、`Secure`、`SameSite`、`Domain`、`Path`、`Max-Age/Expires`。

3. 构造对照组
- 同一功能在不同角色、不同入口、不同子域重复抓取，确认缺失是否具有系统性。
- 对同名 Cookie 比较不同响应；某个接口设置了安全属性，不代表所有下发点都已修复。
- 若业务声称“仅 HTTPS 可访问”，仍要确认关键 Cookie 是否显式带 `Secure`，不要把传输约束等同于 Cookie 配置合规。

4. 最小化验证
- 以报文验证为主，证明安全关键 Cookie 在下发时缺少必要属性。
- 对 `HttpOnly`，只需确认认证或会话 Cookie 缺少脚本访问限制，不需要额外构造脚本利用。
- 对 `Secure`，只需确认关键 Cookie 未显式声明仅通过 HTTPS 传输；是否进一步上调风险，再看是否存在测试范围内的 HTTP 暴露面。
- 对 `SameSite`，只需确认跨站携带限制未声明或配置不当；不要在未验证配套条件时直接下结论为“可成功 CSRF”。

5. 影响面扩展
- 检查同一应用的主域、子域、认证网关、反向代理层、统一登录层是否复用同类 Cookie 策略。
- 检查是否仅主登录接口已修复，而刷新令牌、注销后重登、记住我、移动端 H5、后台管理入口仍遗漏。
- 若一个响应同时设置多个 Cookie，应分别判断，不要因为其中一个安全而忽略其他关键 Cookie。

6. 留证与归档
- 为每个结论保留最少一组“请求 + 响应头 + 判断说明”证据。
- 对复测场景保留同路径、同账号、同阶段的前后对比，避免因流程差异导致误判。

## 关键判断点

- `HttpOnly` 是否必须：
- 会话标识、认证票据、长效登录令牌通常应设置 `HttpOnly`。
- 明确需要前端脚本读取的非敏感业务 Cookie 可例外，但需要说明业务理由，不能默认合理。

- `Secure` 是否必须：
- 认证态或会话态 Cookie 原则上应设置 `Secure`。
- 若仅是统计类 Cookie，风险可保守描述；若存在 HTTP 入口、明文跳转或代理链路不一致，风险应上调。

- `SameSite` 是否必须：
- 依赖 Cookie 鉴权的敏感操作应优先考虑 `SameSite` 控制。
- 若业务必须跨站单点登录或跨域嵌入，应确认是否采用 `SameSite=None; Secure` 的合规组合。
- 浏览器对未设置 `SameSite` 的默认行为可能不同，报告中更适合写成“缺少显式声明带来兼容性与防护不确定性”，不要脱离上下文夸大。

- 是否属于真实问题：
- 关键 Cookie 缺少必要属性，且不存在明确业务例外说明，通常可成立。
- 仅普通偏好 Cookie 缺失，且不承载敏感状态时，更适合按低风险或基线问题表述。

- 是否是组合风险：
- 缺少 `HttpOnly` 往往会放大脚本注入类问题影响。
- 缺少 `SameSite` 往往会放大跨站请求伪造风险面。
- 缺少 `Secure` 往往会放大明文传输或链路降级风险。
- 若组合前提未在本次测试中验证，不要把链式利用写成既成事实。

## 证据链要求

- 必须有响应侧证据：
- 完整原始 `Set-Cookie` 头。
- Cookie 名称、路径、域、是否认证态、缺失的具体属性。

- 必须有上下文说明：
- 触发该 Cookie 的功能点。
- 是否登录后才出现。
- 使用的账号角色和测试时间点。

- 必须有判断依据：
- 为什么该 Cookie 被认定为会话或认证相关。
- 为什么某个属性在该场景下应当存在。
- 是否存在补偿控制，以及补偿控制不能完全替代的原因。

- 复测时必须有对比证据：
- 同一路径、同一流程下修复前后的属性差异。
- 若系统会在多个接口重复下发同名 Cookie，至少覆盖一个主流程和一个易遗漏流程。

## 风险定级思路

- 默认从低危或中低风险起评，避免把所有属性缺失一律上升为高危。
- 综合判断时重点看四个维度：Cookie 是否承载认证或会话、缺失是单项还是多项、是否存在可确认的放大条件、是否有明确补偿控制。
- 倾向低危的常见情形：
- 非敏感 Cookie。
- 仅体现基线不规范，未见可验证的放大条件。

- 可上调至中危的常见情形：
- 会话或认证 Cookie 缺少 `Secure`，且存在可确认的明文传输面。
- 会话或认证 Cookie 缺少 `SameSite`，且敏感操作缺少独立 CSRF 防护。
- 会话或认证 Cookie 缺少 `HttpOnly`，且同系统已确认存在脚本注入面。

- 不要仅凭“理论上可被利用”直接定高危，除非已有充分链路证据支撑。

## 修复与复测

- 修复建议
- 为会话和认证相关 Cookie 补齐 `HttpOnly`、`Secure`，并按业务需要显式设置 `SameSite`。
- 在认证网关、应用框架或中间件层统一配置，避免只修单个控制器或单个接口。
- 对必须前端读取的 Cookie 单独梳理，避免因批量加 `HttpOnly` 造成业务回归。
- 对跨站场景采用可解释的白名单与 `SameSite=None; Secure` 组合，不要以兼容性为由完全放弃限制。

- 复测步骤
1. 复测首次登录、会话刷新、退出后重登、敏感操作前后等多个下发点。
2. 复测不同角色、不同子域、不同网关入口，确认策略一致。
3. 对同名 Cookie 检查每一次 `Set-Cookie` 是否都带齐属性，避免“首次正确、续期遗漏”。
4. 若修复涉及 `SameSite`，确认关键业务流程未因跨站限制异常失效。
5. 仅在低影响前提下验证功能可用性，不做额外攻击性验证。

## 报告表达模板

- 问题概述
- “系统在 `<功能点>` 下发的关键 Cookie 未显式设置 `<缺失属性>`，导致该 Cookie 的会话保护边界弱于推荐安全基线。”

- 判断依据
- "在测试中，使用 `<角色类型>` 访问 `<功能类型>` 后，响应头返回原始 `Set-Cookie`。从 Cookie 用途及其与登录态的关联可判断其承载 `<会话/认证/跨站状态>` 功能，但未包含 `<属性名>`。"

- 影响描述
- “该问题通常作为会话保护薄弱项存在，会放大 `<明文传输风险/XSS 后 Cookie 可读风险/跨站请求携带风险>`。若缺少相应补偿控制，可能进一步影响认证态安全。”

- 修复建议
- “建议在统一 Cookie 下发链路中按用途补齐安全属性，并对所有同名 Cookie 的下发点做一致性治理。”

- 复测结论
- “复测应以相同业务流程重新抓取 `Set-Cookie` 为准。仅当主流程、续期流程及相关子系统均返回正确属性组合时，方可判定修复完成。”
