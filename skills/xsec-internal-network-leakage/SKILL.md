# 内网地址与网络信息泄露测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：响应、前端资源、错误页、配置、日志片段中出现内网 IP、内部主机名、内部端口、回源地址或拓扑线索。
- 触发信号：`passive_internal_ip_match`、`passive_internal_hostname_match`、`internal_port_detected`、`upstream_host_leak_detected`、`client_internal_url_detected`。
- 测试前置环境：通常需要有对外可见的泄露来源；只判断泄露价值，不主动扫描内网。
- 参考工件：`passive_findings`、`source_location`、`request_response_snippet`、`client_asset_snippet`。
- 解锁输出：`ssrf_candidate_context`、`middleware_management_candidate`、`version_info_candidate`、`vulnerability_chain_input`。
- 建议阻断（可低影响补齐时先补证再测）：仅为 127.0.0.1/测试代理地址、浏览器本机地址、无业务意义占位或非目标系统内容。

## 适用场景

- 目标系统的前端页面、静态资源、接口响应、调试信息、错误回显或配置片段中出现疑似内网地址、内部主机名、内部端口、服务别名、节点编号、回源链路描述。
- 测试人员已经在测试范围内观察到“对外可见内容包含内部网络线索”，需要判断其是否构成有效漏洞，以及应如何低影响留证。
- 需要对“IP 泄露”“内网 IP 泄露”“内网地址泄露”“网络拓扑线索泄露”等近义标题进行统一分析、复测和报告表达。
- 需要区分普通公开地址、代理地址、脱敏示意值与真实内部网络标识，避免把无效信息误判为漏洞。
- 需要在不主动探测内部网络的前提下，对泄露信息的稳定性、业务关联性、可利用辅助价值进行风险评估。

## 测试思想

- 把这类问题视为“可为后续攻击提供环境认知”的信息泄露，而不是把“出现一个地址字符串”直接等同于高风险。
- 优先回答三个问题：泄露内容是不是真的指向内部网络；外部用户是否可稳定获取；这些线索是否足以帮助定位关键资产或推断拓扑。
- 坚持最小化验证。目标是证明“内部网络信息被不必要地暴露给外部可见面”，而不是去连接、扫描或深入触达该内部地址。
- 必须做对照。正常流程与异常流程、登录前与登录后、低权限与高权限、主页面与静态资源、原始响应与前端渲染结果，都可能给出不同结论。
- 定级重点不在“有没有地址”，而在“地址是否真实、是否稳定、是否携带主机角色/端口/路径/调用关系、是否能明显降低攻击者侦察成本”。

## 操作流程

1. 信息收集
   - 浏览页面源码、前端打包文件、SourceMap、注释、调试输出、接口返回、错误页、控制台日志、网络面板和响应头。
   - 重点关注配置对象、即时通信/音视频配置、文件服务地址、回源服务名、网关转发标识、异常堆栈、上传下载回调地址等位置。
   - 记录泄露出现的载体类型：HTML 注释、JS 变量、JSON 字段、Header、报错信息、图片或 OCR 可见内容。

2. 构造对照组
   - 使用同一功能的正常请求与异常请求对比，判断泄露是否只在报错、回退、调试分支或边界输入下出现。
   - 使用匿名态、普通用户态、低权限业务账号等测试身份对比，判断泄露是否面向所有访问者还是仅特定角色可见。
   - 比较首屏页面、懒加载资源、历史缓存文件和移动端/H5 版本，判断泄露是否为单点现象还是构建链路普遍问题。

3. 最小化验证
   - 仅验证“外部响应中确实存在内部网络线索”，不主动对内部主机发起访问或枚举。
   - 对泄露值做语义归类：私有地址、内部域名、主机别名、端口、服务类型、环境标识、节点编号、内部路径。
   - 如需证明稳定性，可重复访问同一入口或同类入口，确认该信息并非一次性调试残留或偶发缓存。

4. 影响面扩展
   - 横向查看同模块其他接口、同域名其他页面、同套前端构建产物是否复用相同配置。
   - 观察同一泄露值是否同时伴随服务名、端口、网关标识、机房/环境标识、调用链字段，判断其是否能拼出更完整的拓扑线索。
   - 结合系统已知能力做辅助评估，例如是否存在服务端代请求、文件回源、内部代理、消息推送或调试入口，但不要越出测试范围和低影响边界。

5. 留证与整理
   - 固化请求时间、访问角色、请求路径、响应位置、原始字段名、完整原始泄露值、页面可见位置和复现步骤。
   - 原始敏感内容保存到受控证据目录；共享发现、截图展示、报告和委派使用最少必要的原始摘录（xSec 不做自动脱敏）与证据引用，截断只因体积限制并明确标记。
   - 明确写出“无需访问内部地址，仅凭外部响应即可观察到泄露”的结论，这一点直接影响报告可接受度。

## 内网IP有效性鉴别

检测到疑似内网地址时，**必须先完成本节所有判断**，确认为真实内网IP后方可作为漏洞依据。不得将任何"看起来像IP"的字符串直接录入报告。

### 第一步：地址范围核查

只有以下 RFC 标准私有地址范围才算私有内网地址：

| 范围 | CIDR | 典型示例 |
|------|------|---------|
| A 类私有 | 10.0.0.0/8 | 10.x.x.x |
| B 类私有 | 172.16.0.0/12 | 172.16.x.x ～ 172.31.x.x |
| C 类私有 | 192.168.0.0/16 | 192.168.x.x |
| 回环地址 | 127.0.0.0/8 | 127.x.x.x |
| 链路本地 | 169.254.0.0/16 | 169.254.x.x |
| 容器/K8s 常见 | 172.17.0.0/16、10.244.x.x 等 | 视具体编排方案而定 |

其他地址（如 1.2.3.4、8.8.8.8、198.x.x.x 等）属于公有地址，不在内网泄露的范畴内，应直接排除。

### 第二步：语境干扰排除（防误判清单）

命中私有地址范围仍**不等于**是真实内网IP。必须逐项检查以下干扰场景：

**版本号干扰**
- 形如 `1.2.3.4`、`10.2.3.4`、`172.16.0.1` 的字符串出现在 `version`、`ver`、`v`、`sdk`、`release`、`build`、`app_version`、`api_version` 字段中，或紧邻 `v` 前缀（如 `v10.2.3.4`），优先视为版本号。
- JavaScript 文件开头的 `/* v10.x.x.x */` 或包名后的版本标识，不认定为IP。

**CSS / 颜色值干扰**
- `rgba(10, 20, 30, 0.5)`、`rgb(192, 168, 1)` 等颜色函数的参数部分与私有段数字重合时，不认定为IP。

**时间戳 / 日期干扰**
- 以点分格式表达日期（如 `2024.10.1.0`）出现在时间相关字段，不认定为IP。

**文档示例与占位符**
- `example.com`、`X.X.X.X`、`0.0.0.0`、`255.255.255.255`、`192.168.x.x` 等示例性写法，不认定为真实内网IP。
- Swagger/OpenAPI/接口文档中的请求示例或模板变量，需结合是否为实际响应数据来判断。

**其他常见干扰**
- Zoom / WebRTC / SDP 协商中的候选地址（需确认是否为本机或服务端回送的真实私有地址，部分为客户端自身的局域网地址，暴露价值有限）。
- 内容安全策略（CSP）中列出的 `192.168.0.0/16` 等格式为 CIDR 策略规则，不等同于直接泄露。

### 第三步：真实性确认条件

满足以下任意一条，方可判定为"真实内网IP泄露"：

1. **字段语义支持**：字段名为 `host`、`ip`、`addr`、`address`、`server`、`backend`、`origin`、`upstream`、`peer`、`node`、`endpoint`、`src`、`dest`、`internal`、`intranet` 等网络语义词。
2. **URL/URI 上下文**：该IP出现在 URL 路径、`href`、`src`、接口回调地址或文件下载地址中。
3. **HTTP 响应头**：出现于 `X-Forwarded-For`、`X-Real-IP`、`Via`、`X-Backend-Server`、`Server`、`Location` 等头字段。
4. **异常堆栈/错误信息**：出现在数据库连接失败、服务调用超时等后端报错中，且与服务名、端口一同暴露。
5. **多证据佐证**：同一IP在多个不同接口或页面稳定出现，排除随机占位可能。
6. **关联业务可解释**：IP所处位置与系统的服务调用、文件存储、消息推送等已知功能模块有合理对应关系。

### 第四步：快速排除决策树

```
发现疑似内网IP
├─ 不在 RFC 私有段范围内？ → 排除，不记录
├─ 在私有段范围内
│   ├─ 字段名 / 上下文含义是版本号？ → 排除，标注"版本号误触发"
│   ├─ 出现在 CSS/颜色/日期/文档示例场景？ → 排除，标注"非网络地址"
│   ├─ 仅客户端 WebRTC 本机候选地址？ → 降级，低价值信息
│   └─ 满足"真实性确认条件"中任意一条？
│       ├─ 是 → 确认为真实内网IP泄露，进入后续"关键判断点"流程
│       └─ 否 → 记录为"待确认/可能误报"，不写入漏洞结论
```

## 关键判断点

- 判断真实性：**必须先完成上节"内网IP有效性鉴别"**，确认地址属于私有段且非版本号、CSS值、文档示例等干扰后，再进入此判断流程。
- 判断暴露面：确认信息是否对匿名用户、普通用户、低权限用户可见，还是仅在开发工具、特定流程或异常分支中暴露。
- 判断稳定性：一次性截图不够，至少确认同入口重复请求仍可见，或同类接口存在相同模式，避免把缓存残留误报为长期问题。
- 判断业务关联：单独的内部别名通常弱于“内部地址 + 端口 + 服务角色 + 业务模块”的组合线索。
- 判断拓扑价值：若能推断网关后端、消息服务、文件服务、音视频节点、数据库代理或管理组件，应提高关注度。
- 判断是否需要上调风险：只有当泄露信息明显降低侦察成本、可辅助定位高价值资产、或与系统内其他能力形成可解释链路时，才建议评为中高风险。
- 判断误报边界：公开 CDN、反向代理外网地址、示例文档中的占位值、被充分脱敏的地址片段，一般不应直接认定为该漏洞。

## 证据链要求

- 至少保留一组完整请求与响应，能显示泄露发生的入口、返回位置和外部可见性。
- 至少保留一份页面或抓包截图，能让审阅方直观看到泄露位置位于源码、接口、报错、配置或调试信息中。
- 对中高风险结论，补充一组对照证据，证明该信息具有稳定性、可重复性或多处复用，而不是单次偶发现象。
- 说明访问身份、访问前置条件、功能入口和影响模块，避免报告只写“某接口返回了内网地址”而缺少业务上下文。
- 对敏感内容保留完整原始值和语义，包括内部主机、端口和服务角色，便于后续 Agent 继续验证。
- 如果引用前端代码或异常信息，应标出字段名、变量名、注释位置、资源文件名或报错层级，以便开发快速定位。
- 证据链要能支撑三个结论：泄露真实存在、外部可见、具备辅助侦察或拓扑推断价值。

## 风险定级思路

- 低风险
  - 单一页面、单一注释或单次报错中出现零散内部线索。
  - 不包含明确端口、服务角色或环境信息。
  - 无法证明持续暴露，也看不出明显的业务价值或链路辅助价值。

- 中风险
  - 多个接口、页面或静态资源稳定暴露相同内部地址或主机标识。
  - 同时出现端口、服务名、路径、环境标识、节点信息中的两项及以上。
  - 可较清晰推断系统部署结构、服务边界或关键模块位置，明显降低侦察成本。

- 高风险
  - 对外可见内容稳定暴露多处关键内部节点、端口及角色信息，足以拼接核心网络结构。
  - 泄露内容直接指向高价值内部服务、管理组件、网关后端或关键业务支撑节点。
  - 在测试已有事实中，可合理说明这些线索会显著放大其他已知问题的危害面，即使本步骤本身仍坚持低影响验证。

- 定级时避免机械套用“出现内网地址就是高危”。必须结合暴露面、稳定性、语义完整度、业务价值和链路辅助性综合判断。

## 修复与复测

- 修复方向
  - 清理前端构建产物、注释、调试代码、SourceMap、默认配置中的内部地址与内部主机名。
  - 对接口响应、异常堆栈、网关头、回源报错做统一脱敏，避免把后端真实网络标识返回给前端。
  - 将内部服务通过统一网关、别名或受控代理暴露，避免前端直接感知后端真实位置。
  - 区分开发、测试、生产配置，避免把非生产环境的内部参数打包进入线上资源。
  - 建立代码审查与发布检查项，把“内部地址、内部域名、内部端口、调试标识”纳入上线前扫描。

- 复测方法
  - 按原入口复测页面源码、静态资源、接口返回、错误回显和控制台输出，确认同类位置均已清理。
  - 清缓存后重新加载，并检查历史资源路径、懒加载分包、移动端/H5 与 Web 端是否仍残留旧配置。
  - 复测正常流程与异常流程，避免只修主链路而遗漏报错分支、回退逻辑或调试接口。
  - 若原问题跨多个模块出现，复测时至少覆盖同套前端构建和同网关下的代表性接口，不要只验证单一页面。
  - 复测结论应写明“未再观察到内部网络标识对外暴露”，而不是只写“漏洞已修复”。

## 报告表达模板

- 漏洞概述
  - 在测试过程中，测试人员于 `<entry-point>` 发现对外返回内容包含内部网络线索，例如 `<private-host>`、`<private-port>`、`<internal-service>` 等脱敏信息。该信息可被 `<access-role>` 在无需额外高影响操作的情况下直接获取，说明系统未对内部网络标识做充分隐藏或脱敏处理。

- 风险说明
  - 该问题本身属于信息泄露，但会向外部暴露系统部署结构、服务边界或关键节点线索，可能降低攻击者对目标环境的侦察成本，并在其他问题存在时放大整体攻击面。

- 证据说明
  - 复现时通过访问 `<entry-point>`，在 `<carrier-type>` 中观察到 `<clue-type>`。对照 `<comparison-case>` 后，确认该信息并非前端展示伪造或偶发缓存，而是系统稳定返回的内部网络线索。

- 修复建议
  - 建议清理前端与接口中的内部地址、内部主机名和调试信息，统一收敛回源标识展示方式，完善异常处理与发布检查，避免内部网络结构继续暴露至外部可见面。

- 复测结论
  - 复测时应确认原入口、同类入口及相关静态资源中均不再返回内部网络标识；若仅个别页面修复而同构资源仍泄露，不建议判定为完全修复。
