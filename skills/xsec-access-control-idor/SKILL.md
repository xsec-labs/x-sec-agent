# 业务系统整体越权测试方法论

## 编排适配

- 适用场景：已进入登录后业务区，需要验证对象级权限、水平越权、垂直越权、IDOR、只读资源归属校验。
- 触发信号：`authenticated_session_obtained`、`role_switch_available`、`second_account_available`、`id_like_resource_paths_detected`、`403_or_401_boundary_observed`、`customer_data_fields_detected`。
- 测试前置环境：至少有一个有效登录态；双账号水平/垂直越权需要同级或不同角色测试账号；必须存在只读对象接口、列表/详情/下载/预览请求，且授权方允许最小化对照验证。
- 必需工件：`browser_state`、`request_corpus`、`api_inventory`、`owned_resource_baseline`、`role/account map`。
- 解锁输出：`access_control_boundary_mapped`、`idor_candidate_detected`、`sensitive_data_exposure_candidate`、`file_download_access_control_candidate`。
- 阻断条件：无有效登录态、无可识别对象 ID/资源归属、缺少对照账号、scope 禁止查看其他测试对象或接口只有写操作。

## 适用场景与前提

**适用场景**：已对目标业务系统取得合法登录权限，在授权范围内验证访问控制是否正确实施。

**测试前提**：
- 已有至少一个可登录的测试账号（Cookie 或 Token 有效）。
- 明确授权边界：仅对目标系统的访问控制逻辑做只读验证，禁止任何增加、修改、删除操作。
- 测试发现的问题只用于出具报告，不做漏洞利用、数据下载或扩散。

**测试覆盖的三类场景**（按账号数量分支）：

| 账号条件 | 测试类型 | 目标 |
|----------|----------|------|
| 仅一个账号 | 单账号 IDOR 遍历 | 寻找数字型、可预测 ID 参数，通过自增或相邻值探测他人数据是否可访问 |
| 两个同级账号 | 水平越权 | 用 B 账号的 Cookie/Token 请求 A 账号的私有对象，验证服务端是否校验归属 |
| 两个不同权限账号 | 垂直越权 | 用低权限 Cookie/Token 访问仅高权限角色可见的接口或数据，验证角色鉴权 |

## 铁律：禁止的操作

> 以下操作在任何情况下均不得执行，违反即终止测试。

- **禁止调用任何写操作接口**：POST/PUT/PATCH/DELETE 类请求一律不发，只发 GET 或等价只读请求。
- **禁止修改他人数据**：即使接口允许，也不得提交修改、更新、编辑、删除、绑定、解绑请求。
- **禁止新增任何数据**：不得创建账号、订单、记录、附件、评论、配置项等。
- **禁止删除任何数据**：不得触发注销、撤销、清除、批量删除等操作。
- **仅做读取验证**：以获取到"不应返回的数据"为漏洞证据，截图或记录后立即停止，不扩展遍历范围。

## 分支一：单账号 IDOR 遍历测试

### 适用条件
只有一个测试账号，通过观察接口参数中是否存在数字型、自增型、可预测型对象 ID 来发现越权读取风险。

### 目标参数特征

重点寻找以下形态的参数：

```
GET /api/order/detail?orderId=10023
GET /api/user/info?userId=1001
GET /api/report/view?reportId=8
GET /api/record/get/{id}
GET /api/message/read?msgId=200
```

- 参数值为纯数字（整数或长整数）。
- 参数值具有明显规律：连续自增、时间戳近似值、固定前缀加数字。
- 参数出现在 URL 路径段、Query String 或请求体 JSON 字段中。

### 测试步骤

**步骤 1：识别含数字 ID 的只读接口**
- 使用浏览器开发者工具或抓包工具（Burp Suite）捕获所有 XHR/Fetch 请求。
- 过滤出请求方法为 GET（或明确只读的 POST 查询接口）的请求。
- 标记所有参数中含有数字值且语义为"对象标识"的接口，记录完整请求。

**步骤 2：确认当前账号的合法对象 ID**
- 在正常业务操作中，记录当前账号的合法对象 ID，例如当前用户订单 ID 为 `10023`。
- 保存该请求与响应作为基线（合法访问基线）。
- 确认响应中包含可识别当前账号的字段，例如用户名、手机号、账号 ID。

**步骤 3：构造相邻 ID 进行探测（只读，最多验证 3 个）**
- 将对象 ID 替换为当前值 ± 1（例如 `10022`、`10024`）。
- 保持 Cookie/Token 不变（仍为当前账号）。
- 观察响应：
  - 若返回他人的数据字段（姓名、手机、订单内容与当前账号不符），则存在 IDOR。
  - 若返回空、报错或鉴权失败，说明服务端有校验，记录并继续其他接口。
- **最多验证 3 个相邻 ID**，不做批量遍历，不写脚本循环请求。

**步骤 4：验证差异，确认越权**
- 对比基线响应与越权响应中的关键字段，例如 `userId`、`name`、`phone`、`idCard`、`orderOwner`。
- 若两者字段值不同且越权响应包含他人信息，则确认存在 IDOR 水平越权。
- 截图并记录：接口路径、替换的参数名、替换前后的值、响应中的差异字段。

**步骤 5：签名参数场景的特殊处理**
- 若接口带签名、摘要或加密字段，先判断该字段是完整授权凭据，还是仅由可预测输入派生的完整性校验。
- 若签名可由公开规则和可预测编号生成，或服务端只校验签名格式不校验资源归属，仍需按正常 IDOR 流程验证。
- 签名只能证明参数经过处理，不等于服务端做了对象级授权。

**步骤 6：两步访问模式的验证**
- 若资源访问分两步完成（如：第一步获取临时 token/预签名 URL，第二步凭该凭据读取内容），分别验证：
  - 第一步是否以他人 ID 为参数即可获得可继续访问的二级标识。
  - 第二步是否仅凭该二级标识即可读取目标内容（无需原始身份）。

**步骤 7：扩展同类接口验证（可选，最多 2 个）**
- 对同一资源类型（如"订单"）的其他只读接口（列表、详情、导出、附件）各测一个，确认问题是否为机制性。
- 若列表接口已返回他人订单列表，仅记录该事实，不翻页也不遍历。
- **重点覆盖高频漏检点**：打印页、下载页、预览页、二维码跳转页、消息通知链接常绕开主业务接口的授权中间件，应单独验证这些旁路入口。

### 单账号 IDOR 判定标准

| 现象 | 判定 |
|------|------|
| 替换数字 ID 后返回与当前账号归属不同的真实业务数据 | 确认 IDOR，水平越权 |
| 返回数据但所有字段均为当前账号归属（共享对象） | 非越权，记录并排除 |
| 返回 401/403 或业务层鉴权失败 | 无漏洞，记录服务端有校验 |
| 返回 200 但响应体为空或对象不存在 | 无漏洞，ID 不存在 |

## 分支二：双账号水平越权测试

### 适用条件
已有两个同级别账号（角色相同或相近），验证 A 账号的私有数据能否被 B 账号的会话读取。

> A 账号：持有私有对象（数据属于 A）  
> B 账号：发起请求的攻击方会话（Cookie/Token 为 B 的）

### 测试步骤

**步骤 1：用 A 账号建立基线**
- 用 A 账号登录，正常访问 A 账号的私有对象，例如：
  - 个人信息：`GET /api/user/profile`
  - 订单详情：`GET /api/order/detail?orderId=<A-order-id>`
  - 报告/记录：`GET /api/report/view?reportId=<A-report-id>`
- 记录 A 账号请求（含 A 的 Cookie/Token）和响应，保存为基线证据。
- 记录响应中可识别 A 账号归属的字段（姓名、手机号、账号 ID 等）。

**步骤 2：用 B 账号登录，获取 B 的认证凭据**
- 用 B 账号登录，通过抓包获取 B 账号的 Cookie 或 Bearer Token。
- 在 B 账号正常会话中，记录 B 账号自身的同类对象 ID（如 B 的订单 ID），作为对照。

**步骤 3：用 B 的凭据请求 A 的对象（越权构造）**
- 复制步骤 1 的请求，将认证头或 Cookie 替换为 B 账号的凭据。
- 保持请求路径和参数不变（包括 A 的对象 ID）。
- 仅发送 GET 或只读查询请求，不发送任何修改请求。
- 观察响应：
  - 若返回 A 账号的私有数据（字段值与步骤 1 基线一致，而非 B 的数据），则确认水平越权。
  - 若返回 B 自己的数据（系统忽略参数 ID，以会话身份为准），则无漏洞但记录这一机制。
  - 若返回 401/403 或业务拒绝，则无漏洞。

**步骤 4：验证多个入口（同资源族，最多各取 1 个）**
- 对同一资源的详情、列表、导出等不同入口各测一个，确认问题范围。
- 不对全部接口做穷举，只证明机制性问题存在。

### 水平越权判定标准

| 现象 | 判定 |
|------|------|
| B 的会话请求 A 的对象 ID，响应返回 A 的私有数据 | 确认水平越权 |
| 响应返回 B 自己的数据（系统按会话过滤） | 无漏洞，记录机制 |
| 返回 401/403 或业务鉴权失败 | 无漏洞 |
| A 的对象为共享/公开资源（需业务确认） | 排除，非越权 |

## 分支三：双账号垂直越权测试

### 适用条件
已有两个不同权限级别的账号，验证低权限账号的 Cookie/Token 能否访问仅高权限角色可见的接口或数据。

> `<high-priv-user>`：高权限账号（管理员、审核员、超级用户等）  
> `<low-priv-user>`：低权限账号（普通用户、访客、只读用户等）

### 目标接口特征

重点寻找以下类型的高权限接口：
- 管理后台入口：`/admin/`、`/manage/`、`/backstage/`、`/console/` 前缀路径。
- 用户管理接口：查询全部用户列表、查看任意用户详情（只读验证：查列表/查详情）。
- 审核/审批接口：查看待审核队列、查看审核日志（只读验证）。
- 数据导出接口：全量数据导出、敏感报表接口。
- 系统配置接口：查看系统参数、查看日志配置（只读）。
- 跨组织/跨机构数据：查看其他部门/机构的业务数据。

### 测试步骤

**步骤 1：用高权限账号建立高权限接口基线**
- 用 `<high-priv-user>` 登录，访问其专属的管理接口或高权限数据接口。
- 记录请求（含高权限 Cookie/Token）和响应，保存为基线证据。
- 标记响应中的关键高权限字段，例如用户列表、系统配置项、全量报表数据。

**步骤 2：用低权限账号登录，获取低权限凭据**
- 用 `<low-priv-user>` 登录，获取其 Cookie 或 Bearer Token。
- 在低权限会话下，确认该账号在前端无法访问上述高权限功能（记录前端表现：无菜单、无按钮、跳转登录页等）。

**步骤 3：用低权限凭据直接请求高权限接口（越权构造）**
- 复制步骤 1 的高权限请求，将 Cookie 或 Token 替换为 `<low-priv-user>` 的凭据。
- 不修改请求路径和参数，仅替换认证凭据。
- 仅发送只读请求（GET 或查询类 POST），不发送任何操作类请求。
- 观察响应：
  - 若返回高权限数据（用户列表、配置项、管理数据），则确认垂直越权。
  - 若返回 401/403、无权限提示或重定向到登录，则无漏洞，记录服务端有鉴权。
  - 若返回 200 但数据为空或仅限自身数据，则无漏洞，记录机制正常。

**步骤 4：验证前端隐藏但接口直接可达**
- 若低权限账号前端无菜单/按钮，但通过直接构造请求可访问，应同时保存：
  - 前端截图：确认低权限下无操作入口。
  - 接口响应截图：确认直接请求成功返回高权限数据。
- 两者对比是关键证据，证明权限控制仅在前端，服务端未鉴权。

**步骤 5：覆盖同类高权限接口（最多 2 个）**
- 对同一权限层级的其他只读接口各取 1 个验证，确认是机制性问题。
- 不穷举全部管理接口。

### 垂直越权判定标准

| 现象 | 判定 |
|------|------|
| 低权限凭据请求高权限接口，返回高权限数据 | 确认垂直越权 |
| 前端无入口但接口返回高权限数据 | 确认垂直越权（前端隐藏不等于鉴权） |
| 返回 401/403 或业务无权限提示 | 无漏洞，服务端有鉴权 |
| 返回 200 但仅含低权限自身数据 | 无漏洞，按会话过滤 |

## 通用操作规范

### 认证凭据替换方式

```
# Cookie 替换（在请求头中替换整个 Cookie 字段）
Cookie: sessionid=<target-account-cookie>

# Bearer Token 替换（在 Authorization 头中替换）
Authorization: Bearer <target-account-token>

# 自定义 Token 替换（按系统实际字段名）
X-Auth-Token: <target-account-token>
```

替换时：
- 只替换认证相关字段，不修改其他请求头（User-Agent、Content-Type 等保持不变）。
- 敏感凭据在报告中一律替换为占位符 `<cookie-of-B-account>` 等，不在报告中展示真实 Token。

### 抓包与构造工具使用规范

- **Burp Suite**：使用 Repeater 模块发送单次验证请求，不使用 Intruder 做批量遍历。
- **浏览器开发者工具**：Network 面板复制请求为 cURL，手动替换参数后在命令行发送一次验证。
- **cURL**：手动构造命令，每次只发一个验证请求，不写循环脚本。
- **禁止**：不使用自动化脚本批量遍历 ID；不使用 Intruder/ffuf 等工具对本场景做自动化枚举。

## 证据收集规范

每个发现的漏洞，须同时保存以下证据（缺一不可）：

### 1. 账号与对象说明

```
账号 A（数据归属方）：角色=<role>，账号标识=<A-user-identifier>
账号 B（发起越权请求方）：角色=<role>，账号标识=<B-user-identifier>
目标对象：类型=<resource-type>，ID=<object-id>，归属=账号 A
```

### 2. 基线请求与响应（合法访问）

```
# 账号 A 合法访问其自身对象
请求：GET /api/xxx?id=<object-id>
认证：Cookie: <A-account-cookie-placeholder>
响应状态：200
响应关键字段：{ "userId": "<A-id>", "name": "<A-name>", ... }
```

### 3. 越权请求与响应

```
# 账号 B 使用自身凭据请求 A 的对象
请求：GET /api/xxx?id=<object-id>  ← 与基线路径参数完全一致
认证：Cookie: <B-account-cookie-placeholder>  ← 仅此处不同
响应状态：200
响应关键字段：{ "userId": "<A-id>", "name": "<A-name>", ... }  ← 返回了 A 的数据
```

### 4. 差异说明

```
除认证凭据外，请求保持完全一致。
响应返回了账号 A 的私有数据，证明服务端未将当前会话身份与目标对象归属绑定校验。
```

## 关键判断点

- 服务端是否只校验"是否已登录"，而未校验"当前用户是否有权访问该具体对象"。
- 是否信任客户端传入的 `userId`、`orgId`、`tenantId` 等身份字段（而非从服务端会话中取）。
- 是否仅通过前端菜单隐藏、路由守卫、按钮禁用做权限控制，服务端接口无鉴权。
- 数字型对象 ID 是否连续自增且无对象归属校验，导致可直接遍历他人数据。
- 切换认证凭据后，响应是否仍绑定请求参数中的对象 ID 而非当前会话身份。
- 是否存在"高权限接口路径已知，低权限直接携带自身凭据请求即可成功"的情况。
- 是否为共享资源、公开资源或有明确代理授权关系——若是，须排除后再下结论。
- **带签名参数不是免检理由**：如果签名可由公开规则和可预测编号生成，或服务端只校验签名不校验资源归属，仍可能存在 IDOR。
- **打印页、下载页、预览页、二维码跳转页、内部管理页是高频漏检点**：它们常绕开主业务接口的授权中间件，须单独验证。
- 状态码 `200` 不等于漏洞成立：要对比业务字段、页面标题、记录主键等是否真正切换到他人对象，区分错误页、空结果和缓存页。

## 风险定级思路

| 风险等级 | 典型场景 |
|----------|----------|
| 高危 | 可读取高敏感个人信息（身份证、手机号、医疗记录、资金流水、处方、账单）、管理员数据、跨租户/跨机构数据；或数字 ID 可大规模遍历；可触发后续身份冒用 |
| 中危 | 可读取他人部分详情或摘要，已能证明授权缺失，但批量性有限或数据敏感度中等 |
| 低危 | 仅暴露低敏感元数据，业务前提强，影响范围较窄，但仍违反最小权限原则 |

定级时同时考虑四个维度：**数据敏感度**、**可批量性**、**认证门槛**、**是否可联动其他业务流程**。

- 对象 ID 为数字且可遍历时，风险上调（实际影响面远大于单个样本）。
- 若仅前端可见性异常但服务端最终拒绝，判为权限展示缺陷，不误报为越权。
- 即使只能读取摘要信息（而非完整详情），若摘要含身份、账单、就诊、联系方式或内部编号等敏感字段，仍可构成中危。

## 修复与复测

**修复原则：**
1. 所有敏感接口在服务端做联合鉴权：先验会话身份，再验角色权限，最后验目标对象归属。
2. 身份信息只从服务端可信会话或服务端解出的 Token 声明获取，不信任客户端提交的用户标识。
3. 对象查询条件必须绑定当前主体（"当前用户 + 目标对象"联合查询），不能只按对象主键查询。
4. 前端隐藏、参数加密、ID 混淆不能替代服务端授权控制。
5. 同一资源族的详情、列表、导出、日志、附件、打印、下载、预览、二维码跳转接口须做一致授权，避免修补单点后残留旁路。
6. **签名参数重新设计**：签名应绑定用户身份、目标对象、时效和用途，且服务端仍需独立校验对象归属，不能以签名校验代替授权校验。
7. **审计与限速**：为异常遍历行为补充审计日志、访问限速和告警，降低批量利用效率——但这只能作为纵深防御，不能替代授权修复。

**复测方法：**
- 用原始越权请求（含目标 ID 和越权凭据）复测，确认已返回拒绝或空结果。
- 对同资源族的导出接口、移动端接口、打印接口、二维码跳转接口、后台接口各测一次，确认未残留旁路。
- 若数字 ID 遍历为漏洞触发条件，须确认相邻 ID 请求也返回鉴权失败。
- 若修复包含标识替换或签名升级，仍要验证服务端是否真正校验对象归属，防止"只改编号格式、未改授权逻辑"的旁路。

## 报告表达模板

**漏洞标题**：`<水平越权 / 垂直越权 / IDOR 对象级访问控制缺失>` — `<资源类型>`接口未校验对象归属

**漏洞概述**：系统在处理 `<resource-type>` 查询请求时，服务端未将当前会话身份与目标对象授权关系进行绑定校验，导致 `<B-account>` 可直接读取归属于 `<A-account>` 的非授权数据。

**触发条件**：攻击者持有任意已登录账号的 Cookie 或 Token，将请求中的对象 ID 替换为他人对象 ID（或直接访问高权限接口），服务端即返回非授权数据。

**影响描述**：未授权读取他人 `<敏感数据类型>`；若对象标识为数字且连续，可进一步演变为批量遍历风险。

**证据摘要**：使用账号 B 的凭据请求归属账号 A 的 `<object-id>`，除认证凭据外其余请求完全一致，服务端返回账号 A 的 `<关键字段>`，证明授权控制缺失。

**修复建议**：在服务端对 `<接口路径>` 实施基于会话身份与对象归属的联合校验；禁止信任客户端提交的用户标识字段；对同资源族全部只读接口同步加固并回归复测。

**复测结论**：修复后应验证原漏洞接口、同类接口、导出接口，确认非授权请求均返回明确拒绝或空结果，且不可通过替换等价参数绕过。
