# 验证码、OTP机制缺陷与通知接口滥用测试方法论

## 编排适配

先读 [运行边界与证据口径](../../references/security-boundaries.md)。在分配的节点、预算和低影响约束内执行；`scope_policy` 只做资产归因，新发现的目标记录来源即可，不因 `in_scope=false` 停止；证据保留观察到的原始值，报告与委派只取证明问题所需的最小片段。

- 适用场景：存在图形验证码、短信/邮箱 OTP、找回密码、注册、绑定换绑、通知发送或消息重发接口。
- 触发信号：`captcha_detected`、`otp_endpoint_detected`、`sms_send_endpoint_detected`、`email_send_endpoint_detected`、`notification_send_endpoint_detected`、`password_reset_flow_detected`。
- 测试前置环境：测试手机号/邮箱/账号或测试环境接收端；发送类验证需限制次数，不向真实第三方持续发送。
- 参考工件：`forms/actions`、`api_inventory`、`request_corpus`、`test_recipient`、`captcha_or_otp_baseline`。
- 解锁输出：`captcha_bypass_detected`、`otp_reuse_detected`、`notification_rate_limit_missing`、`weak_pass_check_unblocked`。
- 建议阻断（可低影响补齐时先补证再测）：未发现验证码/OTP/发送接口、无测试接收对象、禁止发码或目标发送能力会影响真实用户。

## 适用场景

- 适用于登录、注册、找回密码、手机号绑定或换绑、邮箱绑定或换绑、实名确认、敏感资料修改、设备绑定、支付前确认、账号激活等依赖验证码或一次性口令的流程。
- 适用于图形验证码、短信验证码、邮件验证码、软令牌口令等"本应一次性、与对象强绑定"的校验因子。
- 适用于怀疑存在验证码绕过、验证码回显、跨账号共享、重复使用、刷新不失效、重发不失效、错误次数无控制等问题的场景。
- 适用于短信/邮箱/通知接口服务端频控缺失场景：发送接口无限速、前端有倒计时但服务端不限制、发送对象可任意指定、多入口共用同一缺陷频控等。
- 适用于邮箱激活链接滥发、业务提醒通知滥用、后台人工重发接口无控制等不以验证码为核心但存在发送能力滥用的场景。

## 测试思想

### 验证码机制
- 把验证码机制拆成五个控制点来审视：生成、发放、绑定、校验、失效。任何一个控制点缺失，验证码都可能退化为装饰性字段。
- 先证明"错误输入仍可完成最终业务动作"，再判断这是绕过、共享、回显还是失效处理缺陷；不要只凭单个接口的成功提示下结论。
- 把"验证码是否可用"与"验证码是否绑定到正确对象"分开看。很多高风险问题不是验证码生成错误，而是没有绑定手机号/邮箱、账号、场景、会话或具体业务动作。
- 把"前置校验"和"最终校验"分开看。若验证码只在独立接口校验，最终业务动作不复核，实际等同于可绕过。

### 发送接口频控
- 先把问题拆成三件事：谁能调用、向谁发送、多久能重复发送。只要其中一项缺少服务端控制，就可能形成滥用风险。
- 把"前端有倒计时"与"服务端有限流"分开判断。界面校验不能约束直接请求，必须看服务端是否阻断。
- 把"接口返回成功"与"通知实际送达"分开判断。只有确认至少一次送达到接收端，证据链才完整。
- 对手机号、邮箱等标识做归一化验证，同一接收对象因格式差异（大小写、+86前缀、空格）绕过频控也成立。
- 始终构造对照组，避免把消息队列延迟、单次补发机制或正常重试误判为漏洞。

## 图形验证码专项测试

图形验证码的核心安全属性是：每张图与其对应答案只能单次有效使用，且服务端必须在最终业务动作处真正核验。以下两类测试覆盖最常见的实现缺陷。

### 图形验证码复用测试

**目标**：确认一张图形验证码是否在首次成功校验后立即失效，还是可被多次重复使用。

**操作步骤**：
1. 在目标业务入口（登录、注册、找回密码等）获取一张图形验证码，记录对应的 `captcha_id`、`challenge`、`img_token` 或类似关联字段和正确答案。
2. 使用该验证码完成一次正常流程，观察服务端是否成功受理（基线）。
3. 不刷新页面，不重新请求图形，立即再次以相同验证码答案提交同一业务请求，观察服务端是否再次受理。
4. 若第 3 步仍成功，则进一步刷新页面后使用同一旧 `challenge` / `img_token` 与答案提交，验证是否跨会话仍可复用。

**判断**：只要服务端在"已成功使用一次"后仍接受相同验证码完成最终业务动作，即可判定存在图形验证码复用缺陷。

**证据固化**：保留两次请求的完整 Request / Response，标注关键字段值相同，以及两次均返回业务成功的结果。

---

### 图形验证码绕过测试（删除参数法）

**目标**：确认服务端是否在最终业务动作处真正校验图形验证码，而不是仅依赖前端拦截或独立的预校验接口。

**操作步骤**：
1. 用 Burp Suite 等代理工具截获目标业务的登录（或其他带图形验证码的）请求，记录完整参数。
2. 构造以下三种变体请求，分别单独发送，观察服务端响应：
   - **变体 A（删除验证码内容）**：保留所有字段，仅将验证码答案字段值置空（`captcha=`）或改为任意错误字符串（`captcha=xxx`）。
   - **变体 B（删除验证码 Token / Cookie）**：在请求中删除 `captchaToken`、`challenge`、`img_token`、`verifyCode`、`captcha_session` 等服务端生成的验证码关联字段（包括 Cookie 中的）。
   - **变体 C（同时删除所有验证码相关字段）**：将验证码答案字段、关联 Token、关联 Cookie 全部移除，仅保留账号、密码等核心凭据。
3. 若任意变体返回与正确验证码相同的业务成功响应，则确认绕过成立。

**常见绕过信号**：
- 删除 `captchaToken`/`challenge` 后服务端仍进入正常登录逻辑。
- 验证码答案改为 `null`、`0`、`undefined`、空字符串后业务请求成功。
- 前端会弹出"验证码错误"但直接发 API 请求（绕过前端校验）后仍返回成功。
- 服务端只在独立校验接口 (`/api/verify-captcha`) 返回成功，但最终业务接口 (`/api/login`) 不再二次校验。

**证据固化**：截图/保存变体请求包和响应包，标注已删除哪些字段，以及服务端仍返回业务成功的结论。

## 短信验证码专项测试

短信验证码的安全属性包括：限速发送、绑定接收号码、强制单次失效、不在响应中回显、足够复杂度。以下四类测试覆盖常见实现缺陷。

### 短信验证码滥发测试（20 随机手机号）

**目标**：确认发码接口是否对接收方号码做了防滥发控制，防止攻击者将系统当作短信炮台。

**操作步骤**：
1. 截获发送短信验证码的 API 请求（如 `/api/sendSms`）。
2. 准备 20 个随机、真实格式的手机号（无需真实存在，仅格式合法），例如 `13x00000001`～`13x00000020`，写入文件或 Burp Intruder payload。
3. 将请求中的手机号字段设为变量，依次替换为上述 20 个号码，按序发送（不并发），每次间隔 3～5 秒，避免网络层速率误判。
4. 记录每次响应码、响应体和耗时。

**判断**：
- 若 20 次请求全部返回"发送成功"（或等效状态码），则确认存在短信滥发（短信轰炸/短信炮）缺陷，系统未对接收方数量或同 IP 发码量做限制。
- 若中途触发限流（如第 N 次返回频率限制错误），记录阈值，评估防护是否足够（通常同 IP 每分钟对不同号码发送 5 次以上应触发限制）。


**证据固化**：保留 Intruder 或脚本的完整请求/响应日志，标注哪些号码全部返回成功以及总次数。

---

### 短信验证码爆破测试（对单号连续发送 20 次）

**目标**：确认同一手机号在短时间内能否被无限次请求发送验证码，验证发码频率限制是否真实生效。

**操作步骤**：
1. 截获发送验证码的 API 请求。
2. 固定手机号为单一测试号码，重复发送 20 次，间隔约 2～3 秒。
3. 记录每次响应，关注是否出现"发送频率过高""已发送，请稍后重试"等限速提示，以及从第几次开始被拒绝。

**判断**：
- 若 20 次均成功（或仅在极高次数后才限流），确认发码接口缺少有效频率限制，可被用于短信轰炸单一用户。
- 正常情况下同一手机号每 60 秒最多允许 1 次发送，或在 N 次失败后进入冷却期。

**证据固化**：保留全部 20 次的响应，重点标注第几次开始出现限制（如未出现则全部标注"发送成功"）。

---

### 短信验证码回包返回漏洞测试

**目标**：确认发码接口的响应体是否直接返回了验证码明文，导致攻击者无需接收短信即可获取验证码。

**操作步骤**：
1. 截获发送短信验证码的 API 请求和完整响应（包括 Response Headers、Body、Set-Cookie）。
2. 在响应体 JSON、HTML、Set-Cookie、自定义响应头中搜索以下模式：
   - 4～8 位纯数字字符串（典型验证码格式）
   - 名称含 `code`、`otp`、`sms_code`、`verify_code`、`auth_code` 等字段
   - 与请求手机号关联出现的数字序列
3. 若响应中出现验证码明文，立即以该值提交校验接口，验证是否可直接完成认证。

**判断**：响应中任何字段直接包含验证码明文即确认漏洞成立，无需进一步验证（属于高危）。

- 原始敏感内容保存到受控证据目录；共享发现、截图展示、报告和委派使用最少必要的原始摘录（xSec 不做自动脱敏）与证据引用，截断只因体积限制并明确标记。

---

### 四位短信验证码爆破测试

**目标**：若系统使用四位数字验证码（1000～9999 共 9000 种），且未做失效或错误次数限制，攻击者可遍历全部组合完成爆破。

**前提判断**（满足以下全部条件才进行爆破测试）：
- 确认当前场景下的验证码为四位纯数字（从发码记录、前端输入框 `maxlength="4"` 或抓包截获明文验证码推断）。
- 确认验证码在测试期间未因超时而失效（单次有效期超过 5 分钟，或无有效期）。
- 确认校验接口无错误次数限制（即连续输错不会锁定，或锁定阈值极高）。

**操作步骤**：
1. 对测试手机号触发一次发码。
2. 截获验证码校验请求（如 `/api/verifyCode`），定位验证码参数字段。
3. 使用 Burp Intruder（Sniper 模式）或脚本构造 `0000`～`9999` 的数字 payload。
4. 设置合理速率（如每秒 5～10 次），依次发送，观察响应差异（成功时响应长度、状态码或 body 通常不同）。
5. 定位到正确值后停止发送，不要遍历完全部 payload 除非必要。

**判断标准**：
- 若在遍历过程中命中正确验证码并完成最终业务动作，确认四位验证码爆破成立（高危）。
- 若遍历约 100～200 次后触发锁定或 IP 封禁，评估锁定阈值和强度，记录防护生效时机。

**证据固化**：保留触发成功时的请求/响应对，以及 Intruder 结果列表（可仅截取成功附近的若干条），标注验证码值、请求次数、是否完成最终业务动作。

## 邮箱验证码与邮件通知专项测试

邮箱场景与短信场景的测试逻辑基本相同，但有以下差异需特别关注：
- 邮件送达时间比短信更不稳定，需用可控测试邮箱（如自建 SMTP 接收端）作为证据接收端，避免延迟误判。
- 邮箱地址存在格式变体（大小写、+别名、点分隔）可能绕过归一化校验。
- 邮件通知类型更多样：验证码邮件、激活链接邮件、业务提醒邮件各需单独判断。

### 邮箱验证码滥发测试

**目标**：确认邮件验证码发送接口是否对接收方邮箱做了防滥发控制。

**操作步骤**：
1. 截获邮件验证码发送 API 请求（如 `/api/sendEmailCode`）。
2. 准备多测试邮箱地址（或格式合法但不存在的地址），依次替换接收方字段，按序发送（每次间隔 3～5 秒）。
3. 记录每次响应码和响应体，关注是否出现频率限制错误或静默成功。

**判断**：对多个不同邮箱地址连续请求均返回成功，说明服务端未对同 IP 或同账号的邮件发送量做有效限制。

### 邮箱格式归一化绕过测试

**目标**：确认服务端是否对邮箱地址归一化后再做频控，防止通过格式变体绕过冷却限制。

**测试变体**（以 `test@example.com` 为基础）：
- 大小写变体：`Test@example.com`、`TEST@EXAMPLE.COM`
- 加号别名：`test+1@example.com`、`test+pentest@example.com`
- 点分隔（Gmail 等）：`t.e.s.t@example.com`
- 域名大小写：`test@EXAMPLE.COM`

**判断**：若使用格式变体后可绕过冷却期继续发送，且最终送达同一邮箱，说明服务端缺少统一归一化校验。

### 邮件激活链接滥发测试

**目标**：确认注册激活、邮箱绑定、密码重置等发送激活链接的接口是否有频率限制。

**操作步骤**：
1. 定位激活邮件发送入口（注册页"重新发送激活邮件"、个人中心"绑定邮箱"等）。
2. 对同一接收邮箱在短时间内触发多次发送，观察服务端是否拒绝。
3. 记录接收端实际收到的邮件数量和时间间隔，与服务端响应对照。

**判断**：服务端持续返回成功且接收端收到多封邮件，确认激活链接滥发成立。

### 邮箱验证码回包返回测试

**目标**：确认发码接口响应是否直接返回邮件验证码明文。

**操作步骤**：与短信验证码回包测试相同，在邮件发码接口的响应体、响应头、Set-Cookie 中搜索 4～8 位数字或邮件 token 字段。

**判断**：响应中任何字段包含验证码明文或可直接替代验证码的令牌即确认漏洞成立。

## 通知接口频控与滥用专项测试

适用于不以验证码为核心，但系统具备发送能力的接口，例如：预约提醒、招聘报名通知、业务消息提醒、后台人工触发重发、营销推送等场景。

### 测试步骤

1. 确认范围，优先使用测试手机号和测试邮箱。
2. 定位发送入口：从页面交互、接口命名、抓包记录中定位入口，记录请求方法、参数、是否需要登录态、是否依赖图形验证码。
3. 建立基线：单次触发发送并确认接收端收到通知（证明接口确实有发送行为）。
4. 构造频控对照：在预期冷却时间内对同一接收对象重复最少次数请求，观察服务端是否拒绝或继续发送。
5. 构造多对象对照：保持调用方不变，切换接收对象，判断限制是按接收对象、按账号、按 IP 还是根本不存在。
6. 测试格式绕过：若存在冷却限制，尝试以手机号格式变体（+86、空格、区号）或邮箱格式变体绕过。
7. 测试多入口覆盖：检查同一业务是否有多个发送入口（注册页/个人中心/后台重发/开放接口），各入口是否共用同一频控策略。
8. 收集证据后立即停止，整理请求样例、接收端多条通知证明。

### 关键判断

- 未登录即可调用且接收对象可任意指定，风险高于已登录接口。
- 已登录低权限用户可对任意手机号或邮箱重复发送，仍构成滥用风险。
- 若仅个别入口修复，其他入口仍可触发，应按"控制点覆盖不完整"报告，而非单接口问题。
- 若发送对象只能是当前账号已绑定的本人联系方式且有总量限制，通常接近低危骚扰，不宜夸大。

---

1. 信息收集：定位验证码出现的业务入口及所有发送能力入口，记录页面动作、请求顺序、关联参数和响应差异，重点关注 `<code>`、`<captcha>`、`<challenge_id>`、`<scene>`、`<phone>`、`<email>`、`<account>`、`<ticket>`、`<nonce>` 等字段是否贯穿完整流程。
2. 建立基线：测试对象完成一次正常流程，记录"发码请求、校验请求、最终业务请求"三段链路，确认成功路径和状态变化，以免后续异常样本没有参照物。
3. 构造错误对照组：仅修改验证码相关变量，分别测试"错误验证码""空验证码""删除验证码参数""替换关联对象字段""复用旧验证码"几种最小差异，观察最终业务是否仍成功。
4. 验证绕过链路：若前端存在验证码但最终请求中不带校验因子，或带了任意值也能成功，优先判断为后端未校验；若先调用独立校验接口成功，再改动最终请求仍可通过，优先判断为校验结果未绑定最终动作。
5. 验证失效链路：在单个对象上验证一次"成功后复用"、一次"失败后复用"、一次"刷新或重发后旧码复用"，确认验证码是否真正做到一次性和状态失效，不要进行多轮高频尝试。
6. 验证共享链路：仅在两个受控账号或手机号/邮箱之间做最小化对照，检查同一验证码是否可跨接收对象、账号、场景使用。
7. 验证回显链路：检查发码接口、校验接口、前端存储、调试日志、错误提示中是否直接返回验证码；邮件场景同样需检查响应头和 Set-Cookie 中的验证码明文。
8. 验证发送频控：对短信/邮箱/通知发送接口，验证同一接收对象连续触发是否受服务端限制；测试格式变体（+86 前缀、大小写、点分隔别名）是否可绕过频控；检查注册页/找回密码页/个人中心/后台重发等多个发送入口是否共享同一频控策略。
9. 评估影响面：在已确认单点缺陷后，仅扩展验证同一系统内的相邻高价值场景，如登录、找回密码、换绑手机号/邮箱、敏感资料修改。
10. 固化证据：对每一种成立结论至少保留一组"正常样本"和一组"异常样本"，标明差异字段、时间点、对象关系和最终业务结果。
11. 修复复测：修复后按同一矩阵复测，确认覆盖生成、绑定、校验、失效四个核心控制点，以及全部已知发送入口。

## 关键判断点

- 绕过成立的关键不是验证码接口返回什么，而是错误码、空码或任意码是否仍能完成最终业务动作。
- 未失效成立的关键不是页面有没有刷新，而是同一验证码在成功使用后、失败后、刷新后、重发后是否仍能被服务端接受。
- 共享成立的关键不是多个对象是否都收到了短信，而是同一验证码或同一校验状态能否跨手机号、账号、会话或业务场景成立。
- 回显成立的关键不是前端能看到"发送成功"，而是响应包、前端变量或本地存储中是否出现验证码明文，或出现可直接替代验证码的校验凭据；邮件场景需额外检查响应头与 Set-Cookie。
- 发送频控缺失成立的关键：服务端在预期冷却期内对同一接收对象连续返回成功，且接收端实际收到多条通知；仅前端倒计时不构成有效控制。
- 格式绕过成立的关键：使用手机号或邮箱的格式变体后，服务端视为不同对象并继续发送，最终送达同一接收端。
- 高风险判断通常来自"验证码缺陷直接影响身份确认或敏感操作确认"，例如登录、找回密码、换绑、重置口令、实名绑定等。
- 中风险判断通常来自"验证码缺陷主要削弱自动化防护"，例如图形验证码形同虚设，但仍需正确账号口令或其他前置条件；短信/邮箱滥发可对任意目标骚扰但不直接影响身份。
- 误报排除要点包括：前端显示异常但最终业务未成功、同一手机号/邮箱短时间收到同码但服务端仍单次校验且单场景绑定、测试对象本身处于免验证白名单或调试态。
- 若仅发现缺少频率限制，不要直接上升为可爆破结论；应结合验证码绕过、未失效或对象未绑定等事实综合判断。

## 证据链要求

- 保留一条完整业务链路的关键节点：发码前界面状态、发码请求、校验请求、最终业务请求、最终结果页面或响应。
- 对照证据必须成对出现：一组正常样本证明流程可用，一组异常样本证明仅改动验证码相关条件后仍出现不应有的成功结果。
- 每条证据都要标注时间点、测试对象原始身份、对象关系和相关原始账号/手机号，确保后续 Agent 可直接复用。
- 绕过类证据应突出“最终成功”和“验证码变量异常”之间的对应关系，不要只截图输入框或单独的预校验接口。
- 共享类证据应突出“一个验证码对应多个对象”或“一个对象收到的验证码可作用于另一个对象”。
- 回显类证据应截取最小必要响应片段，证明服务端返回了验证码或等效凭据，同时避免展示完整响应体、完整会话标识或其他无关敏感字段。
- 未失效类证据应至少体现两次使用关系，例如首次使用与再次复用的时间顺序、是否重发、是否刷新、最终结果是否都成功。- 发送频控缺失类证据：保留至少一组基线请求（证明接口可触发发送）和一组时间接近的重复请求结果（服务端未阻断），以及接收端收到多条通知的原始截图；保留真实手机号、邮箱地址和完整消息内容。
- 格式绕过类证据：对照展示原始格式与变体格式的两次请求，以及接收端实际收到多条通知，说明服务端未做归一化判断。- 复测证据应与初测使用相同路径和同类对照组，证明问题确已消失，而不是仅更换了一个入口或仅改变了前端提示。

## 风险定级思路

- 高危：可绕过登录、找回密码、换绑手机号/邮箱、重置口令或其他敏感操作确认；或短信/邮箱验证码在响应包中直接回显；或四位验证码无失效且无错误次数限制（可遍历爆破）；或同一验证码可跨账号、跨手机号/邮箱完成身份冒充；或未登录即可对任意目标持续发送且无任何服务端限制。
- 中危：图形验证码后端未校验（参数删除可绕过）；图形验证码可多次复用；短信/邮箱发码接口无频率限制（可轰炸单一接收对象）；验证码未失效、可重放或可共享，已显著削弱防自动化和身份核验能力，但仍需其他条件才能完成高价值动作。
- 中危偏高：短信/邮箱滥发（可对任意目标批量发码），叠加无速率限制或可格式绕过时应上调，因为会对第三方造成骚扰并消耗通信资源。
- 低危或提示：仅能对本人已绑定接收对象发送且需登录，影响主要是骚扰与体验下降，没有任意目标发送能力；或问题仅影响前端展示、低敏感流程，无法证明身份确认被削弱。
- 若同时存在"验证码可绕过 / 回显 / 爆破 + 无频率限制 + 对象未绑定"，风险应上调，因为漏洞更容易被稳定利用。
- 风险定级应结合业务后果而非只看技术现象，重点问三个问题：能否冒充身份，能否接管流程，能否稳定自动化重复。

## 修复与复测

- 修复方向应覆盖服务端全链路，而不是只改前端校验。验证码必须在服务端生成、服务端保存摘要或状态、服务端绑定对象并在最终动作处复核。
- 验证码必须绑定至少以下要素中的必要集合：账号或手机号、业务场景、会话或事务标识、有效期、尝试次数、单次使用状态。
- 成功使用后应立即失效；重发后旧码应失效；刷新图形验证码后旧图对应答案应失效；达到失败阈值后应触发冷却、重发或重新挑战。
- 任何响应、日志下发、前端变量或本地存储都不应暴露验证码明文，也不应暴露可直接替代验证码的校验令牌。
- 短信或OTP发送接口应限制一次请求对应一个对象，避免通过数组、分隔符、重复参数或批量字段造成共享或滥发。
- **针对图形验证码**：删除请求中验证码答案、`captchaToken`、`challenge` 等任意字段后，最终业务接口应返回明确失败，而非绕过校验。
- **针对短信/邮箱滥发**：同一 IP 对不同手机号/邮箱的发码请求应受每分钟次数限制；触发限制后应返回明确的频率限制错误而非静默成功。
- **针对短信/邮箱轰炸**：同一接收对象的发码请求应设 60 秒冷却期，并在 N 次内（通常 5 次/小时）强制拒绝后续请求。
- **针对格式归一化**：对手机号（+86、空格、区号格式）和邮箱（大小写、+别名、点分隔）做统一归一化，再进行重复判定和频控，避免同一接收对象因格式差异绕过限制。
- **针对验证码回显**：发码接口响应体及所有响应头中不得包含验证码明文；校验接口不得返回正确答案作为提示；前端 JS 不得在本地存储或注释中保存验证码值。
- **针对四位验证码爆破**：短信/邮件验证码应升级为六位或以上；或在连续错误 N 次（通常 5 次）后锁定账号或该业务流程；或设置 5 分钟以内的强制失效期。
- **针对多入口覆盖**：修复应统一覆盖所有同类发送入口（注册/找回密码/个人中心/后台重发/开放接口），不能只修复触发点最明显的那一个。
- 对异常发送频率建立日志与告警，但"仅记录日志"不构成充分修复；日志只能帮助发现，不能替代阻断。
- 复测时至少验证九项：错误码拦截、空码拦截、删除参数拦截、旧码失效、重发后旧码失效、跨对象不可用、发码频率限制（同对象）、批量发码限制（不同对象）、最终业务接口会复核验证码状态。
- 若系统存在多个入口复用同一验证码组件，复测不要只测登录页，还要抽查找回密码、换绑、注册、邮箱绑定和其他敏感动作入口。
